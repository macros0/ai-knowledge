# Инструкция разработчика: подключение своего сервиса к корпоративному SSO (Keycloak IDB)

Основано на внутреннем документе компании про SSO (Keycloak IDP + IDB, федерация с AD через LDAP).
Ваша роль как разработчика приложения — **клиент OIDC**, вся работа с AD/LDAP/Kerberos скрыта за Keycloak IDB.

---

## Шаг 0. Понять архитектуру, прежде чем писать код

**Что делать:** прочитать схему целиком и зафиксировать для себя три сущности:
- **IDP (Identity Provider)** — Keycloak, напрямую федерирован с AD по LDAP. Хранит правду о пользователях и группах.
- **IDB (Identity Broker)** — второй Keycloak, который забирает у IDP личность пользователя через OIDC и раздаёт токены конечным приложениям.
- **Ваше приложение** — OIDC-клиент, подключается **только к IDB**, никогда напрямую к IDP или AD.

**Что вам нужно изучить:**
- Разница между Identity Provider и Identity Broker — зачем нужен посредник, если можно подключиться прямо к AD (ответ: изоляция протоколов, единая точка входа для десятков разных сервисов, возможность сменить AD на другой каталог без переделки всех клиентов).
- Базовые термины OAuth2/OIDC: **Authorization Server**, **Resource Server**, **Client**, **Access Token**, **ID Token**, **Refresh Token**, **Realm** (в Keycloak — изолированный "тенант" с своими клиентами и пользователями).
- Прочитать про **Authorization Code Flow** — это стандартный сценарий входа через браузер, именно его вы будете реализовывать.

## Шаг 1. Узнать параметры подключения у администратора IDB

**Что делать:** написать команде, которая держит Keycloak IDB (в документе фигурирует как отдельный "Ответственный" с контактом), и запросить:
- URL Keycloak IDB и название **realm** (в документе пример: `https://mes-conf.kube-01-conf.private.ziiot-mes-cloud.ru`, realm `mes_conf`).
- **Discovery endpoint** — `{KEYCLOAK_URL}/realms/{REALM}/.well-known/openid-configuration`. Это единственный URL, который вам реально нужен: из него ваша OIDC-библиотека сама вытащит все остальные адреса (authorization_endpoint, token_endpoint, jwks_uri и т.д.).
- Список claim'ов, которые IDB отдаёт в токене — в первую очередь `preferred_username`, `email`, и групповой claim (в документе он называется `group`, см. Mapper Type = *Advanced Claim to Group*).

**Что вам нужно изучить:**
- Что такое `.well-known/openid-configuration` и зачем он — это JSON-манифест, где Authorization Server публикует все свои endpoint'ы, поддерживаемые алгоритмы подписи токенов и т.п. Стандарт OIDC Discovery.
- Разбор JWT токена "на глаз" — попробуйте вручную раскодировать любой ID Token на [jwt.io], чтобы увидеть, какие claims реально приходят.

## Шаг 2. Запросить создание клиента (Client) в Keycloak IDB

**Что делать:** это административное действие, вы сами его не сделаете (нужны admin-права в Keycloak) — нужно попросить админа IDB создать клиента со следующими параметрами (см. в документе раздел "Создание клиента для IDB"):
- **Client authentication:** On (значит это *confidential client* — у вас будет `client_secret`, а не публичный SPA-клиент).
- **Authentication flow:** Standard flow (это и есть Authorization Code Flow).
- **Direct access grants:** включать только если вам реально нужен вход по логину/паролю напрямую из backend (Resource Owner Password flow) — для большинства веб-приложений не нужен, безопаснее оставить выключенным.
- **Valid redirect URIs:** укажите точный URL вашего приложения, куда Keycloak будет возвращать пользователя после логина, например `https://your-app.company.local/auth/callback`.
- Client Scope: обычно достаточно scope `profile` + кастомный scope с групповым mapper'ом (см. документ, Figure 1–2: Mapper *Group Membership*, Token Claim Name `group`).

**Получите от админа:** `client_id`, `client_secret`, точный `redirect_uri`, который был зарегистрирован.

**Что вам нужно изучить:**
- Разница между **confidential** и **public** client в OIDC (confidential — секрет хранится на сервере, используется для классических серверных веб-приложений; public — для SPA/мобильных, где секрет невозможно скрыть, и вместо него применяется PKCE).
- Что такое **redirect_uri** и почему Keycloak жёстко проверяет его на точное совпадение (это защита от подмены получателя токена — классическая атака через open redirect).
- Понятие **scope** в OAuth2 — это то, какие "порции" данных и прав клиент запрашивает у токена.

## Шаг 3. Реализовать Authorization Code Flow в приложении

**Что делать (общий алгоритм, независимо от языка):**
1. Пользователь заходит в ваше приложение неавторизованным → редиректите его на `authorization_endpoint` Keycloak с параметрами `client_id`, `redirect_uri`, `response_type=code`, `scope=openid profile email <ваш_scope>`, и случайным `state` (защита от CSRF).
2. Keycloak сам показывает форму логина (или пропускает через SSO/Kerberos, если сессия домена уже есть) и после успеха редиректит пользователя обратно на ваш `redirect_uri` с параметром `code`.
3. Ваш backend делает POST-запрос на `token_endpoint`, обменивая `code` + `client_secret` на `access_token`, `id_token`, `refresh_token`.
4. Из `id_token` (это JWT) вы читаете claims — логин, email, группы — и создаёте/находите пользователя в своей БД, открываете сессию.
5. `access_token` дальше используете, если нужно ходить в другие защищённые API от имени пользователя.

**Для вашего Python-стека:** используйте библиотеку `authlib` (проще и современнее) или `python-jose` + `requests` вручную. `authlib` умеет сам скачать discovery-документ и сделать весь flow за вас.

```python
from authlib.integrations.flask_client import OAuth

oauth = OAuth(app)
oauth.register(
    name='keycloak',
    client_id='ваш_client_id',
    client_secret='ваш_client_secret',
    server_metadata_url='https://KEYCLOAK_URL/realms/REALM/.well-known/openid-configuration',
    client_kwargs={'scope': 'openid profile email'}
)
```

**Что вам нужно изучить:**
- Что такое JWT и как проверяется его подпись через **JWKS** (`jwks_uri` из discovery-документа) — без этого нельзя доверять содержимому токена.
- Разницу между `access_token` и `id_token` — новички часто путают: `id_token` — это "паспорт" пользователя для вашего приложения, `access_token` — "ключ доступа" к чужим API.
- Concept **state** и **nonce** параметров — зачем они нужны для защиты от CSRF и replay-атак.
- Если будете делать SPA (фронтенд без backend) — обязательно изучите **PKCE** (Proof Key for Code Exchange), без него публичный клиент небезопасен.

## Шаг 4. Смаппить claims токена на модель пользователя в вашей БД

**Что делать:** при первом входе пользователя — создать локальную запись (логин/email из токена), при последующих — обновлять. Роли/права в приложении назначайте на основе группового claim `group` из токена (в документе группы называются по шаблону типа `Admin_AIB_CONF`, `Users_Viewer_LOAD` — у вас список будет свой).

Пример обработки:
```python
groups = id_token_claims.get('group', [])
if 'Admin_YourApp' in groups:
    role = 'admin'
elif 'Users_YourApp' in groups:
    role = 'user'
else:
    role = None  # доступ не подтверждён — отказать
```

**Что вам нужно изучить:**
- Как в вашем IDB настроен групповой mapper (Advanced Claim to Group) — уточните у админа точный формат claim'а (массив строк, вложенный JSON и т.п.), не угадывайте.
- Принцип **fail-closed**: если группа не распознана — не пускать пользователя, а не давать доступ "по умолчанию".

## Шаг 5. Продумать обновление и истечение сессии (refresh)

**Что делать:** `access_token`/`id_token` живут недолго (обычно 5–15 минут). Нужно реализовать обновление через `refresh_token` на `token_endpoint` с `grant_type=refresh_token`, либо просто открывать новую браузерную сессию через Keycloak, если пользователь уже залогинен в домене (тогда редирект на Keycloak пройдёт мгновенно, без формы пароля — это и есть эффект "бесшовности").

**Что вам нужно изучить:**
- Тайм-ауты токенов и что значит "session at Keycloak" отдельно от "token в вашем приложении" — это разные жизненные циклы.
- Логику **single logout (SLO)** — если пользователь разлогинился в Keycloak, надо ли принудительно завершать его сессию в вашем приложении (обычно да, через `end_session_endpoint` из discovery-документа).

## Шаг 6. Тестирование и типичные ошибки

**Что проверить перед сдачей:**
- Redirect URI в вашем коде **побайтово** совпадает с зарегистрированным в Keycloak (частая причина ошибки `invalid_redirect_uri`).
- Токен реально проверяется по подписи (JWKS), а не просто декодируется без валидации — иначе это дырка в безопасности.
- Что происходит, если группа пользователя пуста или не размаппена — приложение должно вежливо отказать, а не пускать с дефолтными правами.
- Логаут корректно завершает сессию и в приложении, и (если нужно) в Keycloak.

**Что вам нужно изучить:**
- Частые коды ошибок OIDC: `invalid_grant`, `invalid_client`, `unauthorized_client` — научитесь их читать в логах Keycloak и в ответах `token_endpoint`.

## Краткая шпаргалка по терминам

| Термин | Что это |
|---|---|
| IDP | Identity Provider — источник правды о пользователях (здесь: Keycloak + LDAP-федерация с AD) |
| IDB | Identity Broker — посредник между IDP и вашим приложением |
| Realm | Изолированное пространство клиентов/пользователей в Keycloak |
| Client | Регистрация вашего приложения в Keycloak |
| Authorization Code Flow | Стандартный сценарий логина через браузер с обменом code → token |
| ID Token | JWT с данными о пользователе (кто залогинился) |
| Access Token | JWT-ключ доступа к API от имени пользователя |
| JWKS | Публичные ключи для проверки подписи токена |
| Claim | Поле внутри токена (например, `email`, `group`) |
