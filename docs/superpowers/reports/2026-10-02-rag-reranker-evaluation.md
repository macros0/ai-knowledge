# Результат первого эксперимента с reranker — 02.10.2026

**Промежуточное решение: текущую конфигурацию не включать; оценку качества продолжить.** BGE достаточно быстра для одиночного поиска на этом GPU, но один worker без очереди обеспечивает scoring только для половины одновременно поступающих запросов. Это ниже заранее заданных 95%. Qwen при 80 блоках превышает бюджет 3 секунд. Этот отказ ограничивает допуск к пилоту, но не мешает измерить качество перестановки на сохранённых источниках.

Оценка качества продолжена и показала выигрыш ранжирования на holdout: **nDCG@10 0,868 → 0,922**, прирост **+0,0539**, paired bootstrap 95% CI **[+0,0024; +0,1090]**. Обязательные источники не потеряны. Проверка парных ответов продолжается; вывод об улучшении самих ответов пока не сделан.

Отчёт разделяет качество порядка, факты/цитаты ответов и ресурсный допуск. Рабочий retrieval, API, генератор, `.env` и история чатов не менялись; коммит и пуш не выполнялись.

## Что реализовано

В `backend/test_scripts/reranker_eval/` находятся capture канонических источников через существующие функции chat API, проверка корпуса и содержимого dirty checkout, стабильная перестановка префикса, окна текста, два модельных адаптера и JSONL worker. Runner завершает процесс при таймауте/отмене, отклоняет неполные оценки и сохраняет исходный порядок при отказе. Следующий запрос при занятом worker получает `busy` без очереди.

CLI `backend/test_scripts/benchmark_reranker.py` поддерживает `capture`, `freeze`, `screen`, `profile`, `replay`, `report`, `answers`. `screen` и `profile` разрешают предварительную проверку ресурсов на development без разметки; их результаты явно помечены `performance_only`, их нельзя использовать в отчёте качества или генерации сравнительных ответов. Обычный replay требует frozen labels, holdout — совпадающую замороженную конфигурацию, включая deadline. Answers проверяет manifest и полный текст источников до генерации; критические/no-answer вопросы получают три пары ответов.

Эталон из 48 вопросов проверен и заморожен: 8 групп по 6, development/holdout по 24 с разделением семейств и выбранных документов. Проверены все 1342 появления источников по 552 различным текстам и 97 исходным чанкам 19 документов. Независимый проверяющий не получал рангов и результатов моделей; после него проверены полное покрытие пула, неизменность запросов/split, положительные mandatory, точные offsets 360 положительных canonical/raw цитат. Исправлены 311 оценок черновика. Итог: 982×0, 229×1, 131×2; 63 обязательных источника; неизвестных оценок нет. Реальные тексты и артефакты остаются только в игнорируемом `tests/artifacts/reranker/`.

Проверка сохранила реальное противоречие условий в ФС/ТС, модальность обсуждаемого решения в переписке и границы авторства. Обнаружены два отдельных ограничения: один необходимый раздел отсутствует в итоговом пуле; другой факт присутствует в canonical content, но не в обрезанном mail_fragment, выбранном для scoring. Обрезанные XML-схемы не считались прямым свидетельством полей, которых в их тексте нет.

## Оборудование и фиксированная политика

- Windows 10 x64, Python 3.12.10; AMD Ryzen 7 7840HS; около 31,7 GiB физической RAM.
- NVIDIA RTX 5070 Ti, 16303 MiB VRAM, driver 610.88. До model smoke было свободно 13218 MiB. Worker ограничен 37,5% памяти GPU и четырьмя CPU threads.
- Отдельное окружение `tests/tmp/reranker/venv`: PyTorch `2.11.0+cu128`, Transformers `4.57.6`, sentencepiece `0.2.1`; полный lock — `requirements.lock.txt`. CUDA smoke пройден. Backend dependencies не изменены.
- Batch 8, FP16, SDPA; максимум четыре окна по 1024 токена, overlap 128, общий лимит пары 2048, max aggregation. N=40/80; хвост, множество и каноническое содержимое блоков сохраняются.
- Холодный запуск в синтетических smoke: BGE 5,84 с, Qwen 4,85 с. Он измеряется отдельно и не включён в тёплые p95. Worker не загружается внутри запроса.
- Генератор остаётся на существующем CT101. CPU inference, пиковый RSS worker и время до первого токена не измерялись. Добавочная стоимость scoring при активной удалённой генерации измерена отдельно ниже; полного end-to-end нагрузочного замера нет.

| Модель | Immutable revision | SHA256 весов |

| BAAI/bge-reranker-v2-m3 | `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e` | `d9e3e081faff1eefb84019509b2f5558fd74c1a05a2c7db22f74174fcedb5286` |

Веса получены с официального Hugging Face, хеши сверены с LFS metadata. Из-за таймаута полного потока использовалась загрузка диапазонами. Модель не получает разрешения загружать код (`trust_remote_code=False`).

## Предварительная матрица времени

По 24 development-вопроса на конфигурацию, после одного warmup. Измеряется подготовка/IPC/окна/tokenization/inference/перестановка на сохранённых блоках, без повторного retrieval и генерации ответа. Deadline 30 секунд используется только для диагностики фактической длительности; порог приёмки остаётся 3 секунды. Малый screen не проходит acceptance независимо от скорости.

| Модель | N | p50, с | p95, с | Успешно scored | >3 с | Пик CUDA tensors, GiB |
|---|---:|---:|---:|---:|---:|---:|
| BGE | 40 | 0,169 | 0,931 | 24/24 | 0 | 1,42 |
| BGE | 80 | 0,171 | 1,315 | 24/24 | 0 | 1,42 |
| Qwen | 40 | 0,571 | 2,720 | 24/24 | 0 | 2,59 |
| Qwen | 80 | 0,663 | **4,224** | 24/24 | 5 | 2,59 |

Всё множество и полное содержимое финальных блоков совпадают с baseline во всех четырёх screen-прогонах. Пик CUDA tensors не равен полной памяти процесса/GPU. Синтетический русский smoke у обеих моделей поставил прямой ответ про ИТ 0003 выше постороннего текста; это только проверка работоспособности.

## 100 парных ресурсных замеров BGE, N=80

BGE взята для дополнительной ресурсной диагностики по результату screen, а не выбрана как победитель по качеству. Development-вопросы циклически повторяются. Baseline — копирование того же списка источников, after — реальный тёплый worker; порядок веток чередуется. Это измерение добавочной стоимости scoring, не end-to-end latency чата. Deadline в этих профилях **3 секунды**.

| Профиль | Пар | Запросов after | Applied | Busy | p95 applied, с | Источники неизменны | Ресурсный gate |
|---|---:|---:|---:|---:|---:|---|---|
| Один запрос | 100 | 100 | 100 | 0 | 1,642 | 100% | Пройден для scoring |
| Два одновременно | 100 | 200 | 100 | 100 | 1,668 | 100% | **Не пройден: 50% <95%** |

Ни одного timeout в этих профилях. Быстрый `busy` не считается успешным scoring. Сохранение источников при fallback обеспечивает корректность ответа, но не выполняет требование покрытия reranker. Это следствие выбранной политики «один job, без очереди», а не неожиданная нехватка производительности GPU.

## Проверка качества на development и holdout

После заморозки эталона выполнены три допустимые конфигурации с фактическим deadline 3 секунды. Qwen N80 ранее исключена по задержке, до просмотра метрик качества.

| Development, 23 answerable | Δ nDCG@10 | 95% CI | Wins / ties / losses | Recall@10 after | p95 scoring, с |
|---|---:|---|---|---:|---:|
| BGE N40 | +0,1410 | [+0,0632; +0,2267] | 15 / 3 / 5 | 1,000 | 1,007 |
| **BGE N80** | **+0,1522** | **[+0,0789; +0,2349]** | **16 / 3 / 4** | **1,000** | **1,422** |
| Qwen N40 | +0,1256 | [+0,0404; +0,2204] | 13 / 4 / 6 | 0,942 | 2,943 |

Baseline Recall@10/20: 0,906/0,986. У всех трёх конфигураций нет новых critical top-20 потерь, полный canonical набор и текст сохранены; 24/24 applied. Эти 24 запроса не заменяют минимум 100 пар ресурсной приёмки. У Qwen один applied-запрос занял 3,007 с; p95 ниже порога, но запас мал.

До просмотра holdout заморожена BGE N80: максимальный development nDCG, разница с N40 составляет 0,0111 и превышает заранее заданный tie-интервал 0,01. Это выбор кандидата для качества; провал parallel coverage не отменён и пилот не разрешён.

Единственный holdout-прогон содержит 24 кейса, из них 20 answerable и 4 no-answer. Модель, окна, N и deadline после результата не менялись.

| Holdout BGE N80 | Baseline | After |
|---|---:|---:|
| Средний nDCG@10 | 0,8679 | 0,9217 |
| Recall@10 обязательных источников | 0,8750 | 0,9583 |
| Recall@20 обязательных источников | 0,9833 | 1,0000 |
| Новые critical top-20 потери | — | 0 |

Прирост +0,0539, CI [+0,0024; +0,1090]; 10 wins, 4 ties, 6 losses. Все ranking quality gates пройдены на этом наборе. Выигрыш неоднороден: broad +0,2353; codes +0,1582; paraphrases +0,0411; tables +0,0150; multiple +0,0058; conditions **−0,0178**; contradictions без изменения. Authorship/no-answer не имеют nDCG и проверяются по ответам. Интервал узко исключает ноль; результат не доказывает улучшение любого запроса или корпуса.

Holdout 24/24 applied, p95 scoring 0,416 с; весь набор/текст блоков неизменен. Отличие от development связано с другим составом входов, поэтому этот малый замер не служит новой оценкой p95 нагрузки.

## Парные ответы и дополнительная нагрузка

Ответы генерируются существующим local_qwen без истории чатов, с неизменными temperature 0,2, thinking=false, output budget 1536 и исходным context budget. Критические/no-answer кейсы получают три пары, остальные — одну; порядок baseline/after чередуется. Каждый результат сохраняется отдельно, manifest включает хеш настроек генерации; fingerprint корпуса проверяется до и после пары.

Первый запуск был заблокирован сетевым sandbox: `chat_budget_unavailable` вызван ConnectError. Разрешённая проверка вне sandbox подтвердила доступность props/tokenizer и n_ctx=32768. Тот же harness продолжен с доступом к существующему генератору; конфигурация сервера не менялась. Неудачные попытки ответов не дали и не являются данными качества.

Во время реальной генерации выполнен дополнительный профиль BGE N80: **100 пар, 100/100 applied, p95 1,445 с**, полный набор/текст источников сохранён. Он подтверждает тёплую стоимость scoring при активном удалённом генераторе; end-to-end время полного ответа и TTFT этим профилем не измеряются.

В источниках и ответах обнаружены разные классы ошибок:

- В одном after-ответе составная ссылка `[12, 13]` не превращается текущим frontend в кликабельные `[N]`. Номера существуют в контексте, но формат ссылки нарушен.
- В двух after-ответах появились новые неподтверждённые утверждения: дата изменения спецификации названа датой вступления в силу; имя параметра TVARVC названо значением подтипа. Правильная ссылка на существующий блок сама по себе не подтверждает утверждение.
- Ошибочная классификация кодов дохода как кодов вычета встречается в обеих ветках и уже содержится в сгенерированной выжимке; первоисточник различает эти категории. Reranker эту ошибку не устранил.
- Часть обязательных деталей отсутствует в обоих ответах: версия отдельного изменения XML, namespace и технические методы. Потери факта в candidate pool, scoring input и выбранном контексте отмечены раздельно: перестановка не добавляет отсутствующий текст.

Генератор и нормализатор во время эксперимента не исправлялись. После 20 сохранённых пар сервер временно вернул `loading_model`; продолжение дождалось готовности той же модели и сохранило manifest настроек. После 36 пар запрос об авторстве вернул `chat_evidence_invalid` (HTTP 422, причина типа ValueError). Неудачный исходный trial сохранён отдельно, без приписывания неизвестной ветке и без повторной выборки до успеха. Экспериментальный сборщик теперь записывает отказ каждой ветки и продолжает независимую вторую ветку; отмена и изменение источников по-прежнему прерывают прогон. Отказ API не считается корректным ответом «автор не указан».

## Гейты и дальнейшее решение

| Проверка | Статус |
|---|---|
| Перестановка без потери/изменения источников | Пройдена в выполненных прогонах |
| p95 ≤3 с, одиночный BGE N=80, 100 пар | Пройдена для тёплой стоимости scoring |
| ≥95% scoring при двух запросах | **Не пройдена** |
| Qwen N=80 p95 ≤3 с | **Не пройдена в предварительном screen** |
| nDCG@10 +0,03; положительный paired CI; Recall/critical top-20 | **Пройдены**: +0,0539, CI [+0,0024; +0,1090] |
| Scoring при активной генерации, 100 пар | **Пройден**: 100/100, p95 1,445 с |
| Факты, отрицания, авторство, цитаты на holdout | В процессе проверки |
| Фоновая генерация: p95 полного ответа ≤+10% | Не измерено |

Ресурсный отказ сохранён; текущая конфигурация не допускается к пилоту. Выигрыш порядка подтверждён на frozen holdout, но проверка ответов ещё не завершена. Возможная следующая ресурсная гипотеза — два независимо ограниченных worker либо явно ограниченный одиночный профиль. Пороги не ослабляются; пул worker не добавлен. Изменение scoring входа для обрезанных писем также требует нового эксперимента, а не подгонки по уже открытому holdout.

## Повторение и проверки

После существующего capture, с уже проверенными моделями в локальном cache, из корня репозитория:

```powershell
& backend/.venv/Scripts/python.exe backend/test_scripts/benchmark_reranker.py profile `
  --cases tests/artifacts/reranker/cases-draft.json `
  --snapshot tests/artifacts/reranker/snapshot-v2.json `
  --worker-python tests/tmp/reranker/venv/Scripts/python.exe `
  --model BAAI/bge-reranker-v2-m3 `
  --revision 953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e `
  --cache tests/tmp/reranker/model-cache --device cuda --top-n 80 `
  --pairs 100 --concurrent 2 --output tests/artifacts/reranker/profile-repeat.json
```

Output создаётся эксклюзивно, существующий результат не перезаписывается. Для screen заменить `profile` на `screen`, убрать `--pairs/--concurrent`, указать `--deadline 30`; N/revision/model задать по таблице. Конфигурация, fingerprint исполнения, cold readiness и причины fallback сохраняются в JSON. Локальная сводка без текста корпуса — `tests/artifacts/reranker/summary.json`; сырые логи — `tests/tmp/reranker/`.

Финальный запуск новых unit/subprocess contracts и связанных suites поиска, источников, области, answer modes, glossary и snapshot: **140 passed за 94,66 с**, одно существующее предупреждение Starlette. Ruff проходит. Независимый code review нашёл ошибки проверки after перед answers, числа повторов, fingerprint файлов, приоритета отмены и числа пар; все исправлены с регрессионными тестами. Полная backend suite, CI и приёмка рабочего UI не запускались: runtime не интегрировался.
