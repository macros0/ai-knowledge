# Приёмка диагностики для администратора

Состояние: реализация в изолированной ветке `codex/admin-diagnostics`; ввод в
production не выполнялся. Исходный код и протокол проверяются синтетическими
событиями. Рабочая ветка синхронизирована с `main` на ревизии `71414f0`;
эта локальная приёмка проводилась до публикации изменений из отдельного worktree.
После синхронизации целевые backend-тесты, включая API диагностики, очередь
документов, таблицы, обработку ошибок и схему БД: `204 passed`;
doc-parser: `400 passed, 1 skipped`; frontend: `258 passed, 1 skipped`;
Ruff по всему backend, Next production build, ESLint по frontend `src`
и `git diff --check` прошли. Последний полный Windows backend-прогон с
CI-порогом покрытия: `2568 passed, 24 skipped`, покрытие `89,41%` при пороге
`85%`; Ruff по всему backend также прошёл. Ранее три параметра Windows-теста
`test_windows_job_removes_descendants_on_every_exit` падали с 3-секундным
лимитом запуска worker, в том числе в неизменённом `main`. В ветке увеличен
только тестовый срок до 15 секунд: все три сценария очистки потомка прошли
в двух последовательных полных backend-прогонах. Два теста, использовавшие
общий `data` worktree, переведены на изолированный `tmp_path`; исходные
ошибки записи воспроизведены, адресные тесты и затем полный набор прошли.
Production-код парсера этими исправлениями не менялся.

| Область | Результат и доказательство |

| Запись и приватность | Строгая схема до записи, ограничения файлов/очереди/квот, отказ от raw LLM dump в production. Тесты `test_diagnostics_schema`, `store`, `recorder`, `privacy`, `dependencies`. |
| Управление | SQL-аудит старта/остановки/просмотра/пакета, RBAC при каждом обращении, CSRF, истечение по монотонным часам и отказ при проблеме аудита. Тесты `sessions`, `api`, `bundle_queue`. |
| Ручная остановка | Новый приём в закрываемый сеанс перекрывается; уже принятые события дописываются перед остановкой, включая задержанную запись. 31 точечный тест recorder/API/lifecycle, затем 46 тестов пакета/очереди/API/lifecycle/recorder прошли. При превышении времени ожидания онлайн-пакет получает `recorder_loss`. |
| Экспорт | Фиксированный состав ZIP, перепроверка каждой строки, CRC/SHA-256, частичность, ограничение размера, защищённое скачивание и lease. Синтетический запрос с chained exception сохраняет код обращения без содержимого исключения в API, spool и ZIP. |
| Offline | CLI не требует БД, отказывает при активном writer, очищает частичный вывод и отмечает `pending_sql`; 8 CLI-тестов и Bash wrapper прошли. Wrapper передаёт только allowlisted Docker state/image для backend/frontend/postgres/qdrant/migrate, а недоступность состояния отмечает gap. На Windows дополнительно собран синтетический ZIP через путь с кириллицей и пробелом, CRC проверен. |
| UI и Node spool | В изолированном браузерном стенде проверены admin start, просмотр событий, сборка и preview, stop, RU/EN. Node пишет счётчики потерь в status файл и обновляет heartbeat; backend читает только проверенные числа и отмечает `frontend_loss`/недоступный статус. Выбор пакета по session ID не смешивается с интервалом; события листаются с фиксированным верхним временем. После синхронизации с `main`: 258 frontend-тестов прошли, 1 skip; ESLint по `src` — 0 ошибок, 40 предупреждений; Next production build успешен. |
| Deploy | Статическая проверка Compose для bundled/external прошла; отдельные spool/mounts, ограниченный Docker log, bootstrap узких ACL. Локальный Docker Desktop и независимый CT 102 Linux smoke обеих топологий прошли: миграция, health, admin lifecycle и restart. На CT 102 выполнены bundled backup/restore в новый проект, offline без PostgreSQL и откат флагов. |

Полный backend-прогон до выноса ZIP-сборки в отдельный процесс завершился:
`2532 passed, 24 skipped`, покрытие `89,62%` при пороге `85%` (2039,43 с).
Предыдущие прогоны не учитываются в приёмке: первый остановился из-за запрета
песочницы на запись в managed worktree, другой дал пять ошибок автосида,
поскольку JSON-манифест изменился во время работы тестового процесса.
`ruff check --no-cache .` чист. Последний полный frontend-прогон:
`255 passed, 1 skipped`;
ESLint — 0 ошибок/41 предупреждение, Next production build успешен.
Doc-parser: `400 passed, 1 skipped`. Нагрузочные серии и storm завершены ниже.
Linux Bash fixtures offline-сборщика и backup/restore дополнительно прошли в
WSL Ubuntu; это не заменяет запуск Compose на Linux staging.
Браузерные сценарии, включая удаление при открытом скачивании, проверены
на одноразовых стендах ниже. Параметры production-ввода владелец выбрал;
само развёртывание ещё не выполнялось.

Повторная read-only рецензия обнаружила и затем были исправлены: штатный
рестарт frontend через PID 1/IPC, преждевременный отказ narrow bundle при
заполненном несвязанными событиями spool, участие браузера по вкладке,
append во время frontend snapshot, абсолютный обрыв скачивания, отсутствие
Docker state и `migrate`, session selector/pagination и stale `.tmp`. Точечные
тесты backend (27) и frontend проверяют эти границы; Linux SIGTERM-тест добавлен
в frontend CI, но на Windows пропущен. PID 1 не захватывает marker после OOM.

Поздняя read-only рецензия выявила две неполноты: изменение снимка добавлением
битой строки после расчёта manifest не влияло на хэши выгружаемых валидных
событий; ещё не записанное событие могло остаться в очереди во время снимка
активной сессии. Красные тесты воспроизвели оба случая. Теперь ZIP дополнительно
сверяет исходные файлы снимка по размеру и SHA-256 до/после записи, а онлайн-
сборка сначала ставит барьер в очередь writer. Недоступный/просроченный барьер
даёт `recorder_loss` и частичный пакет. `summary.txt` и manifest используют
один итоговый признак частичности; scope счётчиков от запуска процессов явно
обозначен в manifest и UI. После этих изменений 47 профильных backend-тестов
и 34 проверки локализации/diagnostics прошли. Ранний полный backend-прогон с покрытием завершился успешно, как указано
выше; актуальный полный прогон после исправления тестовых условий также прошёл.

ZIP-сборка теперь выполняется в отдельном Python-процессе с пониженным
приоритетом. Родительский процесс держит снимок и полный резерв места,
проверяет результат и единолично публикует статус и аудит. RED тест сначала
подтвердил сборку в процессе API; после изменения 28 тестов bundle/queue
прошли. Отдельный тест остановки завершает активный дочерний процесс и
проверяет отсутствие опубликованного или частичного ZIP и освобождение
резерва. Дополнительный RED-тест выявил, что ожидающие задания оставляли
резерв места при штатной остановке; shutdown теперь освобождает его, сохраняя
SQL-строки `queued` для recovery после рестарта. Все 11 тестов queue прошли.
Ruff по изменённым файлам чист.

## Ограничения текущего стенда

В обычной песочнице Docker daemon недоступен (`permission denied` к
`npipe:////./pipe/docker_engine`), поэтому локальный Compose smoke выполнен
с разрешённым доступом в Docker Desktop Linux Engine 29.4.2. Уникальные
проекты `okf-diag-smoke-20260928` и `okf-diag-external-smoke-20260928`
не затрагивали действующий `okf-keycloak` и существующие образы `okf-*:local`.
В обоих режимах тестовые PostgreSQL/Qdrant и fake LLM стали healthy,
миграция дошла до `030b1c2d3e4f`, backend и frontend стали healthy и
отдали HTTP 200. Bundled: повторная миграция и `alembic check` прошли без
новых операций. В режиме development/simulation тестовый `demo.admin`
прошёл start→stop→bundle→preview→HTTP download→CRC ZIP→delete в обеих
топологиях. ZIP содержал ожидаемые семь файлов. В external без frontend
пакет честно был `partial=true`; после запуска frontend новый пакет стал
`partial=false`, `gaps=[]`. После штатного restart backend и frontend
новые пакеты в обоих режимах также были `partial=false`, `gaps=[]`.
Без роли admin скачивание вернуло 403 `forbidden`, хотя в dev-режиме
`AUTH_PROVIDER=disabled` управление открыто; production этот режим запрещает.
При остановленных тестовых frontend, backend и PostgreSQL bundled-контейнер
запустил offline CLI с `--no-deps` и создал ZIP размером 3153 байта; CRC всех
семи файлов проверен, manifest указал `collection_mode=offline`,
`audit_reconciliation=pending_sql`, `partial=true`.
Первый `compose stop backend` завершал тестовый контейнер кодом 137 при
`OOMKilled=false`: Python был дочерним процессом `sh`, а Compose не давал
достаточного времени на завершение. Dockerfile теперь запускает `exec python`,
Compose задаёт `stop_grace_period: 30s`; повторный тест подтвердил Python как
PID 1 и код выхода 0. В CI добавлена проверка этого кода после SIGTERM;
фактический CI run ещё не получен.
Это проверка Linux-контейнеров на локальном Windows-хосте, не независимый
Linux staging. Дополнительно на отдельном временном PostgreSQL 17 выполнен
полный Alembic upgrade до предыдущей ревизии `021b1c2d3e4f`, добавлена
синтетическая строка `developments`, затем выполнен upgrade до
`030b1c2d3e4f`. Строка сохранилась, обе диагностические таблицы появились,
`alembic check` сообщил `No new upgrade operations detected`. Временный
контейнер удалён. Отдельный reboot CT 102 затем подтверждён проверками ниже;
reboot самого Proxmox-хоста не проводился.

frontend/Keycloak/Qdrant запущены. `okf-knowledge.service` имеет статус
