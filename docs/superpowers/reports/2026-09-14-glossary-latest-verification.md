# Проверка текущих результатов глоссария

Дата: 14.09.2026. **Полная приёмка не пройдена.**

Этот отчёт заменяет прежние результаты проверки как оценку текущего рабочего
дерева. При ревью код приложения не менялся; добавлены изолированные тесты
воспроизведения и этот отчёт. Пользовательские базы не очищались.

## Что подтверждено исправленным

Все девять сценариев прошлого ревью теперь проходят: пунктуация после SAP-кодов
не отключает распознавание; merge требует выбора разных непустых полей и
сохраняет поисковые права прежнего безопасного имени; seed откатывается целиком;
отключённые правила резервируют покрытие; одинаковые диапазоны с разными
префиксами допускают безопасное объединение.

Штатные проверки также покрывают исходные примеры пользователя, точные формы
разных видов терминов, диапазоны с пользовательскими префиксами, pending source
edit при merge, перенос переводов, чтение позднего совпадения из полного текста
БД и отсутствие вызова LLM при удалении последнего кандидата строгим фильтром.

## Подтверждённые оставшиеся дефекты

### 1. P2: обрезание выдержки создаёт ложное обозначение

`backend/app/services/glossary/matching.py`, `exact_excerpt`, строки 129–133.

В исходном тексте после 296 символов находится `PA3000 wrong.`, а дальше —
`PA30 exact.`. Для запроса `PA30` функция сначала обрезает текст до 300 символов,
получает окончание `PA30` и считает его точным совпадением. Возвращается начало
текста с усечённым чужим кодом вместо участка с настоящим `PA30`.

Это не доказательство допуска источника без точного совпадения: в данном
воспроизведении правильная форма есть дальше. Дефект именно в ложной цитате и
утрате нужного участка при последующем обрезании.

Рекомендация: проверять границы совпадения в полном исходном тексте, выбирать
выдержку вокруг такого span и не разрезать технический идентификатор на границе
snippet. Добавить проверки для 200/300 символов и лимитов контекста.

### 2. P2: сохраняется алиас, уже порождённый правилом того же ИТ

`backend/app/services/glossary/registry.py`, `_rule_identity_conflicts`.

При правиле `IT, 0000–0999` карточка ИТ `0003` принимает явный алиас `IT0003`.
Проверка пропускает собственного владельца, но не различает допустимое имя
карточки и избыточный новый алиас. Это нарушает пункт плана `redundant_alias`.

Рекомендация: до записи выявлять повтор вычисленной формы внутри карточки,
возвращать `422 glossary_redundant_alias`, не создавать строку и не предлагать
объединение карточки с самой собой. Повторить проверку в create/add/update/merge.

### 3. P2: недоступна предусмотренная смена вида карточки на ИТ

`backend/app/models/glossary.py`, `GlossarySourcePatch`, строка 52;
`backend/app/api/glossary.py`, `update_glossary_source`.

Для существующей транзакции `IT0003` PATCH с `kind=sap_infotype` и
`infotype_number=0003` возвращает 422. Поле kind отсутствует в модели и не
передаётся сервису. Поэтому предусмотренный планом способ разрешить конфликт
нового правила с прежней классификацией карточки не работает.

Рекомендация: добавить явную смену вида в API/редактор с совместной проверкой
нового вида, номера, имён и всех алиасов внутри одной транзакции.

### 4. P2: незавершённая подготовка глоссария неправильно обрабатывается API

`backend/app/api/glossary.py`, `_raise_mutation_error` / `_raise_translation_error`.

При `identities_ready=false` общий слой записи выбрасывает
`GlossaryMigrationRequiredError`. Обработчик мутаций трактует его как ошибку
значения 422, а обработчик переводов пробрасывает исключение без преобразования
в предусмотренный `503 glossary_migration_required`. Штатный тест обнаруживает
422 вместо 503; журнал также фиксирует необработанное исключение PATCH перевода.

Рекомендация: единое преобразование этого исключения в 503 для всех операций.
Проверить также сохранение нулевых изменений БД/аудита/revision после отказа.

### 5. P2: offline audit пропускает конфликты правил и номеров

`backend/app/services/glossary/identity.py`, `identity_keys_for_term`, строки 11–29;
`backend/scripts/audit_glossary_identities.py`.

Два воспроизведения возвращают пустой список конфликтов:

- ИТ `0003` и другая карточка с именем `IT0003` при действующем правиле IT;
- два разных ИТ с номером `0003`, если передано правило только диапазона 1000–1999.

Причины: вычисленные формы не участвуют в сравнении literal-ключей; структурный
ключ номера ошибочно зависит от покрытия правилами. CLI без `--rules-file`
дополнительно не загружает правила из БД.

Рекомендация: использовать тот же контроль пересечений, что при записи; номер
резервировать независимо от диапазонов и enabled. Перед readiness повторять
полную проверку. Поскольку продуктивных данных нет и тестовые глоссарии можно
очистить, это не повод возвращать сложное согласование production-миграции.

### 6. P2: две ошибки версионирования карточки

`backend/app/services/glossary/registry.py`, `update`, строки 749–766.

- Изменение только номера `0003 → 0004` повышает source_revision с 1 до 2,
  хотя исходные имя, описание и язык прежние. Переводы становятся устаревшими
  без изменения переводимого текста; merge для тех же полей использует иной критерий.
- Запрос со старой версией принимается, если присланные значения уже совпадают
  с текущими: ранний return расположен до проверки версии.

Рекомендация: проверять ожидаемую версию сразу после чтения под lock;
source_revision менять только при изменении исходного имени/описания/языка,
а обычную version и glossary revision — по соответствующей мутации.

## Дополнительные UI-пробелы по чтению кода

Эти выводы подтверждены кодом, но не отдельным браузерным прогоном:

- `GlossaryPanel.jsx:138`: отмена merge при создании всегда очищает firstAlias,
  включая конфликт исходного имени. Сохранять происхождение конфликта и очищать
  только совпавший алиас; остальные введённые значения сохранять.
- `GlossaryEditor.jsx:83–84`: обычное сохранение передаёт enabled, но sourceEdit
  для конфликтного merge его теряет. Нужен явный контракт итогового состояния,
  иначе одновременное отключение и изменение имени не переносится в preview.
- Ручной выбор второй карточки для merge ограничен текущей страницей списка.
  Добавить поиск по всем карточкам независимо от пагинации.

## Порядок завершения и переиндексация

1. Исправить обрезание обозначений и запрет избыточных вычисленных алиасов.
2. Завершить классификацию, API-ошибки, версионирование и адресный отказ UI.
3. Согласовать audit с рабочим контролем пересечений, не усложняя перенос пустых тестовых данных.
4. Повторить API/UI цепочки создание/редактирование → конфликт → отказ/merge → readback → поиск;
   PostgreSQL concurrency, полный backend и production build.
5. На одном тестовом корпусе подтвердить неизменность векторов/payload после
   правок терминов, алиасов и правил; измерить задержку с чтением полного текста.

Архитектура остаётся query-time: правила ИТ и явные алиасы транзакций меняют
набор разрешённых форм при запросе. **Изменения глоссария не требуют
переиндексации документов.** Новые описанные исправления этого не меняют.
Сравнение контрольных векторов/payload и запрет всех записей через spy остаются
отдельной непроведённой приёмочной проверкой, а не доказанным результатом этого ревью.
