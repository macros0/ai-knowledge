## Исторические подтверждённые замечания до исправления

### 1. P1 — объединение теряет данные исходной карточки

`backend/app/services/glossary/registry.py`, метод `merge`:
алиасу присваивается `term_id=target.id`, затем вызывается `session.delete(source)`.
В загруженной ORM-коллекции source алиас остаётся, и `cascade="all, delete-orphan"`
удаляет его вместе с source. Сценарий с единственным алиасом `SOURCE_ONLY`
возвращает HTTP 200, но итоговая карточка этого алиаса не содержит.
**Воспроизведено на SQLite и PostgreSQL**. Для переводов код использует такой же
способ переноса; их сохранность нужно проверить отдельным регрессионным тестом.

При выборе исходного имени source как итогового старое имя target также теряется:
`build_merge_result` сохраняет только имя source в роли дополнительного алиаса.
На PostgreSQL подтверждены HTTP 200 и отсутствие прежнего имени target.

Рекомендация: сначала сформировать полный итоговый набор данных, перенести
ORM-отношения, проверить сохранность алиасов/переводов и только после этого
удалять source. Проверять итог **после повторного чтения из БД**, а не только
чистую функцию предпросмотра. Явно разрешать конфликты локалей и флагов.

### 2. P1 — формы из правил ИТ не участвуют в общем контроле пересечений

`registry.py:_identity_values` резервирует буквальное имя, явные алиасы и
отдельный ключ `infotype:<номер>`. Он не связывает с этим ключом буквальные формы,
созданные правилом. `rule_registry.py` проверяет пересечения правил между собой,
но не новые формы против имён/алиасов карточек.

Сценарий: правило `0–999`, префикс `IT`; ИТ `0003` с именем `Payroll status`;
затем транзакция с именем `IT0003`. Получено **201 вместо 409** на обеих СУБД.
Это прямое нарушение общего пространства имён из пользовательского пункта 4.

Рекомендация: один механизм разрешения форм и проверки владельца для имени,
явного алиаса и формы из правила. Проверять оба направления: изменение карточки
при существующем правиле и изменение правила при существующих карточках;
проверку выполнять под общей блокировкой записи глоссария.

### 3. P1 — API не проверяет подтверждённый предпросмотр объединения

`backend/app/api/glossary.py:merge_glossary_terms` заново вычисляет digest из
текущих карточек. `GlossaryMergeRequest` не содержит обязательных
`preview_digest` / `expected_revision`; версии source/target необязательны.

Сценарий: предпросмотр, изменение описания source, commit со старым digest и
revision без необязательных версий. Получено **200 вместо 409** на обеих СУБД.
Таким образом API объединяет данные, которых пользователь в предпросмотре не видел.

`GlossaryMergeDialog.jsx` дополнительно не показывает `proposal.merged` и не
сбрасывает proposal при изменении selections.

Рекомендация: отдельные контракты preview/commit; обязательные версии и digest
показанного результата, проверяемые внутри той же транзакции, что и merge;
сбрасывать preview при изменении выбора и показывать итоговые данные.

### 4. P2 — повтор HTTP-запроса объединения не идемпотентен

Тот же `request_id` после успешного merge возвращает **404 вместо прежнего 200**
на обеих СУБД: API читает уже удалённый source до обращения к receipt.
Сервисный unit-тест идемпотентности не проходит через этот код API.
UI генерирует новый UUID при каждом вызове, в том числе при повторе commit.

Рекомендация: искать receipt до чтения source, проверять actor и полный hash
запроса, возвращать сохранённый результат; хранить один request_id на попытку
подтверждённого объединения, включая сетевые повторы.

### 5. P1 — другой процесс может продолжать искать по устаревшим терминам

`expansion.py:_load_query_snapshot` сначала читает старый локальный кэш registry,
затем загружает снимок с актуальной revision и **заменяет его terms старым кэшем**.

Сценарий: прогреть snapshot; отдельным Python-процессом переименовать термин;
в исходном процессе загрузить следующий query snapshot. Revision-loader видит
`Cached new name`, но expansion получает `Cached old name`.
Воспроизведено на файловой SQLite двумя процессами.

Рекомендация: expansion должен целиком использовать один снимок из
`load_glossary_snapshot`, без подмены terms вторым кэшем. Дополнительно исправить
повторное чтение revision в snapshot: повторный `session.get` может вернуть
объект из identity map без SQL. Добавить тесты двух процессов/соединений на
согласованность names, aliases, rules и revision.

### 6. P1 — автоматическое предложение объединения и отказ не подключены к UI

Статическая проверка `GlossaryEditor.jsx` / `GlossaryPanel.jsx`:
при ошибке сохранения показывается toast; `shouldOfferMerge` и
`resolveRejectedAlias` из `glossaryConflicts.mjs` не используются редактором.
Кнопка ручного объединения с выбранной карточкой не реализует сценарий
«ввёл совпадающий алиас → предложение → согласие/отказ».

Рекомендация: подключить структурированный 409 к диалогу, сохранить остальные
черновики; при отказе очищать только новый конфликтующий алиас или восстанавливать
сохранённую строку. Проверить браузером полный путь через кнопки интерфейса,
включая поиск карточки, которой нет на текущей странице списка.

### 7. P2 — SQLite оставляет ключи удалённого source

В `_on_sqlite_connect` не включён `PRAGMA foreign_keys=ON`. Для
`glossary_identity_keys` рассчитывают на FK `ON DELETE CASCADE` без явного
удаления ключей source. Выбор source-name при merge возвращает на SQLite
**500 / UNIQUE constraint failed**, тогда как на PostgreSQL тот же сценарий
возвращает 200. Ошибка подтверждена исполняемым сценарием.

Рекомендация: согласовать удаление ключей с общей транзакцией merge и добавить
проверку отсутствия orphan-ключей. Изменение глобального режима SQLite FK требует
отдельного полного прогона — оно затронет другие модули приложения.

### 8. P2 — общие контракты аудита и кодов ошибок не синхронизированы

Полный backend-прогон выявил три сбоя:

- `tests/test_audit.py::TestAuditService::test_action_types_enum_frozen`:
  ожидаемый перечень не содержит `glossary_term_merge`, `glossary_rule_create`,
  `glossary_rule_update`, `glossary_rule_delete`. Это требует обновления контракта
  теста для уже введённых событий с проверкой их фактической записи.
- `tests/test_error_codes.py::TestCodeCoverage::test_no_code_is_declared_but_never_raised`:
  `GLOSSARY_INVALID_RULE` объявлен, но нигде не выдаётся. Нужно использовать его
  для ошибок валидации правил вместо кода невалидного алиаса либо убрать
  неиспользуемый контракт.
- `tests/test_error_codes.py::TestCodeTranslations::test_every_code_has_a_dictionary_key`:
  нет frontend-ключей для `glossary_identity_conflict`, `glossary_rule_overlap`,
  `glossary_rule_not_found`, `glossary_invalid_rule`.

Все три сбоя связаны с новыми glossary-контрактами. Они не относятся к известному
порядкозависимому тесту `_inflight`, который в этом прогоне не упал.
