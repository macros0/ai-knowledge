# Повторная проверка текущей реализации глоссария

Дата: 14.09.2026. Статус: **приёмка не пройдена**.

Проверено текущее рабочее дерево после исправлений предыдущего ревью. Код
приложения в ходе этой проверки не изменялся. Добавлены только изолированные
проверочные сценарии и документы проверки. Пользовательские базы не очищались.
Этот отчёт описывает новый прогон; цифры предыдущих отчётов являются историческими.

`test_non_infotype_codes_only_trigger_through_explicit_aliases` не ожидает исходное
имя в разрешённых поисковых формах. Новый план предусматривает безопасное точное
имя. Это рассогласование теста с новым контрактом, а не шесть доказанных регрессий.

На frontend один тест проверяет прежнюю строковую форму вызова

Новые девять падений ниже — шесть групп воспроизведённых проблем, включая четыре
параметризации пунктуации. Все используют временную SQLite на каждый тест.
Сценарии: `backend/.tmp-glossary-review/test_recheck_contracts.py`.
Логи: `recheck-backend.log`, `recheck-frontend.log`, `recheck-contracts.log` в той
же папке. Команда для независимых сценариев из backend:

```powershell
$env:TEMP = Join-Path (Get-Location) '.tmp-glossary-review'
$env:TMP = $env:TEMP
.\.venv\Scripts\python.exe -m pytest .tmp-glossary-review/test_recheck_contracts.py -q -p no:cacheprovider --basetemp=.tmp-glossary-review/recheck-contracts-next --tb=short
```

Полный backend, production build и браузерный E2E в этом ревью не выполнялись.

успешный SQLite-прогон не подтверждает межпроцессные гонки PostgreSQL.

## Подтверждённые проблемы и рекомендации

### P1. Пунктуация отключает точное распознавание SAP-термина

`backend/app/services/glossary/normalization.py:109–127`.

`PA30` и `IT0003` распознаются, но `PA30.`, `PA30:`, `IT0003.` и `IT0003:` дают
`no_match` и пустые `strict_groups`. Причина: точка и двоеточие всегда считаются
продолжением идентификатора, включая конец предложения. Потеря распознавания
также выключает строгий фильтр для такого запроса.

Рекомендация: различать внутренний разделитель идентификатора (`PA30.OLD`) и
знак пунктуации после законченного обозначения. Использовать одну проверку
границ для запроса и текста источника. Сохранить отрицательные проверки
`XIT0003Y`, `IT00037`, `/ABC/IT0003`, `PA30-OLD` и `PA30.OLD`.

### P1. API merge допускает потерю непустого описания без выбора

`backend/app/services/glossary/merge.py:65–68`.

У source и target разные непустые описания. Запрос выбирает только итоговое имя.
Preview и commit проходят; source удаляется, его описание не переносится.
UI требует больше выборов, но backend этого не гарантирует.

Рекомендация: вычислять `unresolved_fields` на сервере, запрещать commit при
неразрешённых различиях и проверять выбор повторно внутри транзакции. Совпадающие
значения и единственный непустой вариант можно разрешать автоматически.

### P1. Перенесённое имя перестаёт работать после merge

`backend/app/services/glossary/merge.py:89–93`.

До объединения имя `PA30` распознаётся. После объединения с карточкой
`Maintain personnel` оно сохраняется как alias с `auto_expand=False` и
`search_enabled=False`; следующий запрос `PA30` возвращает `no_match`.

Рекомендация: сохранять разрешённую поисковую семантику безопасного старого имени
или показывать явный выбор этих прав. Сейчас автоматически создаваемые алиасы
старых имён отсутствуют в редакторе флагов merge-диалога.

### P2. Seed применяется частично при конфликте с существующим алиасом

`backend/app/services/glossary/seed.py:98–124`.

В БД есть алиас `Reserved form`. В пакете первая новая карточка корректна,
вторая имеет имя `Reserved form`. Вторая операция отклоняется, но первая остаётся
в БД. Предварительная проверка только canonical/исходных полей не заменяет общей
транзакции всех записей.

Рекомендация: весь apply выполнять под одним state-lock и в одной транзакции,
включая проверки существующих имён, алиасов, номеров и правил. Ошибка любой строки
должна откатывать весь пакет. Исторический чекбокс атомарного seed не подтверждён.

### P2. Отключённое правило не резервирует своё покрытие

`backend/app/services/glossary/rule_registry.py:261`.

После сохранения отключённого правила `IT, 0000–0999` успешно создаётся второе
правило с теми же диапазоном и префиксом. `_find_conflicts` проверяет только
enabled-правила. Между тем check показывает такие пересечения, а план требует
учитывать и отключённые правила.

Рекомендация: один общий критерий конфликтов для check/create/update/merge,
независимый от enabled. Отключение влияет только на участие в поиске.

### P2. Безопасное объединение правил с разными префиксами запрещено

`backend/app/services/glossary/rule_registry.py:280–291`.

Правила `IT, 0000–0999` и `ИТ, 0000–0999` не объединяются: preview возвращает
конфликт из-за разных списков префиксов, хотя итог сохраняет то же множество форм.

Рекомендация: поддержать одинаковый диапазон с объединением префиксов и
пересекающиеся диапазоны с одинаковыми префиксами. Проверку digest и повторное
построение результата выполнять под одним lock: сейчас rule merge проверяет
preview до входа в транзакцию записи. Гонка здесь установлена по коду, отдельно
не воспроизводилась.

## Дополнительные пробелы UI, установленные чтением кода

- `GlossaryEditor.jsx:55–61,90–109,173`: конфликтное редактирование алиаса хранится
  в локальном draft, а в merge передаётся `source={term}`, то есть сохранённая
  карточка. Изменённые флаги/язык/текст не входят в план объединения. При конфликте
  исходных полей действует тот же разрыв. Передавать ожидаемое изменение вместе
  с версией source; отобразить его в preview.
- Редактор существующей карточки выбирает первого конфликтующего владельца.
  Нужен полный список с явным выбором пользователя, как уже начато в create-flow.
- `GlossaryMergeDialog.jsx`: повторяющийся alias с разными flags/locale требует
  выбора на backend, но UI молча отображает первое значение и отправляет
  `alias_choices` только после изменения поля. Нужен явный неразрешённый выбор.
- В API отсутствуют маршруты объединения правил; UI правил содержит CRUD без
  согласованного merge-сценария. Одного сервисного метода недостаточно для приёмки.
- Синхронизировать EN-словарь и сгенерированные manifests командой
  `node scripts/export-ui-keys.mjs` из frontend.

Эти UI-сценарии не выдаются за подтверждённый браузерный прогон.

## Что уже подтверждено новым штатным прогоном

Прошли тесты исходных примеров ИТ, полных явных форм в strict filter при нулевом
бюджете, объединения явных и rule-форм, отключённых карточек и дедупликации
виртуальных ИТ. Прошли новые merge acceptance-тесты запрета разных номеров,
проверки replay, свежести переводов и ревизии между workers (модель в SQLite).
API create/edit номера и merge несохранённого черновика также прошли.

## Рекомендуемый порядок завершения

1. Исправить распознавание пунктуации, обязательный выбор полей merge и сохранение
   поисковых прав прежних имён; включить воспроизведения в основной suite.
2. Завершить правила и атомарный seed; затем передавать pending draft в merge UI,
   закрыть выбор владельцев и противоречащих алиасов.
3. Обновить старые ожидания тестов под согласованное точное имя, локализацию и
   manifests; повторить связанные suites.
4. Выполнить PostgreSQL concurrency и браузерный сценарий
   create/edit → конфликт → отказ/merge → readback → поиск. После этого полный
   backend, build и проверка точности/задержки на тестовом корпусе.

Изменения глоссария остаются query-time: исправления этих дефектов не требуют
переиндексации документов. В этой проверке Qdrant не переиндексировался; свежая
контрольная проверка неизменности всех векторов/payload не проводилась.

План полностью не выполнен. Требуются исправления и повторная приёмка, а не
только косметическое обновление старых зелёных отчётов.
