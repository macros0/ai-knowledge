# Эталон поиска IT3330 и IT3273 — 14.09.2026

## Что требуется от измерительной базы

Измерительная база уже пригодна для проверки этих сценариев: пользователь
ввёл правила инфотипов и проверил IT3330 и IT3273 с глоссарием и без него.
Дополнительное наполнение или повторное ручное согласование этих двух
запросов для начала работы не требуется.

От базы нужны воспроизводимые документы, правила и условия поиска. Эталон
содержит минимальные ожидаемые источники; текущая выдача с известными
потерями хранится отдельно как исходный замер. Порядок и точное количество
всех результатов не являются эталоном: дополнительные релевантные концепты
разрешены, обязательные концепты должны сохраняться.

## Зафиксированные ожидания

Ожидания сохранены в
[`infotype-reference-cases.json`](../../../backend/test_scripts/infotype-reference-cases.json).
Это объединение источников последних сохранённых пользовательских поисков
с включённым и выключенным глоссарием, а не автоматически одобренная новая
выдача. Основание — просьба пользователя использовать эти проверки как эталон.
Исторические даты и состав обеих выдач сохранены в `historical_evidence`.

- **IT3273: минимум 2 концепта.** «Есть все данные для заполнения ИТ 3330 и
  3273» из разработки 3409 и «По периоду анализа осуществляется выбор записей
  инфо-типа 3273 по дате заведения инфо-типа, поле „Действие С“» из ФС 0706.
- **IT3330: минимум 5 концептов.** Два концепта «Есть все данные для заполнения
  ИТ 3330 и 3273» из разных документов; «Доработка выбора отсутствий при
  проведении мероприятия UU»; «Период с нарушением периода в ИТ 3330»;
  «Отсутствует первичный ЭЛН в ИТ 3330».

Идентичность источника определяется по `(doc_id, slug, chunk_index)`.
Одинаковые заголовки из разных документов не объединяются. Заголовки и
типы точек также сохранены в результатах прогона.

Ожидания сформулированы для глоссария **on**. Режим **off** служит сравнением,
его неполнота относительно объединённого набора сама по себе не является
ошибкой приёмки. Эти два запроса не доказывают качество на всём корпусе.

## Условия измерения

- Профиль: «Измерительная база Stage 8»; PostgreSQL `okf_stage8_test`;
  Qdrant `okf_knowledge_stage8_test`.
- 9 документов, 761 концепт, 66 чанков, 827 точек Qdrant.
- 2 запроса × 2 режима (BM25/hybrid) × 2 пути (search/chat retrieval) ×
  глоссарий off/on = **16 сценариев**.
- По 2 прогрева и **100 измерений** на сценарий: 1600 измерений, без учёта
  прогревов. Порядок сценариев перемешивается в каждом круге, seed 32733330.
- `top_k=50`, `search_per_branch_top_k=40`, без фильтров по тегам и языку.
  Широкий top_k выбран для диагностики потерь; это не обещание того же
  состава в короткой UI-выдаче с другим лимитом.
- В hybrid каждый раз вызывается штатный Embedder. Дополнительного кэша
  эмбеддингов в benchmark нет. Время включает подготовку запроса, эмбеддинг,
  Qdrant, загрузку текстов, объединение и фильтры соответствующего пути.
- Не включены HTTP/auth, генерация ответа LLM и отрисовка браузера.
- p95 — ближайший ранг: элемент `ceil(0.95*n)-1` отсортированной выборки.
- Фиксируются снимок правил и revision глоссария, контрольные суммы Python-кода
  backend/app, текстов/идентификаторов концептов и чанков, список документов,
  параметры весов и лимитов. Git HEAD указан, но рабочая папка содержит
  незакоммиченные изменения: для воспроизводимости важны именно контрольные суммы.

## Результаты

Время приведено в миллисекундах, **p50 / p95**.

| Запрос | Режим | Путь | Глоссарий off | Глоссарий on |
|---|---|---|---:|---:|
| IT3330 | BM25 | search | 4.04 / 5.29 | 17.81 / 23.38 |
| IT3330 | BM25 | chat retrieval | 4.36 / 5.83 | 19.20 / 25.69 |
| IT3330 | hybrid | search | 47.90 / 60.56 | 62.61 / 78.60 |
| IT3330 | hybrid | chat retrieval | 48.03 / 60.18 | 64.90 / 80.55 |
| IT3273 | BM25 | search | 3.89 / 5.18 | 20.07 / 25.40 |
| IT3273 | BM25 | chat retrieval | 3.96 / 5.35 | 20.39 / 27.92 |
| IT3273 | hybrid | search | 47.03 / 58.45 | 55.53 / 65.12 |
| IT3273 | hybrid | chat retrieval | 48.45 / 60.60 | 55.49 / 72.46 |

Для каждого сценария порядок, идентичность и заголовки финальных источников
были стабильны во всех 100 повторах. Контрольная сумма проверяемых данных БД,
число точек Qdrant и снимок глоссария до/после совпали. Векторы Qdrant целиком
не хэшировались; совпадение количества точек не доказывает неизменность всех
векторов. Скрипт выполняет чтение и не запускает переиндексацию.

| Ожидание | Chat off | Chat on | Статус on |
|---|---:|---:|---|
| IT3330 — 5 обязательных концептов | 2/5 | 4/5 | не выполнено |
| IT3273 — 2 обязательных концепта | 1/2 | 1/2 | не выполнено |

Эти результаты одинаковы для BM25 и hybrid. В обоих запросах отсутствующий
обязательный концепт есть в raw-кандидатах, но отсутствует после точной
фильтрации. IT3330 теряет «Доработка выбора отсутствий при проведении
мероприятия UU»; IT3273 теряет «Есть все данные для заполнения ИТ 3330 и 3273»
из разработки 3409. Это исходные известные потери, которые нельзя закреплять
как правильное поведение.

Для IT3273 дополнительно действует фильтр заголовков: после merge доступны
12 блоков в BM25 и 10 в hybrid, а в контексте чата остаётся 1. Для IT3330
поиск отдаёт 8 блоков, чат — 4. Проверять нужно оба пути, а не только текст
ответа модели или одну карточку в интерфейсе.

Абсолютный предел задержки пока не согласован. Эти цифры — измеренный
baseline, а не автоматически принятый SLA. Старый порог «+20%» не применяется.

## Артефакты и повторный запуск

Полные артефакты находятся в
[`tests/artifacts/stage8/infotype-reference-20260914`](../../../tests/artifacts/stage8/infotype-reference-20260914):
`reference.json`, `manifest.json`, `retrieval.json`, `samples.json`, `summary.json`.
Каталог локальных артефактов исключён из Git; файл ожиданий и скрипт находятся
в `backend/test_scripts`, чтобы их можно было сохранять вместе с кодом.

Запуск из корня репозитория, при доступном измерительном контуре:

```powershell
. ./tests/scripts/stage8/stage8-test-profile.ps1
$referenceProfile = Get-Stage8TestProfile
foreach ($entry in $referenceProfile.Environment.GetEnumerator()) {
    [Environment]::SetEnvironmentVariable($entry.Key, [string]$entry.Value, 'Process')
}
$referenceOutput = 'tests/artifacts/stage8/infotype-reference-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
& backend/.venv/Scripts/python.exe backend/test_scripts/benchmark_infotype_reference.py `
    --reference backend/test_scripts/infotype-reference-cases.json `
    --output $referenceOutput --samples 100
```

`--capture-reference` использован только при первичном снятии ожиданий.
Для следующих проверок его не добавлять: новый поиск не должен перезаписывать
эталон. Новый каталог результатов обязателен, существующие результаты не
перезаписываются.

После исправлений сравнивать наличие всех обязательных источников,
`missing_at_stage`, конечный состав и p95 с этим замером. Изменение правил,
документов или параметров записывать как изменение условий, а не приписывать
его эффект только исправлению кода. Работа с потерями остаётся отдельным
исправлением; в этом прогоне код поиска и правила глоссария не изменялись.
