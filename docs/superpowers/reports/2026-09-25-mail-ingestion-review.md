# Ревью импорта Outlook-писем

Дата: 2026-09-25. Проверялось текущее незакоммиченное состояние рабочей копии,
включая новые файлы, а не только tracked diff. Реализация не изменялась.
Синтетические воспроизведения находятся в игнорируемом `tests/tmp/`.
Приватное письмо пользователя в этом ревью не использовалось.

Вывод: найденные R1–R9 исправлены в текущей рабочей копии и закреплены
регрессионными тестами. Общая видимость писем принята пользователем: отдельный
ACL не является требованием релиза. До включения импорта остаются внешние
release gate: Linux RLIMIT_AS и сквозная приёмка с доступными LLM/Qdrant.

## Повторная проверка после исправлений

- `doc-parser`: 106 passed, 1 Windows-only skipped. Включая EML body boundary,
  вложения в MIME containers, embedded MSG dict attachments, plain MSG с
  угловыми скобками, RTF fixture и Unicode CJK guard.
- Backend mail/source/export: 137 passed, 1 POSIX-only skipped. Включая
  безопасную публикацию attempt directory, resume с полной проверкой
  checkpoint, 102 чанка и DB-backed OKF export с `sources.json`/`source_id`.
- Frontend: 37 passed.
- Присланный пользователем приватный Unicode MSG повторно разобран через
  supervised worker: 3 source nodes, 2 вложения, предупреждений и U+FFFD нет.
  Обезличенный отчёт остаётся вне Git в `tests/tmp/mail/`.

## Подтверждённые замечания

### R1 — P1: при выборе тела EML нарушается граница вложенного письма

Код: `doc-parser/src/docparser/eml_parser.py:171–176`, аналогичный обход HTML
на строках 183–188.

У родителя HTML-тело `PARENT HTML BODY`, у вложенного `message/rfc822` —
plain-text `CHILD BODY`. `message.walk()` проходит внутрь вложенного письма,
и его внутренний text/plain не имеет disposition=attachment. Парсер выбирает
его вместо HTML родителя. В результате `CHILD BODY` появляется одновременно
под `root` и `root/0`; текст родителя исчезает. Предупреждений нет.

Рекомендация: выбирать тело только в MIME-дереве текущего сообщения,
не заходя в поддеревья attachment/message/rfc822. Отдельно обходить вложения.
Регрессионный тест должен проверять сохранность обоих тел и правильный
source_id каждого, включая обратную комбинацию plain/HTML.

### R2 — P1: у embedded MSG пропадают собственные вложения

Код: `doc-parser/src/docparser/msg_parser.py:82–100`.

Зависимость `msg_parser.Message._get_attachments()` возвращает словарь,
включая поле `EmbeddedMessage['attachments']`. Корневой `parse_msg()`
преобразует его в список значений; рекурсивная `_parse_message_data()` этого
не делает. Цикл получает строковые ключи и пропускает их через `continue`.

Воспроизведена структура MSG → embedded MSG → proof.eml с формой данных
установленной зависимости. Существует только `root` и `root/0`: разрешённое
вложение `root/0/0` не имеет ни текста, ни узла, ни маркера, ни предупреждения.

Рекомендация: нормализовать коллекцию вложений на каждой глубине. Добавить
регрессионный тест на dict-структуру зависимости и реальный бинарный MSG
с вложением во вложенном сообщении.

### R3 — P1: MIME-контейнер скрывает вложения без предупреждения

Код: `doc-parser/src/docparser/eml_parser.py:63–66`.

Для `multipart/signed → multipart/mixed → text/plain + decision.eml`
верхний `iter_attachments()` возвращает multipart-часть; её decoded payload
равен None, и поддерево пропускается. В проверке остаются тело и файл подписи,
а decision.eml и его текст APPROVED отсутствуют. Предупреждений нет.
Проблема относится к структурному обходу MIME; проверка достоверности подписи
для её исправления не требуется.

Рекомендация: рекурсивно обходить MIME-контейнеры с явными правилами для
alternative, related, signed и message/rfc822. Добавить тесты на сохранность
каждого ожидаемого вложения и диагностику намеренно пропущенных частей.

### R4 — P1: обычный resume смешивает старые концепты с новым источником

Код: `backend/app/services/pipeline.py:491–504`, `520–521`, `533–535`.

Проверки версии парсера, SHA-256 и раскладки чанков выполняются только при
`staging.partial_chunks`. У обычной паузы после успешно обработанных чанков
(например, перед следующим LLM-вызовом или на индексации) этот список пуст.
Затем raw-текст и source_id переписываются, а уже готовые концепты пропускаются.

Воспроизведение: staging содержит old-parser, другой SHA-256 и OLD CONTENT;
текущий EML содержит New text. `_process(..., resume=True)` не отказывает,
переписывает chunk_00.md новым текстом и сохраняет OLD CONTENT без генерации.
Это особенно существенно при обновлении с прежней сквозной разбивки на
разбивку по источникам.

Рекомендация: до записи чанков и публикации артефактов проверять совместимость
всех повторно используемых checkpoints. Для legacy checkpoints без версии
проверять фактический текст и границы либо требовать регенерацию, когда доказать
совместимость нельзя. Тестировать обычную паузу, salvage и сбой индексации.

### R5 — P1: ошибка повторного разбора удаляет ранее сохранённые вложения

Код: `backend/app/services/parser_supervisor.py:280–282`; вызывающая сторона —
`backend/app/services/pipeline.py:408–418`.

Supervisor считает attachments_dir каталогом одной попытки и удаляет его
целиком при ошибке. Pipeline передаёт постоянный `uploads/<doc_id>/attachments`,
который при resume/regenerate уже содержит файлы предыдущего прохода.

Проверка с заранее сохранённым previous-success.bin и ошибкой worker
подтвердила удаление старого файла. Аналогичный cleanup используется при timeout
и превышении памяти. Строки БД при этом могут продолжать ссылаться на файл.

Рекомендация: разбирать в отдельный каталог попытки, валидировать результат,
публиковать его контролируемой заменой с сохранением старого набора до успешного
перехода. При отказе удалять только временные файлы текущей попытки. Тестировать
ошибку/timeout после успешной обработки и проверять доступность старых downloads.

### R6 — P2: после 100 чанков концепты получают чужой source_id

Код: `backend/app/services/pipeline.py:779–780`; построение списка — строка 705.

Файлы chunk_XX.md сортируются лексикографически: chunk_100 идёт раньше
chunk_11. Привязка `chunk_rows[ci]` ошибочно считает позицию списка равной
числовому chunk_index. На 102 чанках с чередующимися root/root/0 подтверждены
два расхождения; концепт чанка 11 получил root вместо root/0.

Рекомендация: сортировать по числовому индексу и получать строку по словарю
`chunk_index → row`. Проверить также соответствие индексов chunk-векторов БД.
Регрессионный тест: 102+ чанка с разными источниками, сверка concept/chunk/Qdrant.

### R7 — P2: обычный текст MSG ошибочно интерпретируется как HTML

Код: `doc-parser/src/docparser/msg_parser.py:73–79`.

Условие «содержит < и >» не определяет формат тела. В копии публичного валидного
CFB/MAPI fixture Unicode Body заменён на `Contact <alice@example.test> for approval.`.
Публичный parse_document_result вернул `Contact for approval.` без предупреждения.
Аналогично могут потеряться placeholders и XML-фрагменты.

Рекомендация: сохранять происхождение выбранного Body/Html/RTF-представления и
вызывать HTML-нормализатор только для HTML. Добавить тест на адрес, placeholder,
XML и отдельный настоящий HTML body.

### R8 — P2: исправление mojibake портит корректный Unicode MSG

Код: `doc-parser/src/docparser/msg_parser.py:215–226`; вызовы — строки 73 и 193.

Эвристика «больше 30% CJK + печатаемый CP1252» применяется к любому тексту,
включая тему. В валидном публичном MSG fixture заменён UTF-16 Subject stream
без изменения размера. Правильная тема с 中文测试 преобразовалась в
`-N‡eKmÕ‹...`; предупреждений нет. Проверка прошла через публичный parser,
а не только прямой вызов helper.

Рекомендация: исправлять декодирование только конкретного ANSI/RTF пути по
типу MAPI property и кодировке. Unicode-поля не переинтерпретировать эвристически.
Добавить настоящие CJK и смешанные Unicode темы/тела рядом с ANSI RTF fixture.

### R9 — P2: штатный OKF-экспорт не сохраняет новые связи источников

Код: `backend/app/services/export_okf.py:26–146`; частичная новая реализация —
`backend/app/services/okf_generator.py:313–314`.

`sources.json` добавлен в save_bundle, но штатный API export-okf использует
export_okf_bundle из БД и вызывает build_okf_docs. Он не читает DocumentSource,
не экспортирует source_id чанков/концептов и не создаёт sources.json.
В проверке БД содержала root/root/0 и связанные чанк/концепт; в экспорте
не было ни sources.json, ни source_id. Предыдущая приёмка проверяла только
альтернативный режим okf_write_bundles=True.

Рекомендация: использовать общий контракт экспорта дерева и связей для обоих
путей. Проверить ZIP именно через API и согласованность manifest/файлов/ссылок;
отдельно проверить переносимость путей Windows/Linux.

## Проверки и границы результата

- Полный doc-parser suite: **101 passed, 1 skipped** (Windows symlink).
- Backend: mail pipeline, source store/API/chunking, parser-version, supervisor,
  upload similarity: **38 passed, 1 skipped** (POSIX).
- Frontend: sourceTree, uploadFailures, uploadReview, i18n: **37 passed**.
- Четыре backend-воспроизведения подтвердили ошибочное поведение R4/R5/R6/R9.
  Они намеренно утверждают наличие дефекта: их успешный результат не является
  доказательством корректности реализации.
- Parser probe подтвердил R1/R2/R3/R7/R8. Для R7/R8 использована изменённая
  временная копия публичного MSG; исходный fixture не менялся.
- Runtime LLM/Qdrant, Linux RLIMIT_AS, миграции на production PostgreSQL и
  браузерная приёмка в этом ревью не выполнялись. pip-audit заново не запускался.

## Порядок дальнейшей работы

1. Исправить R1–R5 и добавить тесты с ожидаемым корректным результатом.
2. Закрыть R6–R9; сохранить один контракт source_id для БД, Qdrant и экспорта.
3. Повторить соответствующие suites и проверить реальные комбинации HTML/plain,
   MSG → MSG → документ, документ → письмо → вложение, повторную обработку после
   сбоя, 100+ чанков и штатный ZIP-экспорт.
4. Выполнить чистый Linux-прогон и сквозную приёмку загрузка → поиск → источник →
   скачивание с доступным LLM/Qdrant. Это остаётся отдельной необходимой проверкой.
5. Для IRM/зашифрованных/неподдержанных вариантов показывать явный статус и
   сохранённый оригинал; отсутствие возможности разобрать вложение не должно
   выглядеть как полная успешная обработка.

До исправлений и приёмки сохранять MAIL_IMPORT_ENABLED=false. Этот флаг
ограничивает standalone-письма; новый разбор вложенных писем в DOCX/XLSX/PDF
сам по себе им не отключается, что нужно учитывать при развёртывании.
