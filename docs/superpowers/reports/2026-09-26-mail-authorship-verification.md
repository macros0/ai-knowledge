# Строгая проверка авторства и GPT-4.1

26.09.2026. Пользователь разрешил GPT-4.1 для генерации OKF и строгую проверку авторства. Эти решения больше не ожидаются. Future chunk-risk/admin gate остаётся отдельным backlog.

## Поведение

Локальные LLM_MODEL и LLM_CHAT_MODEL теперь openrouter/openai/gpt-4.1. Подтверждённый синтетический backend :18000 точечно перезапущен; startup log подтверждает обе модели и mail-sources-v21. PostgreSQL/Qdrant рабочего корпуса не изменялись; массовая перегенерация не запускалась.

Вопросы с явным запросом авторства RU/EN идут через консервативный extractive режим. Сервер повторно читает канонический чанк SQL по документу, chunk_index и source_id; для концептов координаты читаются из SQL, не берутся из digest/index. Родительский источник не подставляется вместо вложения. Модель выбирает только цитаты; сервер проверяет их дословное наличие именно в названном источнике, длину и номер. Другие поля ответа модели не публикуются. Непригодный JSON/выдуманные цитаты дают ответ о неустановленном авторстве.

Самостоятельная строка Автор:/Authors:/Составитель:, включая «Автор таблицы:», показывается как указание в конкретном источнике. Непосредственно подписанная реплика после цитируемого вопроса («Ольга: …») показывается отдельно как «Обозначения реплик в исходном тексте», без утверждения об авторстве всего документа. Кодовые примеры и цитируемые подписи не считаются доказательством. Это не независимая проверка личности и не доказательство, что автор всего источника написал каждую цитату/вложение. Sender, office creator и имя над цитируемым вопросом не используются как доказательство автора вложения или неподписанного ответа. Фрагменты выдаются в fenced text, с внешней серверной ссылкой: исходные картинки/ссылки/[N]/backticks не создают активный Markdown внутри цитаты.

Составной вопрос сохраняет фактическую часть как проверенные цитаты. Это сознательно более консервативный ответ, чем обычный свободный пересказ. Возможны ложные отказы при подписи в другом формате, недостаточной выдаче или обрезанном контексте. Распознавание явных запросов авторства лексическое; эта доработка не является гарантией для всех парафраз и спонтанных атрибуций в обычном чате. Улучшение универсального извлечения типизированных утверждений требует отдельного объёма работ.

## Свежие результаты

Последнее дополнение: положительные контроли сначала дали RED (явный автор таблицы, подписанные реплики и подпись внутри кодового примера). После исправления 26 тестов авторства и 14 связанных chat/locale/hydration прошли: 40 Windows и 40 Linux, exit0. Linux проверен offline/read-only на frozen исходниках с двумя явно подключёнными окончательными файлами; это scoped suite, не повтор всего backend. Ruff E4/E7/E9/F/I для этих файлов прошёл.

Новый real-model прогон `tests/tmp/mail-authorship-positive-v21/report.json`: четыре настоящих загрузки EML, включая XLSX без автора и DOCX с подписанной таблицей, публикация, BM25 и GPT-4.1 generation/chat в отдельной `mail_semantics_author_v4`. Все структурные проверки прошли. Семантическая проверка ответов: неподписанные уточнения сохраняют 22 дня/электронный акт и неизвестное авторство; пересланная XLSX сохраняет 14 дней без приписывания Петру; две реплики Ольги показаны как обозначения реплик; «Автор таблицы: Ольга Смирнова.» взят из DOCX `root/0`, а не из родительского письма. Этот небольшой набор не доказывает распознавание всех форм подписей.

После последнего изменения только подтверждённый синтетический backend перезапущен (45408).
