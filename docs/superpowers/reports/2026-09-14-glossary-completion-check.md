# Глоссарий: проверка после исправления замечаний

Этот отчёт продолжает `2026-09-14-glossary-final-results-review.md` и уточняет
его выводы после последующих исправлений. Исторические результаты не заменяют
проверку текущего дерева. Коммитов и переиндексации документов не выполнялось.

## Исправленные замечания

- Merge проверяет новые формы в draft/source_edit и итоговые алиасы: вычисленный
  повтор того же ИТ и форма другого номера не обходят обычную валидацию.
  Прежнее имя не записывается отдельным алиасом, если его уже предоставляет правило.
- Бюджет контекста применяется после глобальной сортировки прошедших точную проверку
  блоков. Слабый sibling не вытесняет более сильный блок другого документа.
- Seed dry-run проверяет полное пространство имён, включая существующие карточки,
  их алиасы и отключённые правила. `--rules-file` позволяет атомарно загрузить
  правила вместе с терминами; повтор пакета идемпотентен.
- Merge API возвращает типизированный результат и свежий preview при конфликте;
  commit требует revision и digest. Появилась read-only проверка правил.
- Offline migration проигрывает план на частной копии метаданных, проверяет начальные
  версии, поддерживает несколько merge в одну цель и проверяет итоговый namespace.
  Backup содержит полные метаданные; аудит сохраняет checksum плана и результата.
- После трёх неудачных optimistic reads snapshot использует короткую блокировку
  state. Readiness повторно проверяется; revision, timestamp и аудит не меняются.
- Добавлены `common.loading` и отдельное объяснение недопустимого объединения правил.
  Диалоги удерживают фокус; первый Escape закрывает вложенный список языков,
  возвращая фокус его кнопке, следующий — сам диалог.
- Ввод имени в create/edit использует debounce 350 мс и учитывает черновые kind
  и infotype_number. При известном конфликте обычное сохранение заблокировано;
  отдельная кнопка открывает merge с текущими полями и алиасами. Отказ сохраняет
  их и возвращает фокус кнопке. Добавлен read-only `/conflicts/check` полного draft.
- Добавлен read-only `/rules/preview`: предложенное правило проверяется без БД,
  в том числе до миграции. UI показывает формы для примера запроса и скрывает
  устаревший ответ после изменения границ, префиксов или запроса.

## Правила диапазонов в интерфейсе

По замечанию пользователя проверена реальная страница. Форма существовала, но
не имела оформления: поля сливались в одну строку, префиксы были подписаны
«IT, ИТ», заголовок говорил об одном системном правиле. Блок оформлен как
«Правила инфотипов»: отдельный список диапазонов, явная форма нового правила,
четырёхзначные границы и поле «Префиксы через запятую».

В браузере на disposable SQLite-контуре сохранено второе правило `1000–1999`
с префиксами `IT, ИТ, Infotyp`. Оно появилось рядом с первым правилом.
Readback через preview: `IT1000` и `ИТ 1999` распознаны; `IT2000`, `IT10000`
и `XIT1000Y` имеют `no_match`. Индекс для этого не создавался и не изменялся.
Статус `limited` у положительных запросов означает действующий бюджет добавления
форм; проверка полного набора разрешённых форм от этого не становится нечёткой.

В UI предпросмотр `ИТ 1999` в диапазоне `1000–1999` показал `IT1999` и шесть
форм трёх префиксов. После изменения конца черновика на `1998` старый результат
исчез, повтор дал «Совпадений нет». Сохранённое правило осталось `1000–1999`,
version=1: проверка по Enter ничего не записала.

Для итогового просмотра тестовая форма оставлена с двумя понятными примерами:
«Основные данные персонала» `0000–0999` и «Организационный менеджмент» `1000–1999`.
Это данные disposable-контура, не автоматические настройки пользовательских баз.

## Производительность и решение пользователя

Последний завершённый замер: LocalQdrant + SQLite, 40 документов / 80 точек,
50 префиксов, 30 повторов. Это локальный поисковый путь без HTTP, embedding и LLM.

| Запрос | p95 без расширения | p95 с расширением | Добавленная задержка |
|---|---:|---:|---:|
| Один термин | 5,259 мс | 7,390 мс | 2,131 мс |
| Пять терминов | 7,487 мс | 13,761 мс | 6,274 мс |

При холодных кэшах приложения: p95 29,165 и 50,411 мс соответственно.
Чтение полных текстов составляет 346 100 UTF-8 байт вместо 24 000; индексный
fingerprint не изменился. Артефакты: `glossary-exact-benchmark-final.json` и
`glossary-exact-cold-cache-final.json` в `backend/.tmp-glossary-review/`.

Прежний порог прироста p95 «не более +20%» не достигнут. Пользователь выбрал:
«Согласовать абсолютный предел задержки отдельно». Числовой абсолютный предел
пока не установлен; производительность не помечается как прошедшая этот критерий.

## Текущий статус проверки

- Frontend: **153 passed**, 0 failed; целевой ESLint без ошибок; production build
  Next.js завершился с exit 0. Логи `frontend-frozen-acceptance.log` и
  `frontend-build-frozen.log` в `backend/.tmp-glossary-review/`.
- PostgreSQL: **5 concurrency pytest passed**; 11 существующих migration-plan
  и 2 snapshot-contract функции выполнены на реальном отдельном PostgreSQL.
  Дополнительные probes подтвердили dry-run без записей, два merge в одну цель,
  apply/replay/persisted checksum и полный rollback при ошибке аудита.
  Первый timezone-assert теста сравнивал часы разных зон; исправлено сравнение
  одного UTC-момента, повтор прошёл. Кластер :15432 штатно остановлен.
- Словари UI и snapshot в новом процессе: **29 passed**. Предыдущий полный прогон
  дал **1416 passed, 5 failed, 5 skipped**: обновление UI manifests во время его
  работы рассогласовало process cache ключей с новым `ui_en.json`. Это не зелёный
  полный прогон. После завершения изменений новый полный backend-прогон прошёл:
  **1448 passed, 5 skipped, 113 warnings**, exit 0, 13 мин 27 с. Пять skipped —
  PostgreSQL-тесты, отдельно все пять прошли. Полный Ruff также прошёл.
  Лог: `backend/.tmp-glossary-review/full-frozen-acceptance.log`.
- Browser QA: create/edit name conflict, blocked Save/Create, явный merge,
  отказ без потери имени/описания/другого алиаса и возврат фокуса проверены.
- Независимое ограниченное ревью новых API/UI: блокирующих замечаний не найдено;
  отдельный RAM-probe проверил границы, spans, draft kind, foreign/own owner и
  SQL write-spy для preflight; дополнительных изменений кода не потребовалось.

Текущая совместимость API: `GET /rules` сохраняет прежний ответ-массив;
числовые границы остаются числами в JSON, а UI отображает их четырьмя цифрами.
Revision доступна в query/merge preview. Типизированный merge-preview сохраняет
старые имена полей и дополнительно возвращает `result`, `revision`, `preview_digest`,
`removed_term_id`, `conflicts` и `requires_confirmation`.

## Рекомендации

1. Отдельно согласовать абсолютный p95 для тёплого и холодного поиска на
   представительном корпусе, с явно заданными числом кандидатов и размерами текстов.
2. Настраивать диапазоны и буквальные префиксы в UI; не переносить их в код
   и не создавать постоянные алиасы для всех номеров диапазона.
3. Сохранить регрессионные проверки merge, полного текста и отсутствия записи
   в индекс. Изменения терминов, алиасов и правил ИТ не требуют переиндексации.

## Отметка о выполнении

Запрошенные доработки и исправления замечаний выполнены и проверены. Обновлённый
редактор оставлен для просмотра на `http://127.0.0.1:16301/admin/glossary`
с отдельным тестовым backend :18001 и SQLite. Это контур проверки глоссария;
поискового корпуса и полного стека Qdrant/LLM в нём нет. Основные сервисы
:16300/:18000 и пользовательские документы не перезапускались и не менялись.
Временный PostgreSQL остановлен. Commit/push не выполнялись.

Числовой предел p95 остаётся отдельным согласованием. Этот отчёт подтверждает
функциональные проверки и замеры, но не прохождение всех исходных критериев
производительности плана.
