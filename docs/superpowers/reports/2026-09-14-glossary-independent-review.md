## Подтверждённые замечания

### 1. P1 — строгий фильтр отбрасывает разрешённый явный алиас

`expansion.py:129,481`, `context_builder.py:97`.
Транзакция с именем `PA30` и поисковым алиасом `Maintain HR master data`:
запрос `PA30` добавляет алиас в sparse, но `strict_groups` содержит только
`PA30`. Проверка текста `Maintain HR master data` этой группой возвращает False;
search/chat передают именно эти группы в фильтр и удаляют такой найденный блок.

Рекомендация: сформировать единый набор полных разрешённых форм для строгой
проверки. Ограничения размера запроса не должны подменять эквивалентность форм.
Проверить обе стороны name→alias и alias→alias на реальном retrieval-пути.

### 2. P1 — распознавание ИТ правилом теряет явные поисковые алиасы

`expansion.py:211,223` заменяет полный набор форм карточки на
`forms_for_number`. При запросе `IT0003` разрешённый явный алиас
`Personnel status record` не появляется в `added_sparse_texts`; остаются только
`it0003` и `it 0003`. Лимиты в тесте заведомо достаточны.

Рекомендация: объединять источники форм карточки и правила, сохраняя flags,
вместо замены одного набора другим. ИТ и обычные термины должны проходить через
один контракт разрешённых форм.

### 3. P1 — объединение разных номеров ИТ удаляет одну идентичность

`registry.py:1118,1189`. Созданы карточки `0003` и `0004`, правила не нужны.
Preview и merge принимают их объединение; остаётся `0004`, source удалён.
Это нарушает запрет объединять разные предметные номера из раздела 7 плана.

Рекомендация: проверять совместимость kind/номеров до preview и повторно внутри
commit; возвращать конфликт без удаления source. Подтверждение объединения
не делает разные номера одним инфотипом.

### 4. P1 — номер ИТ не задаётся через обычный UI

`GlossaryPanel.jsx:29,68,105`, `GlossaryEditor.jsx`,
`models/glossary.py:35,52`, `registry.py:395`.
В форме создания и редакторе нет поля номера. Сервис принимает новую карточку
`sap_infotype` с `infotype_number=None`, что подтверждено сценарием. API
редактирования исходных полей не содержит `infotype_number`. Созданная так
карточка не получает связь с номером через правило.

Рекомендация: добавить номер в create/edit UI и API; для новых ИТ требовать
ровно четыре ASCII-цифры, для остальных видов запрещать номер. Nullable для
исторической миграции не должен разрешать новые неполные карточки.

### 5. P2 — отключённая карточка ИТ обходится виртуальной карточкой

`registry.py:638`, `expansion.py:174,187`. Snapshot содержит только enabled
карточки. После отключения ИТ `0003` правило всё равно даёт `applied`, создавая
виртуальный термин вместо отключённого. План явно запрещает такой обход.

Рекомендация: передавать в snapshot информацию о владельцах отключённых номеров
и блокировать виртуальную подстановку для них.

### 6. P2 — один виртуальный ИТ повторяется в плане запроса

`expansion.py:185`. Без карточки запрос `IT0003 ИТ 0003` создаёт два
`AppliedTerm` и два dense-маркера одного `IT0003`. Для `term_id=None` поиск
существующей группы всегда пропускается. Это также расходует лимит терминов.

Рекомендация: группировать по предметному ключу `infotype:0003`, объединяя spans.

### 7. P2 — replay сверяет переданный digest, но не полный запрос

`registry.py:1086`. После успешного merge изменение `target_term_id` при прежних
`request_id` и digest принимается: возвращается старый результат, а не конфликт.
Повтор не выполняет новую операцию, но нарушает контракт проверки содержимого.

Рекомендация: хранить hash нормализованного commit-запроса, включая source,
target, selections, версии и digest; сравнивать его до возврата receipt.

### 8. P2 — перенесённый перевод ошибочно становится актуальным

`registry.py:1120,1179`. У source `source_revision=2`, у target до merge — 1.
После merge у target тоже 2, и скопированный перевод source сохраняет revision 2
и reviewed_by. Перевод другого исходного текста теперь считается актуальным.

Рекомендация: свежесть определять соответствием исходного текста, а не равенством
счётчиков разных карточек. Сбрасывать review и помечать переносимый перевод
устаревшим при изменении источника; увеличивать source_revision target только при
изменении его исходных полей.

### 9. P2 — изменение перевода не обновляет snapshot другого процесса

`translations.py:343,396`. Все пути записи переводов используют старый
`session_scope`, без общего state-lock и bump revision. Сценарий прогревает
snapshot, записывает перевод через штатный сервис с отключённой локальной
инвалидацией (модель другого worker), проверяет сохранение в БД. Следующий запрос
продолжает показывать старое имя.

Рекомендация: после LLM и для ручных переводов применять общий протокол записи
глоссария, включая ревизию и повторные проверки внутри транзакции. Отдельно
проверить PostgreSQL-гонку merge↔translation; в этом ревью она не воспроизводилась.
