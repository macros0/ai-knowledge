# Диагностический пакет для разработчика — проект решения

Дата: 2026-09-27. Статус: проект для разработки; реализация не начата.

## 1. Назначение и границы

Администратор продуктивной системы должен самостоятельно получить техническую
диагностику сбоя и передать её разработчику, не предоставляя доступ к системе.
Для уже произошедших ошибок сохраняется небольшой постоянный журнал. Для
воспроизводимых проблем администратор временно включает подробный сбор.

Обязательный результат: ZIP с понятной сводкой и машинно-читаемыми событиями,
который позволяет связать запрос, фоновую операцию, этап обработки и ошибку.
Передача за пределы системы выполняется вручную. Никаких внешних SaaS, отправки
по почте, Docker socket в приложении, дампа БД или содержимого документов.

Охват первой версии: backend API, фоновые задачи и обработка документов,
LLM/эмбеддинги/Qdrant, сервер Next.js и ограниченные технические ошибки браузера.
Недоступность самой админки покрывается отдельной командой эксплуатационного
администратора. Логи внешних сервисов заказчика автоматически не собираются.

## 2. Проверенные точки интеграции

- `backend/app/main.py`: обычный `logging.basicConfig(INFO)`, обработчики ошибок,
  lifespan и мягкий старт при сбое зависимостей. Общей трассировки запросов нет.
- `backend/app/services/llm_client.py`: `_dump_debug_response` пишет сырой ответ
  в `data/debug`, ошибка разбора включает первые 200 символов ответа. Это нельзя
  экспортировать как безопасную диагностику.
- `backend/app/services/pipeline.py`: фоновые потоки, этапы, retries, состояния
  документа и попытки обновления; ошибки могут содержать произвольный текст.
- `backend/app/services/export_queue.py`: полезный образец квот, leases,
  фонового построения и аудита; сам worker экспорта исходников не переиспользовать.
- `backend/app/services/job_queue.py`: очередь документоцентрична. Диагностика
  не должна становиться задачей удаления/генерации или её частью.
- `backend/app/services/audit.py`: append-only аудит. Читает роль `security`;
  наличие роли `admin` не даёт права выгружать полный журнал ИБ.
- `frontend/src/app/api/[...path]/route.js`: потоковый прокси, несколько
  `Set-Cookie`, `no-store`, удаление поддельных forwarding headers.
- `frontend/src/lib/api.js`, `chatStream.mjs`: централизованные ошибки HTTP и
  отдельно ошибки NDJSON после начала streaming-ответа.
- `frontend/src/components/AdminPanel.jsx`: действующая панель фоновых операций.
- `docker-compose.yml`: один backend-процесс, один frontend; два production-режима.
- Установленная документация Next.js описывает `src/instrumentation.js` и
  `onRequestError(err, request, context)`; сырые аргументы hook не сериализовать.

## 3. Ограничения и значения по умолчанию

Все объёмы ниже — МиБ, 1 МиБ = 1 048 576 байт. Это решения данного проекта,
а не измеренные характеристики уже существующей реализации.

| Параметр | Значение |
|---|---|
| Постоянный backend-журнал | WARN/ERROR + lifecycle; 7 суток; 50 МиБ |
| Журнал Next.js | ошибки proxy/SSR + lifecycle; 7 суток; 20 МиБ |
| Подробная сессия | 15 минут; допустимо 5–60 минут; 100 МиБ |
| Одновременно активных сессий | 1 на инсталляцию |
| TTL подробных данных | 24 часа после остановки сессии |
| TTL готового пакета | 24 часа после публикации |
| Общее хранилище | 500 МиБ: backend 480 + frontend 20 |
| Резерв свободного места | 2 ГиБ на соответствующем filesystem |
| Размер готового ZIP | не более 200 МиБ |
| Очередь пакетов | 1 строится, максимум 2 ожидают |
| Ограничение администратора | 1 незавершённый пакет, 3 создания в час |
| Событие | не более 8 КиБ; не более 32 кадров стека |
| Очередь backend-событий | 4096 записей; неблокирующая постановка |
| Очередь Node-событий | 256 записей; неблокирующая постановка |
| Сегмент журнала | не более 5 МиБ; запись не пересекает границу сегмента |
| Maintenance | не реже 1 раза в 60 секунд, также при старте |
| Браузерный отчёт | до 4 КиБ, 10/мин на пользователя и 100/мин суммарно |
| Число записей на странице UI | 50; API разрешает максимум 100 |

Backend-квота включает события, control-файлы, снимки входных данных, архивы,
`.building`, `.deleting`, deferred-audit journal и все резервирования. У frontend
свой фиксированный бюджет, поэтому два процесса не обещают одни и те же байты.
Записи и выходной архив проверяются до каждого увеличения файла; metadata тоже
учитывается. SQLite/PostgreSQL metadata ограничивается сроками и rate limits,
но не входит в файловые 500 МиБ. Audit retention остаётся отдельной политикой.

Превышение срока или объёма прекращает подробную сессию. Постоянные журналы
ротируются. При низком свободном месте прекращается запись на диск, остаются
ограниченные счётчики и состояние `storage_degraded`; основные операции не падают.
При занятых leases/reservations новый пакет отклоняется, активные данные не стираются.

Подробная сессия ограничивает только успешные `request_finished` (HTTP 2xx/3xx):
не более 20 событий в секунду на шаблон маршрута. Это предохраняет writer от
потока однотипных успешных запросов; HTTP 4xx/5xx, WARN/ERROR и события
предметных операций не семплируются. Число пропущенных успешных запросов
показывается как `recorder_sampled_success` в manifest и не считается аварийной
потерей `recorder_loss`. Одновременно активна лишь одна сессия.

## 4. Формат событий и запреты

`DiagnosticEventV1`: `schema_version=1`, `event_id`, `timestamp_utc`, `boot_id`,
`component` (`backend|frontend|browser`), `level`, `event_code`, `request_id?`,
`operation_id?`, `diagnostic_session_id?`, `route_template?`, `http_method?`,
`http_status?`, `duration_ms?`, `doc_id?`, `generation_id?`, `chunk_index?`,
`retry_index?`, `dependency?`, `error_code?`, `exception_type?`, `frames?`,
`counts?`, `origin` (`server|client_reported`). Поля разрешаются отдельно для
каждого `event_code`; лишние поля отвергаются, не перекладываются в `extra`.

Нельзя записывать: `str(exc)`, `repr(exc)`, traceback source lines/locals,
request/response bodies, URL query/fragment, cookies, auth headers, DSN, env dump,
SQL и его параметры, filename/title/путь пользователя, промпты, текст ответа LLM,
текст чата, содержимое документа/письма/вложения. Стек содержит только разрешённый
путь модуля относительно приложения, функцию и номер строки. Неизвестный кадр
заменяется маркером `external_frame`; неизвестный тип — `UnknownError`.

Идентификаторы документов/операций — проверенные непрозрачные ID. Учётная запись,
IP, группы и имя администратора остаются в аудите, не в диагностическом пакете.
Настройки экспортируются явным allowlist; `model_dump(settings)` запрещён.
Вместо произвольного имени модели экспортируется профиль и fingerprint модели;
полные endpoint URLs и имена серверов не экспортируются.

Очистка выполняется до попадания в очередь/на диск; повторная валидация — при
построении пакета. Чужой/старый/повреждённый формат не включается и отражается
счётчиком. Невозможно обещать очистку произвольного старого текстового лога:
такие логи никогда не служат входом обычной выгрузки.

Python-handler для существующих WARN/ERROR берёт только безопасный контекст,
уровень, зарегистрированный logger, тип/кадры исключения; никогда `getMessage()`
или `args`. Полезные детали новых событий пишутся явно через `emit_event`.
Для повторов сохраняются первый/последний момент и счётчик; переполнение очереди
и любое сокращение отражаются в сводке, а не маскируются полнотой результата.

Сырой LLM dump отключается в production без возможности включить его из UI.
Для development возможен отдельный явный opt-in с собственной квотой/TTL,
не связанный с этой функцией. Существующие `data/debug` не экспортируются и
не удаляются автоматически при обновлении: их инвентаризация/удаление — отдельная
операция владельца системы. Префикс ответа удаляется из текста исключения.

## 5. Корреляция и отбор

Next.js создаёт UUID запроса, заменяя присланный извне `X-Request-ID`; возвращает
его браузеру и передаёт backend. Backend проверяет формат, сохраняет валидный
ID либо генерирует новый. ID — метка связи, не доказательство авторизации.
В режиме прямого backend клиентский UUID считается недоверенной меткой.
SSR `backendFetch` наследует request-context, если он есть, иначе создаёт ID.

Backend middleware должен быть pure ASGI: не буферизовать upload, ZIP или NDJSON.
Контекст снимается в `finally`. В `ThreadPoolExecutor`, pipeline и очереди
передаётся явный immutable context; новая генерация/resume имеет свой operation ID
со ссылкой на исходный request и существующий generation ID. `boot_id` меняется
при рестарте. Ошибка после HTTP 200 записывается и передаёт `request_id` в
NDJSON error event. UI показывает тот же код обращения.

Scope сессии: `system`, `document` (ровно один существующий doc_id), `search_chat`,
`interface`. Это фильтр записи дополнительных событий, а не только фильтр ZIP.
Общие переходы доступности зависимостей добавляются как контекст с отдельной
меткой; чужие операции документа в сессию не включаются. Уже начатая до сессии
операция отбирается по событиям, произошедшим после её включения.

При создании пакета выбирается либо сессия, либо UTC-интервал не более 7 суток;
дополнительные фильтры `request_id`, `operation_id`, `doc_id`. Дефолт — последний
час. Архив — конечный snapshot с `cutoff_at`, не постоянно меняющаяся ссылка.
Сбор событий не запускает повторную генерацию, запрос к LLM или переиндексацию.

## 6. Состояния, хранение и аудит

Две отдельные таблицы: `diagnostic_sessions` и `diagnostic_bundles`; новые задачи
не помещаются в `jobs`. Метаданные и запрос обязательного аудита коммитятся одной
SQL-транзакцией. При SQLite/PG проверяется одна и та же семантика.

Сессия: `starting -> active -> stopped`; terminal reason:
`manual|expired|size_limit|storage_low|storage_error|server_restarted|disabled`.
`starting` нужен для границы SQL/filesystem: до committed start-аудита запись
подробностей запрещена; сбой активации даёт terminal reason, не тайный active.
Повторный stop идемпотентен. Рестарт никогда не возобновляет подробный сбор.
UTC нужен для отображения, monotonic deadline — для работающего процесса.

Пакет: `queued -> building -> ready|failed`, затем `expired|deleted`.
Артефакт строится в `.building`, после проверки атомарно переименовывается;
скачивание разрешено только при metadata `ready`, существующем файле и живом TTL.
Рестарт помечает queued/building как failed/restart; сам не повторяет сбор.
Метаданные stopped/failed/expired/deleted удаляются через 7 суток после завершения;
audit_log сохраняется по своей политике. Не удалять строку до физической очистки
и переноса ожидающих audit-событий.

В SQL-строках: UUID, автор, время, scope/filter, состояние, reason/error_code,
counts, schema version и список применённых control event IDs для дедупликации.
У сессии дополнительно deadline, boot ID, bytes; у пакета cutoff/expiry, размер,
checksum и UUID-ключ файлов. Никаких произвольных путей, заголовков и `str(exc)`.
Для browser opt-in у сессии есть bounded JSON со списком не более 10 участников
и hash одноразовых приглашений; эти поля не включаются в диагностические события.

Audit actions: `diagnostic_session_started`, `diagnostic_session_stopped`,
`diagnostic_bundle_requested`, `diagnostic_bundle_ready`,
`diagnostic_bundle_failed`, `diagnostic_bundle_download_started`,
`diagnostic_bundle_deleted`, `diagnostic_bundle_expired`.
Просмотр событий/preview фиксируется `diagnostic_view` с фильтрами и количеством,
без содержимого. Одно UI-открытие и изменение фильтра дают событие, автоматический
polling статуса не порождает аудит каждые несколько секунд.
Приглашение/подключение/отключение браузера фиксируется отдельными действиями
`diagnostic_browser_invited`, `diagnostic_browser_joined`, `diagnostic_browser_left`;
пригласительный код никогда не сохраняется в аудите.

Start, просмотр содержимого, создание, выдача файла и ручное удаление fail-closed
при невозможности обязательного аудита. Download audit означает начало, а не
доказательство получения пользователем всех байтов. Логи событий продолжают
работать при недоступной БД. Остановка и автоматическое ограничение/удаление
по TTL выполняются даже при сбое БД: безопасное сокращение сбора нельзя блокировать.
Control event пишется в локальный bounded journal до 1 МиБ внутри backend-квоты,
после восстановления БД переносится транзакционно с дедупликацией в metadata.
Если недоступны и диск, и БД, гарантировать запись невозможно: показывается
`audit_gap`, новые административные действия блокируются; это документированная
граница, не заявление о безусловной полноте аудита.
При сбое БД UI может не пройти обычную авторизацию: обхода входа ради stop нет.
В таком случае остановка по deadline/лимиту всё равно работает локально,
а эксплуатационный администратор может отключить сбор управляемым рестартом.

Файлы размещаются в отдельном `OKF_DIAGNOSTICS_DIR` вне `OKF_DATA_DIR`:
`backend/` (владелец backend), `frontend/` (владелец Next.js).
Backend читает frontend spool через read-only mount. Frontend не получает доступ
к backend-архивам или документам. Backend не удаляет активные frontend-сегменты.
Frontend получает только отдельный read-only control projection: boot ID, scope,
session ID, deadline и lease на 10 секунд, обновляемый backend каждые 5 секунд.
Нет свежего lease — нет подробной записи; baseline ошибок продолжает работать.
Frontend самостоятельно ротирует spool; при его остановке CLI может обслужить
только просроченные файлы после проверки отсутствия writer lock.

У каждого spool один writer с filesystem lock; второй writer отказывается от
записи и показывает degraded, не повреждает журнал. Одна реплика каждого сервиса —
граница v1, сохранённая в deployment. Истечение TTL проверяется при чтении даже
до следующего sweep. Любая очистка запрещает выход из корня, symlink/junction,
reparse point и следование пользовательским путям.

## 7. Пакет, UI и браузер

ZIP (DEFLATE level 1, потоковое чтение, без полной буферизации) содержит только:
`summary.txt`, `manifest.json`, `events/backend.jsonl`, `events/frontend.jsonl`,
`events/browser.jsonl`, `snapshots/runtime.json`, `snapshots/operations.json`.
Manifest содержит формат, build/revision, timestamps UTC, компоненты, фактическое
покрытие, ограничения, counts dropped/invalid/truncated, checksums записей.
Checksum самого ZIP хранится в metadata, а не внутри себя.

Snapshot сегментов фиксируется с ограничением длины и leases/копией в backend
budget. Для frontend необходима копия со сверкой identity/size и boundary строки;
исчезнувший сегмент — отмеченный gap, не падение всего пакета. Квота резервирует
snapshot + верхнюю оценку ZIP, включая overhead. Не использовать assumption,
что сжатие обязательно уменьшает объём. Если пакет превышает лимит, построение
заканчивается `diagnostic_bundle_too_large` с предложением сузить период.

UI: `/admin/diagnostics`, вход из AdminPanel, RequireRole(admin), русская и
английская локализация. Статус, free/used/quota, последние ошибки, фильтры,
старт/стоп сессии, список пакетов, preview manifest, потоковое скачивание и удаление.
Показывать scope, countdown, actual coverage и причину прекращения. Просроченный
или частичный пакет не показывать полным; недоступный статус не показывать «выключено».
Тексты provider/internal paths в UI не выводить. Подтверждать удаление пакета,
не вводить обязательное повторное подтверждение каждого включения сбора.

Минимальные ошибки браузера собираются только во время interface/system-сессии
для явно подключённого администратором собственного браузера. Другой пользователь
может отдельно подключить свой браузер через короткий код сессии после входа;
код не даёт прав чтения/управления, сервер проверяет действующую сессию.
Приглашение — 128-bit random, передаётся через POST, хранится только hash,
одноразовое и не дольше срока сессии. Участников максимум 10, join — 5/мин/user.
Для самостоятельного отключения участия есть authenticated POST leave;
он удаляет участие, очищает локальную очередь и не останавливает всю сессию.
Не включать скрытый глобальный сбор во всех браузерах. Отправляются фиксированный
код, build ID, route template, request ID и безопасные frame coordinates;
никаких message/DOM/forms/history/console/network bodies. Клиентские данные
всегда помечены `client_reported` и не считаются доказанными серверными событиями.
При offline — только очередь в памяти, до 20 событий/80 КиБ, без localStorage;
flush разрешён только до session deadline, затем данные удаляются с gap-счётчиком.
Публичные sourcemaps не включать; разработчик использует артефакты своей сборки.

## 8. Резервный сбор и эксплуатация

CLI `backend/scripts/collect_diagnostics.py` работает без загрузки FastAPI,
инициализации pipeline и без обязательного соединения с БД. Вход — разрешённый
диагностический корень, период; выход — новый ZIP, без перезаписи существующего.
Тот же validator/builder, те же лимиты. DB/config snapshot при недоступности
заменяется честным `unavailable`, сохранённые события остаются доступны.
Сбор во время работающего приложения идёт через API; offline CLI требует lock
на backend spool и не конкурирует с writer. Отказ writer lock — понятная ошибка.

Production wrapper получает от Docker только allowlisted состояние, exit code,
OOMKilled, timestamps и image identity для сервисов данного Compose project.
Никогда не пишет полный `docker inspect`, env или сырые `compose logs` в ZIP.
При невозможности загрузить runtime даже одноразового контейнера runbook
описывает передачу сохранённого безопасного spool; это граница CLI.
Ошибка до инициализации регистратора, SIGKILL и OOM могут не иметь stack trace;
пакет сообщает границу и последнее сохранённое событие.

Docker stdout/stderr ротируются независимо: `json-file`, `max-size=10m`,
`max-file=3` для каждого сервиса Compose. Это отдельное потребление диска сверх
500 МиБ; backend/frontend/postgres/qdrant/migrate суммарно до примерно 150 МиБ
на одну инсталляцию, с учётом поведения драйвера и дополнительных контейнеров.
Существующие внешние БД и их политики не меняются.

Диагностический каталог не входит в обычный backup документов. SQL metadata
может попасть в backup: restore/recovery прекращает active и проверяет наличие
артефакта до выдачи. Релиз обновляет SECURITY.md, deployment docs и runbook.
Feature flags раздельные: baseline, временный сбор, создание пакетов, скачивание;
выключение не отменяет cleanup. Быстрый откат выключает сбор/выдачу, сохраняет
совместимые metadata-таблицы и не включает старые сырые LLM-дампы.

## 9. Критерии результата

1. Админ получает пригодный ZIP для уже записанного сбоя и воспроизведённой ошибки.
2. Безопасные события сохраняются при падении БД; выдача через UI не обходит аудит.
3. После закрытия вкладки, рестарта, изменения часов и достижения лимита сбор
   не продолжается бесконтрольно; expiry соблюдается на сервере.
4. В сырых новых диагностических файлах, metadata, UI и ZIP нет тестовых секретов
   и текстов документов; старые произвольные логи никогда не импортируются.
5. reader/editor/security/anonymous не получают admin-диагностику; CSRF и
   отзыв admin-роли проверяются на каждом действии и новом download request.
6. Ротация/построение/скачивание не превышают budgets и не ломают business requests.
7. Proxy сохраняет streaming, multiple Set-Cookie, cancellation и безопасные ошибки.
8. Оба production storage modes, Windows dev и Linux контейнеры проходят приёмку.
9. Нагрузочная приёмка: прирост p95 API не более 10% при подробном сборе и 20%
   при построении пакета; прирост RSS backend при build <=128 МиБ, Next <=32 МиБ;
   нет новых 5xx основного сценария. Сравнение на одном изолированном стенде.

## Дополнение от 2026-09-29: уровни сбора и производительность

Принято к реализации по плану `2026-09-28-admin-diagnostics-levels-performance.md`. До завершения разработки и приёмки это контракт новой версии, а не описание уже работающего сервиса. При расхождении с описанием первой версии ниже действуют явно указанные изменения этого дополнения.

### 2. Пользовательская модель и состав данных

В интерфейсе показывать постоянный «Базовый журнал» отдельно от временного сбора. В форме запуска две независимые настройки: «Область» и «Детализация». Значения временной детализации: «Стандартная» и «Подробная»; новая сессия по умолчанию стандартная. Не создавать третье значение `baseline` в `SessionStart`: это действующий постоянный режим, а не ещё одна временная сессия.

Scope остаётся `system|document|search_chat|interface`. Начальное значение scope сохраняется `system`, чтобы не выбирать за администратора чужой сценарий; рядом дать короткую рекомендацию выбирать узкую область. При активной сессии её уровень неизменяем: остановить и создать новую с новым ID. Рестарт не возобновляет capture.

| Данные | Базовый | Стандартный capture | Подробный capture |
|---|---|---|---|
| WARN/ERROR, неуспешные зависимости, HTTP 4xx/5xx, lifecycle | Существующее поведение | Сохранять с корреляцией | Сохранять с корреляцией |
| Browser errors | Нет скрытого сбора | Только opt-in и подходящий scope | То же |
| Начало/итог фоновой обработки документа, переходы parse/split/generate/index/publish | Только ошибки по прежней политике | Сохранять крупные переходы и итог | Сохранять также детализацию выбранной операции |
| Успешные короткие search/chat-операции | Не писать | Один ограниченный итог + агрегаты | Цепочка событий выбранных операций + агрегаты всех |
| Успешные dependency calls | Не писать | Количество/время/максимум; отдельно медленные | Отдельные события выбранных операций |
| Успешные HTTP/proxy, health/status polling | Не писать | Агрегаты; индивидуально медленные | Выборка связанных запросов; служебный polling остаётся агрегированным |
| Retry, fallback, деградация, частичная индексация | Ошибки/предупреждения по текущей классификации | Сохранять | Сохранять |
| Текст запроса/документа/ответа модели, raw stack locals | Никогда | Никогда | Никогда |

Один итог короткой операции заменяет её `operation_started`, дублирующие `stage_started/stage_finished` для того же внешнего этапа и `operation_finished`; ошибки не превращаются в успешный итог. У фоновых документов сохранять крупные этапы: иначе после kill/OOM нельзя определить последний известный этап. Per-chunk/per-batch успешные события в стандартном режиме агрегировать; счётчики прогресса не считать диагностической потерей.

HTTP и proxy имеют разные границы измерения, особенно для streaming. Не складывать их длительности и не называть время до заголовков временем полного ответа. У stream сохранять отдельную ошибку после 200 и стабильный request ID. Успешный heartbeat или health poll сам по себе не должен порождать рекурсивный диагностический шум.

### 3. Политика записи и новые ограниченные структуры

Стартовые параметры фиксируются в immutable policy snapshot сессии; это эксплуатационные настройки запуска, не административные DB overrides. Не менять их на ходу у активной сессии.

| Параметр policy v1 | Значение |
|---|---:|
| Период выдачи агрегатов | 5 секунд |
| Ключей агрегирования на компонент/активную сессию | максимум 256 |
| Итогов успешных коротких операций в standard | максимум 10/с суммарно на backend, burst 10 после замера CT 102 |
| Новых подробных цепочек в detailed | максимум 1/с суммарно на компонент, burst 1 после замера CT 102 |
| Одновременно отслеживаемых цепочек на компонент | максимум 512 |
| Группа записи writer | до 64 КиБ или 50 мс, что раньше |
| Резерв очереди backend / Node для важных событий | 512 / 32 при штатных размерах очереди |
| Порог медленного HTTP/search | 1000 мс |
| Порог медленного Qdrant / DB | 250 мс |
| Порог медленных embeddings / backend proxy | 1000 мс |
| Порог медленного LLM / chat | 30000 мс |
| Порог PDF dependency | 5000 мс |

Пороги — диагностические ориентиры; нарушение SLA определяется отдельной приёмкой. Медленный успех сохраняется вне обычной выборки, но не получает безусловный резерв ERROR: иначе общий slow storm вытеснит ошибки. Для него отдельный rate limit 20/с на компонент с агрегированием остальных и явным счётчиком. WARN/ERROR/retry/деградации и lifecycle не отбрасываются политикой успехов, но физическая потеря при исчерпании общей очереди всё равно возможна и показывается.

Для очереди уменьшенного тестового размера `reserve=min(default_reserve, max(1, queue_size//8))`. Очередь остаётся одной по общему пределу: обычные записи занимают не более `queue_size-reserve`, важные используют оставшееся место. Это сохраняет порядок accepted sequence и упрощает барьер; отдельное переупорядочивание по приоритетам не вводить. При размере 1 обычные записи не принимаются.

Агрегаты группируются только по ограниченным значениям `(session_id, component, route_template, stage, dependency, outcome)`; без request ID, имён документов и произвольных строк в ключе. Поля: `count`, `duration_sum_us`, `duration_max_us`, фиксированная гистограмма длительностей с границами 10/50/250/1000/5000/30000 мс и последним bucket выше 30000. Это гистограмма, а не точный p95. Для document scope doc_id задаётся сессией; у system нельзя автоматически добавлять doc_id в каждый ключ. Переполнение ключей идёт в один overflow bucket с видимым счётчиком, а не в неограниченный dict.

При detailed решение принимается один раз на корневую операцию, переносится через существующий immutable context во все её потоки и дочерние вызовы. Для HTTP/search ключ — серверный request ID; для фонового документа — operation ID новой попытки. Клиент не управляет admission выбором UUID. Выбранная цепочка сохраняет все разрешённые события до границы сессии/лимита; достижение 512 in-flight запрещает новые подробные цепочки, но не выталкивает уже выбранные. Новая попытка resume имеет новое решение. Выборка Node и backend имеет отдельные бюджеты, поэтому межкомпонентную цепочку нельзя обещать полной, если одна сторона её не выбрала.

Сессия может включиться посреди существующей операции: события после включения допускаются, manifest явно сообщает, что начала до включения нет. При ошибке невыбранной операции записывается ошибка с ID, но прежняя история не восстанавливается из воздуха. Кольцевой буфер всех предшествующих событий и автоматическое повышение уровня при ошибке в эту версию не входят.

Счётчики различать: `aggregated_success`, `sampled_out_traces`, `sampled_out_slow`, `policy_omitted`, `aggregate_overflow` — намеренное сокращение; `dropped`, `invalid`, `expired_queue`, `drain_timeouts`, `storage_errors` — потери/сбои. Агрегация и выборка не означают `partial=true` сами по себе; manifest обязан явно описывать соответствующее покрытие. Потерянный flush агрегатов — уже потеря данных. Старый `sampled_success` читается как legacy-счётчик, не переименовывается задним числом.

### 4. Хранение, snapshot и сборка

1. Producer сначала проверяет неизменяемую политику и scope по техническим полям; отброшенный успех не создаёт UUID, asdict, JSON или stack. Принятое событие полностью проверяется до очереди; worker получает только безопасный immutable envelope. Отдельный внешний `append(bytes)` сохраняет строгую проверку для обходящих recorder callers.
2. Writer собирает batch отдельно на каждый stream, сохраняя целые JSONL-строки, границы 5 МиБ и точный учёт записанных байтов. Flush обязателен перед snapshot barrier, ручным stop и shutdown. При deadline/автоматическом stop сохраняется действующая политика прекращения записи, не возникает тайное продление сессии.
3. Index файлов хранилища строится при startup/recovery и обновляется при каждом собственном росте/rename/delete. Обход дерева остаётся в maintenance и явной сверке, а не на каждом событии. Расхождение с диском переводит запись в degraded и запускает сверку; внешние изменения не игнорируются. Статус берёт кэш с временем измерения, не запускает повторные полные обходы.
4. Реальный free-space проверяется перед каждым batch/выделением квоты; нельзя обещать свободное место по устаревшему кэшу. Резервирование должно учитывать конкурентный рост child, Node-бюджет отделён. Контроль файлов и отказ от ссылок сохраняются при открытии/ротации.
5. Сессия хранит immutable runtime view; её lock защищает только смену состояния и счётчики. DB, fs, control projection, fsync и ожидание writer выполняются вне lock, нужного producer. Публикация projection использует revision: устаревшая active-запись после stop не может вернуть подробный сбор. В Node lease остаётся 10 с с backend refresh каждые 5 с.
6. После writer barrier под коротким store lock фиксируются descriptors сегментов: внутренний ID, stream, identity, допустимая длина на границе полной записи, cutoff и TTL. Pin защищает backend-сегменты от физического удаления, но не продлевает право читать уже истёкшие данные. Чтение/JSON/filter/copy не держат store lock.
7. Child читает только зафиксированные префиксы backend-сегментов. Дописывание за пределами prefix допустимо; изменение/усечение самого prefix — ошибка. Frontend остаётся read-only источником: disappearance/rotation отмечаются gap, child никогда не удаляет его сегменты. Snapshot frontend учитывает identity, исходную длину, границы строк и TTL.
8. Child валидирует и фильтрует вход, раскладывает его в три нормализованных component-файла snapshot. В квоту входят только фактически выбранные данные и их разрешённый рост. Не резервировать весь исходный spool: узкий пакет при большой несвязанной истории должен оставаться возможным.
9. Квотами управляет родитель через ограниченный протокол grant/commit между процессами. Child до записи запрашивает кредит порциями до 64 КиБ; не пишет сверх него. Родитель держит outstanding credit в reservations, после подтверждения переводит фактический рост в used. При crash/kill освобождает кредит только после остановки child и сверки/очистки его файлов. Deadline worker — существующие 300 с, один builder. Инвентаризация не должна повторно считать committed и ещё reserved байты; для active child используются записи ledger и outstanding grants.
10. ZIP строится из трёх нормализованных файлов с хэшами/счётчиками, рассчитанными при подготовке. Не сканировать все входные файлы отдельно для каждого component. Сохранять обнаружение изменений исходного prefix, включая повреждённые строки и неизвестные форматы, и нормализованных файлов; CRC и финальный SHA остаются. Состав ZIP — прежние семь имён файлов, DEFLATE level 1.
11. Родитель один публикует ready, SQL audit, download metadata и rename. Убийство child, delete во время building, отказ аудита и shutdown не дают доступного ZIP и не оставляют вечные reservations/pins.

Отдельная экономия: `events/query` не должен создавать экспортный snapshot и копировать весь журнал ради 50 строк. Использовать ограниченное чтение pinned prefixes с фильтрацией и pagination. Просмотр остаётся аудируемым; аудит фиксируется до отдачи строк. В pagination неизменяемый cutoff, лимит 50 по умолчанию/100 максимум, offset по существующему контракту. Из-за TTL/rotation между страницами нельзя обещать вечный снимок; возвращать признак изменения покрытия, а не удерживать leases между HTTP-запросами.

### 5. Версии, данные сессии и совместимость

- Добавить SQL-поля `capture_level`, `policy_version`, `policy_snapshot`. Новые сессии явно пишут `standard|detailed`, `1`, ограниченный allowlisted snapshot. Для старых строк миграция выставляет `detailed`, `0`, `{}` — это прежний сбор с legacy sampling, не полная новая трассировка. ORM и новый API по умолчанию создают standard; SQL defaults остаются legacy-совместимыми для старого кода.
- Новая `SessionStart.capture_level` по умолчанию `standard`; неизвестный уровень — 422. `SessionOut`/status возвращают уровень, policy version, фактические счётчики и ограничения. Scope и минуты сохраняются.
- Добавить v2 schema для новых aggregate/outcome полей и событий. Readers принимают v1 и v2 с отдельными allowlists; writer новой версии пишет v2. Не ослаблять v1 валидатор. Общий corpus fixtures проверяет Python и Node. Запрет неизвестных полей сохраняется.
- Точный контракт новых событий: `operation_summary` = прежние базовые поля + `stage`, `duration_ms`, `counts`, `outcome` из `success|cancelled`; неуспех сохраняет прежний `operation_failed`. `success_aggregate` = базовые поля без request/operation ID + необязательные route/stage/dependency из allowlists + `outcome=success`, `window_start_utc`, `window_end_utc`, `counts`. В counts разрешить `count`, `duration_sum_us`, `duration_max_us`, `le_10ms`, `le_50ms`, `le_250ms`, `le_1000ms`, `le_5000ms`, `le_30000ms`, `gt_30000ms`; buckets непересекающиеся несмотря на верхнюю границу в имени. Все значения целые 0..10^12, сумма buckets равна count. При приближении к численному пределу досрочно выдать aggregate и начать новый, не переполнять/обрезать молча. Duration/outcome endpoint и proxy группируются раздельно по component.
- Manifest v2 добавляет `capture_policies`, `coverage_modes`, `counter_scopes` и `loss_counters_state`. Пакет по временному интервалу может включать несколько старых/новых сессий; не подписывать весь архив одним уровнем. Старые готовые ZIP не переписывать.
- Policy snapshot нужен и offline без БД: хранить безопасную копию policy в bounded control metadata, без пользователей/invitations. Активная сессия после restart не возобновляется. Потеря volatile счётчиков после crash обозначается `unknown_after_restart`, а не доказанной полнотой; metadata checkpoints не чаще раза в 5 с и при штатном stop.
- Control projection v2 содержит только разрешённые policy-поля. Новый frontend при v1/неизвестной версии не начинает новый подробный сбор, оставляет baseline и сообщает несовместимость. Старый frontend при v2 уже отвергает неизвестную schema; это проверить fixture. UI не отправляет новую форму, если backend capabilities не подтверждают уровни.
- При upgrade сначала writers/readers одной версии на тестовом стенде; mixed version обязан дать явное ограничение покрытия. Rollback — выключить capture/bundle/download, оставить cleanup; сохранить совместимые таблицы/файлы. Не откатывать на код, экспортирующий неизвестный v2 как полный или вновь включающий raw dumps.
