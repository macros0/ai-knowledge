# Сценарии ответа: проект изменения

Дата: 23.10.2026. Статус: согласовано и реализовано в ветке `codex/chat-answer-scenarios`. Фактические проверки, отклонения плана и ограничения: [отчёт приёмки](../reports/2026-10-23-chat-answer-scenarios-acceptance.md).

План реализации: [2026-10-23-chat-answer-scenarios.md](../plans/2026-10-23-chat-answer-scenarios.md).

## 1. Цель и согласованный объём

Пользователь сохраняет именованные инструкции подготовки **ответа** по найденным материалам и выбирает их в верхней панели режимов чата. Генерация, хранение и индексация концептов не меняются.

Согласовано:

- Новый режим «По сценарию» находится рядом с существующими переключателями режима ответа; рядом выбирается сценарий.
- Выбор применяется к следующим вопросам, пока пользователь его не изменит. Старые ответы не перестраиваются.
- Редактор содержит название, описание, инструкции, видимость, «Проверить» и «Сохранить».
- Видимость: «Личный» по умолчанию либо «Общий» для всех пользователей сервиса.
- Автор редактирует свой сценарий. Администратор может редактировать и удалять чужие общие сценарии; чужие личные ему недоступны. Остальные используют общий сценарий или создают личную копию.
- Снятие с публикации возвращает сценарий в личный доступ; существующие ответы сохраняются.
- Следующий запрос автоматически использует последнюю сохранённую версию. Уже запущенный запрос завершается с зафиксированной при старте версией.
- Каждый ответ сохраняет название, номер версии и точный текст применённых инструкций.
- Требования к достоверности, источникам и доступу к документам обязательны для любого сценария.

Критерий пользы: сценарий повторно используется для реальной рабочей задачи и уменьшает количество правок ответа. В первую версию не входит отдельная система аналитики использования.

## 2. Проверенная исходная архитектура

На момент подготовки плана:

- `frontend/src/components/ChatPanel.jsx` выводит режимы из `settings.response_modes`; состояние хранится в `frontend/src/context/ChatContext.js`.
- `ChatRequest`/`ChatResponse` в `backend/app/models/schemas.py` допускают `documents`, `fast`, `full` и legacy `null`.
- `backend/app/api/chat.py` содержит поиск, проверку источников, ответ по выбранным фрагментам и запуск LLM. `_answer_mode` использует отдельные direct/map/reduce/synthesis-пути.
- Полный ответ по нескольким пакетам использует `_FACT_INSTRUCTIONS`, `_REDUCE_INSTRUCTIONS`, `_SYNTHESIS_INSTRUCTIONS`; простое добавление текста в `_chat_system_prompt` не покроет этот путь.
- Вопросы об авторстве имеют отдельную проверку оригинальных свидетельств и детерминированную сборку ответа.
- `backend/app/services/chat_history.py` сохраняет `answer_attempt` и канонические `source_blocks` в `ChatMessage.retrieval_metadata`. Это подходящее место для независимого снимка сценария.
- Ответ по выбранным источникам разрешён только в `full`; allowlist есть и в backend, и в `chatSourceSelection.mjs`. Требуется согласованное расширение.
- Транспорт — NDJSON (`chat_stream.py`, `chatStream.mjs`), а не SSE. В нём есть события start/progress/sources/delta/result/error.
- `require_user` при выключенной аутентификации возвращает общий `anonymous`: это не отдельная личность пользователя.
- У проекта есть обязательные RU/EN-переводы, генерируемые UI-манифесты, каталог событий аудита и существующие правила истории/доступа.

## 3. Предлагаемые границы первой версии

Рекомендуется отдельный режим `scenario`, который использует механизм **полного исследования**: один проход, если контекст помещается, иначе обработку пакетами. Не добавлять второй переключатель скорости внутри сценария. Глубина поиска и фильтры остаются пользовательскими настройками.

Сценарий меняет задачу анализа и представление ответа, но не расширяет автоматически поисковую область. Инструкция «все противоречия документа» относится только к реально обработанным источникам. Интерфейс сохраняет ограничения глубины и сведения об охвате.

В первой версии отсутствуют: несколько одновременно активных сценариев, выполнение кода/инструментов, внешние API, переменные шаблонов, вложения в сценарий, адресный обмен, каталог с рейтингами, импорт/экспорт, откат редактора к старой версии. Текст инструкций передаётся буквально, без `format`, Jinja или исполнения Markdown/HTML.

Удаление предлагается физическое для записи сценария и его версий, с подтверждением в редакторе. Уже записанные снимки в истории независимы и сохраняются по существующей политике истории. Копии у других пользователей также остаются независимыми.

## 4. Поведение интерфейса

### Верхняя панель

Ряд: «Документы» / «Быстрый ответ» / «Полное исследование» / **«По сценарию»**.

В режиме сценария показывается компактный выбор: название, автор, текущая известная версия; рядом действие «Сценарии». Список содержит группы «Мои» и «Общие» и действие «Создать сценарий». Собственный опубликованный сценарий показывается один раз в «Мои», с признаком «Общий».

- Пока сценарий не выбран, отправка заблокирована с подсказкой «Выберите или создайте сценарий».
- Переключение на другой режим сохраняет выбор, но не передаёт `scenario_id` в обычный запрос.
- Загрузка списка и фоновое обновление не сбрасывают выбор, черновик вопроса и настройки поиска.
- Если сценарий удалён или перестал быть доступен, выбор помечается недоступным. Пользователь выбирает другой; автоматического перехода к обычному ответу нет.
- При изменении автором выбранного сценария список может ещё показывать старую версию; фактически применённую версию всегда сообщает сервер.
- Состояние переживает перемонтирование вкладки в `ChatContext`. «Новый чат» сохраняет выбранные режим и сценарий по текущему правилу остальных переключателей. На выходе/смене пользователя очищаются сценарии и их кэш.
- Отдельное сохранение предпочтений между устройствами не добавляется. При восстановлении запроса из истории берётся ID его сценария, но новый запуск разрешает актуальную версию.
- На узком экране элементы переносятся; на ширине 360 px нет горизонтального переполнения страницы.

### Каталог и редактор

Каталог открывается модальным окном из верхней панели. Есть поиск по названию/описанию, «Мои»/«Общие», постраничная загрузка. У общего сценария видны автор и описание; текст можно просмотреть перед применением.

Редактор: название, описание, многострочные инструкции, переключатель «Личный / Общий», пробный вопрос, область пробного ответа, кнопки «Проверить», «Сохранить», «Отмена». Для существующего сценария — «Создать личную копию» и «Удалить» у автора; администратор может редактировать и удалять чужой общий сценарий. Для остальных чужой сценарий открывается для чтения и копирования.

Подсказка: «Сценарий задаёт способ подготовки ответа. Требования к достоверности и ссылкам на источники действуют всегда».

Возле публикации: «Название, описание и инструкции будут доступны всем пользователям сервиса. Копии и инструкции в ранее полученных ответах сохранятся после снятия с публикации».

Несохранённые правки не теряются при обновлении каталога или конфликте версии. При закрытии изменённого редактора предлагается сохранить либо отказаться от правок. Сохранение после конфликта не перезаписывает новую серверную версию: пользователь перечитывает её и повторно применяет свои изменения.

### Метка ответа и просмотр снимка

В текущей ленте, недавней и полной истории показывается «Сценарий: Разбор требований · v3». По нажатию открывается текст **снимка этого ответа**, а не текущий текст сценария.

Снимок есть и у остановленной/неудачной попытки, если сервер успел принять её. Старые сообщения без снимка отображаются как раньше. Административный просмотр истории сохраняет существующую read-only модель и аудит; нового доступа к личным сценариям через каталог администратору не даётся.

### Повтор и выбранные источники

- «Повторить» создаёт новую попытку с тем же ID сценария и последней доступной версией; это новый запрос, а не воспроизведение старой версии.
- Ответ по выбранным фрагментам из сценарного ответа сохраняет ID сценария, разрешает его актуальную версию и **не выполняет новый поиск**.
- Для выбранных фрагментов из обычного ответа текущий выбранный режим `scenario` применяется только при явно видимом выборе в панели; иначе сохраняется существующий `full`.
- «Найти источники заново» использует `documents` и удаляет `scenario_id` из параметров этого запроса.
- «Продолжить без оценки источников» сохраняет ID сценария, но заново разрешает актуальную версию; проверка прав и канонических фрагментов остаётся обязательной.

## 5. Права и жизненный цикл

| Действие | Автор | Другой аутентифицированный пользователь |
|---|---|---|
| Создать личный или общий сценарий | Да | Да, собственный |
| Читать/использовать личный | Да | Нет |
| Читать/использовать общий | Да | Да |
| Редактировать/публиковать/снять с публикации/удалить | Да | Администратор — только общий; остальные — нет |
| Сделать личную копию доступной текущей версии | Да | Да |
| Прочитать снимок в своей истории | По существующим правам истории | По существующим правам истории |

Создавать и публиковать могут все аутентифицированные пользователи, включая `viewer`: это новый явно документируемый класс пользовательских настроек, без прав изменения общего корпуса.

При `AUTH_PROVIDER=disabled` возможность недоступна: единый anonymous не обеспечивает личную видимость. Simulation с различными пользователями подходит для разработки и приёмки. Существующие режимы чата продолжают работать.

ID владельца берётся только из проверенной сессии. Чужие личные и удалённые сценарии возвращают одинаковый 404, включая подбор ID. Попытка изменить доступный чужой общий сценарий — 403. Права на документы проверяются независимо и не наследуются от автора сценария.

Резолюция актуальной версии и допуск к ней выполняются одной короткой транзакцией. При гонке с публикацией/удалением результат определяется порядком этой транзакции: допущенная попытка продолжает работу со снимком; все следующие проверяют новое состояние. Блокировки БД не удерживаются во время поиска или LLM.

## 6. Данные и версии

Две новые таблицы SQLAlchemy/Alembic:

**`answer_scenarios`**: `id` UUID-string PK; `owner_id` string(255), `owner_username` nullable string(255); `visibility` private/public; `current_version` positive integer; UTC `created_at`, `updated_at`. Индексы по владельцу и видимости/времени обновления.

**`answer_scenario_versions`**: составной PK `(scenario_id, version)`, FK на сценарий с CASCADE; `name` string(120), `description` text, `instructions` text, `instructions_sha256` string(64), `visibility` private/public как часть снимка сохранения, UTC `created_at`. Строки версий неизменяемы.

Лимиты API и UI после удаления краевых пробелов: название 1–120 символов; описание 0–1000; инструкции 1–12000. Внутренние переносы/пробелы инструкций сохраняются; хеш считается от сохранённой UTF-8 строки. Названия не уникальны; автор различает совпадения. Ограничения длины не заменяют проверку токенового бюджета.

Создание = версия 1. Изменение любого из четырёх полей (название, описание, инструкции, видимость) создаёт следующую версию атомарно. No-op не увеличивает версию. Обновление и удаление требуют `expected_version`; условный UPDATE/DELETE с проверкой числа затронутых строк обеспечивает одинаковый CAS-контракт в PostgreSQL и SQLite. Конкурирующий проигравший получает 409, без перезаписи и лишней версии.

Снимок `retrieval_metadata.scenario`:

```json
{
  "schema_version": 1,
  "id": "uuid",
  "version": 3,
  "name": "Разбор требований",
  "description": "Проверки и ограничения",
  "instructions": "Точный сохранённый текст...",
  "instructions_sha256": "sha256",
  "owner_id": "stable-user-id",
  "owner_username": "author"
}
```

Отдельно в metadata: `scenario_execution` с `status` (`accepted`, `applied`, `no_sources`, `assessment_rejected`, `protected_authorship`), фактическим ID модели и fingerprint набора системных шаблонов. `accepted` не утверждает, что LLM успела применить инструкции. Обычная ошибка/остановка остаётся в существующем `answer_attempt.status`.

Начальный снимок сохраняется в одной транзакции с placeholder попытки, до тяжёлой работы. Последующие checkpoint не могут заменить снимок. Он не имеет FK на каталог и переживает удаление сценария. Полный промпт с документами не сохраняется дополнительно; версия сценария не обещает побитовую воспроизводимость ответа LLM.

## 7. API

Новый префикс `/api/answer-scenarios`, в защищённом роутере:

| Метод и путь | Контракт |
|---|---|
| GET `/` | `scope=all\|mine\|public`, `q` до 200, `limit` 1–100 (50 по умолчанию), `offset>=0`; доступные summary без инструкций, total, стабильная сортировка updated_at desc + id |
| POST `/` | name, description, instructions, visibility (private по умолчанию); 201 и полная текущая версия |
| GET `/{id}` | Только доступная текущая версия, author/can_edit; Cache-Control: no-store |
| PUT `/{id}` | Полная форма + expected_version; новая текущая версия либо 409 `scenario_version_conflict` |
| DELETE `/{id}?expected_version=N` | Автор или администратор общего сценария, CAS; 204; снимки истории не меняются |
| POST `/{id}/copy` | expected_version; копия доступной текущей версии, private, новый владелец/ID, v1; 409 при изменении исходника |
| POST `/preview/stream` | Черновик + вопрос + текущие поисковые параметры; NDJSON, без записи в каталог/историю |

Статические маршруты объявляются до `/{id}`. Входные модели не принимают client-side owner/version snapshots; неизвестные управляющие поля отклоняются. Копия получает название исходника; пользователь может переименовать его, суффиксы не обязательны.

`ChatRequest`: `response_mode` дополняется `scenario`; `scenario_id: UUID | None`. Для `scenario` ID обязателен; для других режимов ID запрещён. Клиент не задаёт номер версии. `source_selection` разрешён с сессией для `full` и `scenario`, по-прежнему несовместим с `search_doc_ids`.

`ChatResponse` дополняется `scenario` и `scenario_execution`; обычные режимы возвращают null. История использует metadata. NDJSON передаёт зафиксированный снимок отдельным progress-событием `phase=scenario` сразу после start, до поиска; final result повторяет его. При ошибке/отмене UI сохраняет уже полученную метку. Не расширять transport-тип `AttemptRef` пользовательским текстом.

Настройки: `CHAT_SCENARIOS_ENABLED=true` (предлагаемый релизный default); `GET /settings` возвращает `scenarios_available`, а `scenario` входит в `response_modes` только при включённой функции и отдельной identity пользователя. При выключении endpoint каталога/preview и новый сценарный запрос отвечают 503 `scenarios_unavailable`. Исторические снимки доступны по прежним правам.

## 8. Подготовка ответа и промпты

Выделить небольшой модуль `chat_prompt_builder.py`; сценарий передаётся по аргументу как неизменяемый снимок, без изменения глобального PromptStore или общего экземпляра LLM.

Для сценария:

1. Системный слой содержит обязательные правила источников, цитирования, языка, точных значений ячеек, запрета необоснованных отрицаний и приписывания авторства. Скопировать эти положения из текущего `chat_system`, сохранив их смысл и тесты.
2. Пользовательский слой содержит отдельное поле `scenario_instructions`, вопрос и найденный контекст. Название/описание — метаданные UI; дополнительных инструкций из них не извлекать. Инструкции сценария подчинены обязательным системным правилам; документы остаются недоверенными данными.
3. Стандартные требования к форме («plain text and lists», дополнительный список источников в конце) для сценария заменяются его формой; обязательные inline `[N]` остаются. Без требования к форме использовать обычный читаемый Markdown. Язык вопроса и текущий locale-fallback сохраняются.
4. Для нескольких пакетов map учитывает задачу сценария при выборе фактов, но возвращает прежнюю проверяемую структуру фактов/цитат. Reduce сохраняет свидетельства и ID; сценарий не меняет контракт JSON. Synthesis получает сценарий вместе с проверенными фактами и обязательными правилами.
5. Проверки `fits` учитывают инструкции на каждом соответствующем проходе. Превышение бюджета не приводит к тихому обрезанию инструкций/источников или обычному ответу; возвращается понятная ошибка бюджета.
6. Разрешённые индексы ссылок и точные цитаты промежуточных фактов проверяются программно, как сейчас. Сам текст промпта не считается доказательством соблюдения правил моделью.

Существующий `chat_system` и его runtime override сохраняют путь обычных режимов. Новый обязательный слой — `backend/prompts/chat_scenario_core.md`, с зарегистрированным fallback и `{locale}` в PromptStore. Не менять runtime-файлы пользователя автоматически. Для сценарного режима не подключать произвольные настройки стиля `llm_local_chat_instructions`, которые могут противоречить выбранной форме; технические параметры модели остаются прежними.

Весь набор шаблонов сценарного запуска разрешается один раз до генерации и получает fingerprint; горячая правка шаблона не меняет уже идущие пакеты.

**Авторство:** в первой версии сохранить существующий защищённый алгоритм и детерминированный ответ. Для таких вопросов сценарий не переписывает доказанное авторство и форму ответа; `scenario_execution.status=protected_authorship`, видимая подсказка «Для проверки авторства применён проверяемый формат ответа». Это явно обозначенное ограничение v1, без скрытого обхода проверки ради форматирования.

## 9. Пробный ответ

«Проверить» работает с несохранённым черновиком: вопрос + name/description/instructions + копия текущих фильтров, области документов, глубины, glossary/mail/assessment/locale. Для формы без вопроса запуск недоступен. `session_id`, `source_selection` и `attempt_id` не принимаются: проверка не читает историю и не продолжает текущий ответ.

Предпросмотр использует тот же поиск, доступ к документам, построитель промптов, бюджет и обработчик ответа. Для него отключена только запись попытки/истории; сценарий помечается «Черновик», без вымышленного номера версии. Внутренний запрос поиска остаётся валидным `ChatRequest(response_mode='full')`; черновик передаётся отдельно доверенным параметром серверного orchestration. Публичный контракт обычного `scenario` с обязательным ID не обходится. Ответ preview имеет `preview=true`, `response_mode='scenario'`, `scenario=null`; обычные ответы имеют `preview=false`.

Один preview на редактор, отдельный AbortController, кнопка «Остановить». Закрытие/правка черновика отменяет текущий preview; запоздалые события прежнего запуска игнорируются. Предпросмотр не останавливает ответ основного чата и не меняет его сообщения, фильтры или ID сессии. Он расходует обычный лимит chat и тот же пул LLM, без обхода очереди и без двойного списания лимита.

Ошибка, отмена или отсутствие источников не создают версию/публикацию. Предупреждения и ссылки preview рендерятся штатными безопасными компонентами. Пробный ответ не сохраняется в историю; пользователь может повторить вопрос в основном чате после сохранения.

## 10. Аудит, миграция, включение и откат

Добавить события create/update/publish/unpublish/copy/delete. В audit только ID, actor, номера версий, видимость и ID исходника копии; без name/description/instructions, вопроса, ответа и текста документов. Следовать текущему API transactional audit/outbox и режимам хранения; при ошибке аудита не возвращать успех незафиксированной операции.

Изменения `SECURITY.md` обязательны: права администратора на чужие общие сценарии без доступа к личным, права viewer на собственные настройки, публикация, снимки в истории, снятие с публикации не отзывает копии, disabled identity, обработка инструкций, события аудита. Diagnostics не включают инструкции или черновики.

Миграция добавляет только две таблицы и индексы. Существующие сообщения не требуют backfill, Qdrant не требует реиндексации. Alembic revision создаётся от актуального head на момент реализации; текущая просмотренная цепочка включает `067b1c2d3e4f`, не фиксировать устаревший head вслепую.

Для dev-БД с отставшим Alembic — отдельный идемпотентный companion, проверяющий именно новые таблицы и индексы. Он не меняет `alembic_version` всей базы и не запускает общие миграции. Общая schema-функция используется Alembic и companion; несовместимая существующая схема даёт явную ошибку.

Перед применением к рабочей БД: резервная копия, проверка восстановления на отдельной БД, миграция, перезапуск backend, проверка входа и обычного чата. В задаче планирования эти действия не выполняются.

Операционный откат — `CHAT_SCENARIOS_ENABLED=false`; обычные режимы и просмотр истории работают, данные сохраняются. Откат на более старый бинарный релиз требует проверки чтения `scenario` metadata; предпочтителен флаг. Удаление таблиц/истории ради отката не выполнять.

## 11. Приёмка

- Два пользователя A/B: личный A недоступен B; опубликованный доступен; копия B личная и независимая.
- Viewer может создать/опубликовать свой сценарий, но не менять чужой. Подмена owner, ID версии и снимка отклоняется.
- Запрос стартовал с v1; автор сохранил v2; первый ответ и его история показывают v1, следующий — v2.
- Снятие с публикации/удаление запрещает новые запросы B, но не изменяет уже допущенную попытку, старые ответы и копии.
- Две вкладки редактора: устаревшее сохранение получает 409, пользовательский текст не теряется.
- Проверены single-pass, multi-pass с реальным synthesis, повтор, выбранные источники, продолжение без assessment, остановка и retained draft.
- Старые режимы и legacy запросы работают как раньше; история без сценариев читается.
- Preview не создаёт записей, использует те же источники/лимиты и не мешает текущему чату.
- RU/EN, клавиатура, focus trap, возврат фокуса, 360/768/1440 px; нет переполнения/потери выбора после переходов.
- На фактической настроенной модели сравнить обычный ответ и сценарии «Кратко», «Сравнение требований», «Тестовые проверки»: форма соблюдается, факты и ссылки проверены, вымышленных условий нет. Отдельно — конфликтующая инструкция, недостаточные источники и авторство. Мок-тесты не заменяют эту приёмку.

Результат этапа планирования: этот проект и связанный исполняемый план. Реализация, миграция рабочей БД, публикация изменений и коммиты не выполнены.
