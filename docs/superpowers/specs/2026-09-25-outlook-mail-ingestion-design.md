# Письма Outlook и вложенные письма: проект доработки

Дата: 25.09.2026. Статус на 26.09.2026: реализация и приёмка по согласованному плану продолжаются; завершение всей матрицы ещё не подтверждено. Раздел 2 описывает исходное состояние на дату проектирования, а фактические результаты — в отчёте приёмки.

## 1. Запрос и границы

Пользователь выбрал ручную загрузку выбранных писем и уточнил, что письма могут быть вложены в документы. Нужно искать содержание писем и их вложений вместе с остальной базой, сохраняя происхождение утверждений.

Обязательные сценарии первой поставки:

- самостоятельные EML и MSG;
- DOCX/XLSX/PDF с реальными вложенными EML/MSG, включая Outlook OLE-объекты;
- EML/MSG с DOCX/XLSX/PDF и другими письмами внутри;
- цепочка DOCX → MSG → XLSX;
- письмо в ячейке таблицы DOCX, повторные вхождения одного вложения;
- понятная частичная обработка повреждённых, зашифрованных, неподдерживаемых или слишком больших объектов.

В эту поставку не входят Microsoft Graph, подключение аккаунта, автоматическая синхронизация папок, PST/OST, Outlook COM, OCR скриншотов, расшифровка S/MIME/IRM и переход по внешним ссылкам. Текст вставленной переписки обрабатывается как текст документа, но не получает выдуманный Message-ID. Иконка письма без встроенных байтов не считается извлекаемым письмом. Обычные ZIP/RAR-вложения не становятся новым поддерживаемым форматом.

## 2. Проверенное исходное состояние

Проверено по текущему checkout, а не только по описанию проекта:

| Участок | Сейчас | Следствие |
|---|---|---|
| `doc-parser/src/docparser/parser.py`, `extensions.py` | DOCX/XLSX/PDF, общий `AttachmentBudget` | Включить EML/MSG в общий диспетчер |
| `embedded.py` | OLE распаковывается преимущественно в ZIP/PDF; только они рекурсивно разбираются | Простого добавления расширений недостаточно |
| `embedded.py` | Граница глубины проверяется после `unwrap_ole`; сохранение opaque-объектов не использует общий бюджет так же, как parsed payload | Проверять лимиты до затратной работы; унифицировать учёт |
| `docx_parser.py` | OLE обходится в основной ветке абзацев; в ветке таблиц обходятся комментарии и картинки | Покрыть OLE в ячейках и не удвоить обход вложенных таблиц |
| `markdown.py` | Есть диапазоны `from_attachment`, нет дерева источников | Нужны идентификатор источника и точные границы |
| `pipeline.py`, `attachment_store.py` | Сохранение вложений и финализация с чанками/концептами уже существуют | Расширять существующий жизненный цикл |
| `chunk_store.py` | Канонический текст чанков в SQL, Qdrant — поисковая проекция | Метаданные происхождения гидрировать из SQL |
| `source_evidence.py` | Проверенные диапазоны по каноническому тексту и его хешу | Не вычислять координаты по очищенной копии |
| `documents.py` | До admission уже есть разбор для проверки похожести | Защита и одинаковая версия парсера нужны и в preview |
| `UploadZone.jsx` | Разрешены только `.docx,.xlsx,.pdf` | Обновить выбор файлов, ошибки и тексты RU/EN |

В checkout есть посторонние staged-изменения, в том числе upload/deduplication. Реализация должна интегрироваться с их фактическим состоянием; этот проект не даёт разрешения на commit/push, создание ветки или удаление этих изменений.

## 3. Модель документа и происхождения

Один загруженный файл остаётся одним `Document`, единицей прав доступа, тегов, разработки, корзины и экспорта. Вложенные письма не создают самостоятельные документы автоматически.

Добавить таблицу `document_sources` для дерева объектов внутри документа:

- составной ключ `(doc_id, source_id)`; `source_id` — детерминированный идентификатор вхождения, root=`root`;
- `parent_source_id`, `ordinal`, `kind` (`document`, `mail`, `attachment`, `image`), `display_name`, `media_type`;
- `saved_path` nullable, `container_source_id` nullable и `container_locator` nullable для MSG substorage;
- `metadata` JSON: тема, отправитель, To/Cc, исходная дата, нормализованное UTC-время или null, Message-ID, In-Reply-To, References, класс MSG;
- `content_fingerprint`, `extraction_status`, `warnings` JSON, `parser_version`;
- `artifact_kind`: `original`, `extracted_original`, `derived`, `container_only`.

Идентификатор ребёнка строить из пути структурного вхождения (родитель + ordinal), а не из темы, абсолютного пути или случайного временного имени. Хеш содержимого хранится отдельно: две одинаковые копии в разных местах имеют два источника.

Для существующей таблицы `okf_attachments` добавить nullable `source_id`. Записи источников без собственного файла сохраняются в `document_sources`, даже если их нельзя добавить в нынешнюю плоскую таблицу вложений.

Для `document_chunks` добавить nullable `source_id`. Новые чанки никогда не пересекают границу источника; старые чанки с null отображаются прежним способом. Письмо, процитированная внутри него история и его файловые вложения не смешиваются в один безымянный источник.

Для `documents` добавить nullable `parse_warnings` JSON и `parser_version`. Все изменения схемы additive; автоматическое переизвлечение старого корпуса не выполняется.

## 4. Контракт парсинга

Сохранить `parse_document(...) -> list[Block]` для существующих потребителей. Добавить `parse_document_result(...) -> ParseResult`, который возвращает `blocks`, `sources`, `warnings`, `parser_version`. Старый API делегирует новому и возвращает `.blocks`.

Один `ParseContext` содержит текущий `source_id`, depth и общий бюджет. Все рекурсивные вызовы передают его дальше. В `Block.meta` добавляется `source_id`; совместимые `from_attachment`/`attachment_name` сохраняются.

EML: стандартная библиотека Python `email`, явная `policy`, MIME-разбор и диагностика `defects`. MSG: адаптер с проверенным поведением на Unicode/ANSI, embedded-message substorage, HTML/plain/RTF и вложениях. Выбор готового MSG backend закрывается ранним техническим и лицензионным gate в плане. Нельзя просто включить расширение до прохождения этого gate.

Проект `extract-msg` проверен как кандидат: его текущий `LICENSE.txt` — GPL-3.0. Это факт о зависимости, не заключение о допустимости её поставки в данном продукте. Не добавлять её автоматически в MIT-проект и production image. Базовый резервный путь — ограниченный собственный MSG-reader на уже используемом `olefile`, реализованный по MS-OXMSG; нельзя копировать GPL-реализацию в такой reader. Если готовый backend не выбран, этот путь требует отдельной оценки трудоёмкости в этапе 1 и тех же приёмочных тестов.

Вложенный MSG substorage не является готовым самостоятельным MSG-файлом. Сохранять исходный контейнер и locator; не выдавать реконструированное письмо за побайтовый оригинал. Кнопка скачивания для такого узла ведёт к ближайшему сохранённому контейнеру с понятной подписью. Отдельный экспорт substorage в MSG/EML не обязателен для первой поставки.

## 5. Текст и семантика письма

- Сохранять оригинальные байты корневого файла; нормализованный Markdown — производная.
- Для MIME alternative выбирать одно представление тела, сохраняя таблицы и ссылки HTML. Не индексировать plain и HTML дважды. При расхождении, которое может скрыть смысл, сохранять диагностику и доступ к оригиналу.
- HTML преобразовывать офлайн в безопасный Markdown. Не загружать remote images/CSS/fonts, не исполнять скрипты, не выводить raw HTML. `cid:` разрешать только в локальные вложения того же письма.
- Не вырезать цитируемую историю и подписи эвристикой. В первой версии явно обозначать историю только при уверенном распознавании; иначе сохранять полный текст. Ответ «Согласовано» обязан остаться рядом с цитируемым предметом согласования.
- Скопированный текст старого письма не получает достоверную атрибуцию только по строке `From:`. Помечать как цитату внутри текущего источника.
- Не считать более позднее письмо автоматически утверждённой заменой предыдущего. Текст письма — источник данных, а не инструкция для приложения/LLM.
- Отсутствующая/невалидная дата остаётся неизвестной; не подставлять время загрузки. Exchange EX-адрес сохранять как есть, не выдумывать SMTP-адрес.
- Bcc, скрытые transport headers и технические идентификаторы не отправлять в LLM и не индексировать по умолчанию. Оригинал по-прежнему может их содержать; это отражается в правилах доступа и загрузки.

Отправитель письма — отправитель контейнера, а не автоматически автор вложенного XLSX или автор каждой цитаты. В UI и RAG эти роли подписывать раздельно. Таблицы и ссылки HTML нормализуются без изменения содержательных чисел/дат; ошибку декодирования нельзя скрывать за неотмеченным replacement character.

## 6. Лимиты и обработка ошибок

Начальные проектные значения, которые проверяются нагрузочными тестами до включения:

| Ограничение | Значение |
|---|---:|
| Корневой файл | действующий `max_upload_mb`, не увеличивать |
| Вложение | 50 MiB |
| Суммарные декодированные вложения на корень | 200 MiB |
| Глубина | корень 0; уровни 1–2 разбираются; 3+ явно пропускаются |
| MIME/MSG nodes, включая inline и сообщения | 1000 на корень |
| Заголовки одной MIME-части до декодирования | 64 KiB |
| Структурная глубина multipart внутри письма | 32 уровня, корень включён |
| Декодируемое тело одного письма | 50 MiB, проверка верхней границы до декодирования |
| Суммарный нормализованный текст | 2 000 000 Unicode-символов на корень |
| Выполнение parse/preview в дочернем процессе | 120 секунд |
| Память дочернего процесса | 1024 MiB |
| Одновременный parse/preview | 2 процесса на backend |

Существующие `ArchiveLimits` не ослаблять. Новые общие ограничения применять и к неизвестным, и к inline-вложениям. Проверять declared size до чтения, фактический размер — во время чтения/декодирования. Счётчик node используется отдельно от depth: 1000 tiny-вложений нельзя обойти нулевым размером. Повторное появление тех же байтов в другом месте тоже потребляет бюджет; цикл на текущем пути не раскрывать.

MIME-счётчик включает body и multipart containers, а не только attachments.
При исчерпании оставшиеся неразобранные siblings получают один общий marker.
Структурная глубина MIME не заменяет общую глубину вложений 0–2.
Вложенное `message/rfc822` извлекается из исходного диапазона байтов с учётом
transfer encoding, без повторной сериализации заголовков и тела. Ошибка
структуры корневого multipart или превышение лимита его заголовка/тела
отклоняют корень; повреждение дочерней части оставляет диагностику и соседей.

Лимит глубины прекращает интерпретацию объекта, но позволяет сохранить сам объект, если хватает byte/disk budget. При запрете сохранения оставить запись о пропуске и доступ к корневому оригиналу. Нельзя одновременно обещать сохранение всех вложений и соблюдать общий лимит.

Parse supervisor обслуживает оба пути (upload preview и background processing) и завершает зависший процесс, а не только ожидание `Future`. На Windows использовать Job Object для лимита памяти/cleanup, на Linux — процессные лимиты и окружение контейнера; отказ установки лимита должен быть видимым, без молчаливого запуска без защиты.

При повреждении одного вложения продолжить обработку соседних. Ошибка разбора корневого письма до admission → 422 со стабильным кодом без ghost document. Таймаут/лимит worker → отдельный диагностический код. Пропущенное вложение при успешном основном тексте → `done` с предупреждением. Диск заполнен/БД недоступна/индекс не готов → существующая инфраструктурная обработка, не `done`.

Список `parse_warnings` хранит все причины. Новый summary-code `attachment_partial_result` не должен затереть `index_partial_failure` или LLM degradation; приоритет отображения: index failure → LLM salvage → extraction partial → classifier fallback → no_concepts/no_text_layer. UI показывает полный список независимо от summary. Метаданные письма сами по себе не являются текстовым слоем: пустое тело + скан-вложение нельзя сделать «текстовым» за счёт From/Subject.

Статусы передаются структурированно: `parsed`, `saved`, `unsupported`, `skipped_depth`, `skipped_size`, `skipped_count`, `skipped_text`, `parse_failed`, `encrypted`, `disabled`. Код не определяется по русскому тексту `note`. Вложение `saved` без ошибки означает доступные bytes, но не успешное извлечение текста.

## 7. Дедупликация и поиск

SHA-256 исходного файла остаётся точным дублем. Для EML/MSG semantic fingerprint включает нормализованные отправителя/получателей/дату/тему, полное тело и отсортированный набор хешей вложений с кратностью. Message-ID — сигнал, но не уникальный ключ: одинаковый ID с другим содержимым не удалять.

Совпадение разных форматов показывать как вероятный дубль в существующем upload-review; не блокировать исключительно по семантическому хешу. Вложенное письмо, повторяющее отдельно загруженное, не лишает родительский документ своего содержимого и происхождения. Глобальное объединение/скрытие писем из разных документов в первой версии не включать.

Генерировать концепты отдельно по источникам. Сохранять порядок программных экстракторов комментарии → таблицы → LLM. В RAG добавлять сервером проверенную цепочку происхождения и дату рядом с номером источника `[N]`. Разделять название root-документа и тему письма. Не индексировать длинный блок технических заголовков. `source_spans` остаются только проверенными дословными диапазонами канонического `DocumentChunk.content`; лексически найденный абзац не записывается как точное доказательство. При чтении его можно показать со статусом `inferred` («Предполагаемый абзац»), а неоднозначное или неподтверждённое совпадение даёт переход к чанку без точной подсветки.

## 8. UI, доступ и эксплуатация

Добавить `.eml,.msg` в обычную загрузку. Прямой drag-and-drop из Outlook в браузер не обещать: основной воспроизводимый путь — сохранённые файлы. В карточке документа показывать дерево источников, почтовые метаданные, статус каждого вложения и путь источника в результатах поиска/чата.

Вложения наследуют эффективную видимость root-документа; почтовые адресаты не становятся ACL. Пользователь подтвердил общую видимость загружаемых документов и исключил отдельное предупреждение/подтверждение этого факта из задачи. Личные почтовые ACL не входят в эту поставку. Локальный `MAIL_IMPORT_ENABLED=true` сохраняется по указанию пользователя; default false до приёмки относится к production.

Проверять права и trash-state на новом source API и на прямом backend download, не полагаться только на frontend proxy. Скачать вложение можно только по зарегистрированному source_id/root, а не произвольному пути. HTML/SVG/письма отдавать как attachment + nosniff. Логи содержат doc_id/source_id/код/размер/время, но не тело, адреса или raw headers.

Новые поля мигрировать на PostgreSQL и SQLite. При dev-drift `create_all` не заменяет миграцию: сначала сравнить реальную схему с Alembic, подготовить адресную совместимую процедуру. Перегенерация обновляет дерево, чанки и вложения одной согласованной версией; resume запрещает смешивать parser_version и старые чанки. Backup/restore и purge включают всё дерево. Bulk raw export продолжает отдавать только загруженные оригиналы, которые уже содержат вложения.

## 9. Проверяемый результат

Приёмочный пример: из DOCX извлекается MSG с темой/автором/датой и его XLSX; запрос о значении из XLSX возвращает значение и цепочку DOCX → MSG → XLSX. Переход открывает правильный канонический фрагмент. Повторная обработка не множит объекты. Повреждённое второе письмо не уничтожает первое и не скрывает предупреждение. Все детали проверяются по матрице в плане.
