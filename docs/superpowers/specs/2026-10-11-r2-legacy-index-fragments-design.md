Дата: 11.10.2026. Статус: **G0 native/решение о хранении проверены; корректировки G1/G2a проверены, G2b validation реализована; интеграция и приёмка ещё не выполнены**.
Основной проект: [R2](2026-10-09-table-processing-design.md); последовательность работ: [G0–G6 основного плана](../plans/2026-10-09-table-processing.md#r2-g-производные-индексные-фрагменты).

## Основание и границы доказательств

Полная проверка 3505 legacy inputs на Windows Ollama/bge-m3 при context4096/physical4096/truncate=false: 3503 приняты, два source chunk inputs отклонены HTTP400 context. Все 3380 concept inputs приняты. Chunk13: 7798 символов/209 содержательных pipe rows; существующая компактизация не помогает. Chunk118: полный source 2379735 символов → compact 4780 символов; только этот compact input проверен native: HTTP200, 1858 tokens, 1024 dimensions. Source/checkpoint bytes не изменены.

Первоначальный бюджет2000bytes был гипотезой. G0 ниже проверил все3030 parts реального A, включая оба проблемных источника; G1 воспроизводит их inputs точно. Это не универсальная token guarantee для будущих документов/моделей. Ни оценки символов/байтов, ни успешный compact chunk118 сами по себе не заменяют полный native audit. Подробные артефакты остаются в `data/table-eval/r2/continuation-20261010-warm-memory/pve-environment-v1` (P).

Цель: сохранить полный canonical source, source_id/generation/chunk_index, концепты, физические повторения и checkpoints, подготовив допустимые provider inputs. Общий механизм обычных чанков применяется одинаково при table_structure_enabled=false/true; TableRef сохраняет отдельный действующий маршрут. Проект закрывает chunk inputs; успешные concept inputs документа A не доказывают универсальную безопасность всех будущих concept inputs.

Не входят truncate, уменьшение общего текста, увеличение контекста, усреднение векторов, новое разбиение до LLM, массовая миграция корпуса, commit/push/main merge/deploy. API документов и процесс загрузки предполагаются прежними. **Неизменность SQL-схемы больше не обещается:** нужен доверенный признак версии проекции, связанный с поколением.

## Решение G0, 11.10.2026

Проверено 125 canonical chunks/250 checkpoint files: 3030 производных inputs, все приняты native Windows Ollama в48 batches за60,92s при прежних context4096/physical4096/truncate=false/timeout30/retry1/batch64. Полный source/title coverage и порядок meaningful pipe-row signatures сохранены, включая повторы. Chunk13 даёт7 parts, chunk118 —5; максимальный fan-out1151 (chunk110). Исходные5 052 667chars → projected body2 641 552chars. Это частный полный аудит A, не универсальная token guarantee. Budget проверяет max(original UTF-8 bytes,NFKC UTF-8 bytes), максимум2000. Title hint128bytes/header hint384bytes; полные title/body сохранены в именованных диапазонах. Новые fragments не переписывают canonical chunks.

**Выбран материализованный SQL store по поколению.** На приватном PostgreSQL warm replay chunk118 стоит219,86ms/50,65MB peak Python allocations; chunk110 last152,59ms/15,50MB; четыре synthetic sources814,48ms/46,79MB. Чтение готовых parts для тех же случаев0,064/0,080/0,297ms и12,7/13,8/37,0KB allocations. Это достаточно для отклонения полного replay в горячем поиске при прежнем историческом p95 около40ms. Эти paired microbenchmarks не являются qualified C/RSS; first request сделан в той же session, cold OS/storage не проверялся. Process lifetime high-water после подготовки таблиц не является peak запроса. G0 cold/RSS/index-volume acceptance остаётся частью integrated G4/G6.

Добавить `DocumentChunkProjection` с PK(doc_id,generation_id,chunk_index), source_id, raw content/title/projection hashes, version и expected count; `DocumentChunkFragment` с FK на этот parent, ordinal, representation/descriptor/hashes. FK generation обеспечивает cleanup. Nullable generation.chunk_projection_version остаётся доверенным переключателем. Canonical DocumentChunk.content_hash и source/title сверяются с parent в active/ACL snapshot без чтения полного content. Candidate writer и publication вычисляют/проверяют проекцию по полному source; reader выбирает ограниченные rows из доверенной SQL projection и сверяет point ID/descriptor/text hash. Qdrant остаётся slim и не задаёт текст. Полное воспроизведение используется при подготовке/публикации/repair, не на каждом поисковом запросе.

После исправления G2a bound parent обязателен для каждого generic chunk, включая unchanged short: complete=true/count0/без fragment rows означает проверенный legacy root внутри marker1. Отсутствие parent не разрешает fallback. Identity source/title/body неизменна при resume и для short input. Store rows доступны лишь при согласованном поколении, версии и complete parent; source scope/ACL/trash проверяются до текста. Неполные candidate rows не публикуются. В новом формате обязательный canonical content_hash создаётся из полного source в publication; sanctioned canonical replacement меняет hash/поколение. Генерируемый portable artifact позволяет восстановить materialized store после backup/import; source-only восстановление возможно лишь через проверенный projector той же поддерживаемой version. SQL models/store и migration061 реализованы; SQLite и изолированная PostgreSQL schema проверены. Ready/publication validation нового marker теперь реализована и проверяется на synthetic candidates. Обычный Pipeline/retrieval ещё не подключён; рабочая БД/корпус не мигрированы.

Proof: P/g0-fragment-feasibility-v1/decision.json. История ошибочного guard диагностического benchmark v1 сохранена: он ожидал r2_lab вместо фактической приватной r2_d2_a_1_warm_baseline_v1; отказ до любых TEMP writes. v2 завершён, actual CT SHA трёх полученных artifacts совпали. ## Выбор хранения и ранняя проверка осуществимости (рассмотренная гипотеза)

Первоначальный кандидат, отклонённый G0 для горячего поиска: производные точки плюс детерминированное воспроизведение из canonical chunk. Для доверенного выбора алгоритма предлагается nullable `DocumentGeneration.chunk_projection_version` (точное имя миграции определить по актуальному Alembic head). NULL означает старый контракт, поддерживаемая версия — фиксированные правила. Это проект изменения схемы, не выполненная миграция.

Version назначается candidate при подготовке, включается в hashed publication и проверяется при публикации; active pointer, canonical rows и доверенный маркер становятся видимы в одной транзакции. На запросе версия читается вместе с active-generation/ACL snapshot из SQL. `table_schema_version` не переиспользуется. Неизвестная версия не трактуется как NULL. Старые ready manifests без маркера продолжают прежний маршрут.

Нельзя вызывать `load_verified_publication` на каждом поиске: он читает manifest и проверяет дерево артефактов. Нельзя брать разрешённую версию, budget или offsets только из Qdrant payload. Совпадение вычисленного ID с payload не заменяет проверку того, что generation разрешает этот контракт.

G0 сначала проверяет цену повторного построения проекции: chunk118, содержательный chunk13, большой некомпактируемый текст и несколько разных больших chunks в одном запросе; cold/warm чтение, несколько parts одного chunk, время SQL/нормализации/выбора частей, RSS, количество points и индексный объём. Request-local reuse не устраняет цену одного большого source или многих разных sources. Сравнение с текущим bounded SQL path записывается до реализации интеграции; итоговые p95≤1,15/RSS≤1,20 и нагрузочные guards не меняются.

Если воспроизведение делает эти границы недостижимыми, остановить интеграцию и рассмотреть доверенное материализованное хранилище проекций с generation lifecycle, backup/import/cleanup. Новые SQL rows нельзя заранее объявлять избыточными. В G0 фиксируются выбранное хранение, версия, точные правила и измеренные издержки; до этого G1–G6 условны. Изменение source chunks до LLM исключено: ломает resume и распределение концептов.

## Контракт проекции и идентичности

`DocumentChunk.content`, content_hash, source_id, chunk_index, сохранённые chunk_XX.md и концепты не меняются. Projector получает полный title/content и доверенную version. Полные прямоугольные Markdown-таблицы компактизируются до любого cap/разбиения: удаляется только непрерывный полностью пустой правый хвост колонок после проверки всех строк. Внутренние пустоты, 0/False, повторные строки и заполненная последняя строка сохраняются. Code fences/ragged/неоднозначные таблицы не компактизируются.

Новый маршрут индексирует полную полученную проекцию. Это **явное расширение покрытия поиска за прежние 8000 символов**, а не только оптимизация памяти; canonical source oracle сохраняется, index oracle меняется. Короткий input без преобразования и разбиения сохраняет прежний ID/представление. Критерий короткого input включает полный title, content и служебные разделители. Старые поколения не получают новое покрытие автоматически.

Подтверждённый G0 на корпусе A бюджет version1: до2000bytes по max(original UTF-8,NFKC UTF-8) окончательной строки provider, включая разделители и повторяемые подсказки; байты не называются exact tokens. Никаких индивидуально подобранных caps для проблемных chunks. Отказ provider сохраняет ошибку/paused и отсутствие публикации; не запускает скрытый truncate или непроверенный новый алгоритм.

Полный title и body покрываются отдельными именованными диапазонами. Границы — half-open offsets в Unicode code points соответствующей нормализованной строки, а budget — UTF-8 bytes. Повторяемые title/header подсказки описываются отдельно и не считаются повторным покрытием данных. При удалении пустых колонок offsets проекции не выдаются за offsets оригинального Markdown.

Строки/абзацы сохраняются целиком, когда помещаются. Для чрезмерно длинной строки/ячейки/заголовка нужны детерминированные continuation parts без потерь Unicode и без выдачи обрывка за полноценную строку таблицы. Перед G1 G0 фиксирует алгоритм header/title reserve и continuation на примерах, включая шапку, которая сама превышает budget. Generic Markdown не получает выдуманные TableRef/Excel coordinates.

Identity части включает doc/generation/source/original chunk_index, version, ordinal, digest полного title и canonical content, digest нормализованной проекции и фактического fragment representation. Point ID вычисляется из этой идентичности. Изменение title тоже инвалидирует часть. Payload содержит проверяемый descriptor, но не задаёт параметры вычисления. Dense и sparse используют один fragment representation; не добавляют полный title повторно после проверки budget. Разные позиции одинакового текста остаются разными parts.

Projector выдаёт iterator; embedding/upsert удерживает один ограниченный batch. Это не обещание постоянной общей памяти: полный source, нормализованная копия, parser/строки и expected ID set отдельно входят в измерения. Не создавать списки всех fragment texts/vectors. Для преобразованного chunk root point не добавляется поверх набора частей; TableRef route не смешивается с generic route.

## Публикация, продолжение и обслуживание

Expected IDs/descriptors/scopes выводятся из canonical подготовленных chunks и доверенной version. Перед active switch проверить их уникальность, полноту, point_type, doc/generation/source/chunk identity и hashes. Проверить фактический набор candidate points; существующий retrieve по ожидаемым IDs сам по себе не обнаруживает лишние точки. Bounded validation не загружает все vectors; криптографическая проверка содержимого векторов здесь не заявляется.

Marker нового формата требует полного набора объявленных chunk parts; старый допустимый concept-only/legacy manifest проверяется по прежним правилам. Частичная новая индексация не публикуется под видом старого формата. Candidate orphan cleanup возможен только по его generation и полному keep set, после завершения индексации; далее повторная проверка. Старый active остаётся доступен при сбое, отмене или конфликте. Повтор той же попытки получает те же IDs/version, включая resume между upsert и publication.

Изменение projection version, разбиения или полного индексного представления, в том числе явный reindex, создаёт новый candidate generation. Восстановление missing dense/sparse points активного поколения допускается только идемпотентно в рамках уже опубликованной версии. Startup backfill не должен создать legacy root поверх fragment points. NULL-поколения автоматически не переводятся в новый формат.

Fresh indexing, repair, chunk backfill, sparse rebuild/backfill и portable export/import используют единые projector/ID rules. Экспорт сохраняет доверенную version и canonical inputs; импорт проверяет поддержку и восстанавливает точки для своей generation. Backup/restore сохраняет marker вместе с generation. Downgrade неизвестной версии запрещён. Теги, trash, delete и source scopes проверяются на всех частях. SQL migration и обновление корпуса — отдельные операции; rollback к reader без поддержки опубликованной новой version не объявляется безопасным.

## Поиск, цитирование и snapshots

В одном авторитетном snapshot проверяются ACL/trash/source/mail/active generation и разрешённая version; затем canonical source/content_hash/title и generation-scoped SQL projection rows. Проверяется согласованность parent/part ID/descriptor/text; неверный hash, unknown version, чужой source/generation или part вне диапазона исключает hit без fallback на payload text. Legacy hits сохраняют bounded SQL path. Generic parts не пропускаются из-за нескольких концептов в исходной группе.

Предлагаемое однозначное правило merge: обычные concept/review блоки сохраняют текущую группировку; каждый distinct generic fragment — отдельный chunk block со своим section/source title и собственным score/evidence. Произвольный концепт всего chunk не присваивается одному фрагменту. Dense/sparse duplicate одной point схлопывается; одинаковый текст разных ordinal не схлопывается. TableRef и legacy grouping остаются прежними.

Дальнейшие глобальная сортировка, top_k, exact-title/lexical filters остаются явными политиками отбора. «Сохранить distinct parts» означает не терять их в identity/merge; это не иммунитет от лимита top_k. До release проверить релевантные parts в single/multi-concept, exact-title, body-match и mail запросах: нельзя объявлять потерю из-за несовместимого фильтра нормой. Менять ranking/filter политику без отдельного доказательства необходимости не входит.

Подтверждённая G4 fan-out потеря: по общей шапке1151части вытесняют соседний chunk/document до SQL hydration (RED2/6 на Windows и actual Qdrant). Поэтому fragment payload получает `chunk_fragment_group`, SHA от doc/generation/source/chunk; публикация сверяет его с canonical identity. Каждая branch сначала делает прежний bounded query; если в нём есть generic parts, grouped query берёт одного лидера на исходный chunk, отдельный bounded query — обычные точки. Лидеры сортируются по score, затем свободные места занимают дополнительные distinct parts первоначальной выдачи. Возвращается максимум прежних40кандидатов; RRF weights/final top5 и downstream filters прежние. Legacy query без parts сохраняет один запрос. Стоимость до трёх Qdrant calls для parts и возможная демоция дополнительных частей требуют новой qualified C/RSS/native quality проверки. Отсутствие group у прежних isolated parts сохраняет чтение, но не считается доказательством diversity: G5 обязан восстановить metadata перед default activation. Тексты/ID/version не меняются.

`excerpt_reference`, `snapshot_blocks`, `_key`, `restore_blocks` требуют версии fragment evidence. Key включает generation/source/part identity, а excerpt offsets относятся к воспроизведённому fragment representation. При restore заново проверить доступ/active version/source hashes, загрузить проверенную materialized часть и проверить excerpt digest; Нельзя использовать `.find()` в raw source для compact/repeated-header текста или схлопывать несколько частей по одному chunk_index. Старые snapshots продолжают прежний путь; смена поколения/невалидная часть даёт существующий 409, а не текст из другого источника.

Citation содержит только canonical-derived fragment text. Ссылка открывает полный original source/chunk; точные исходные offsets/подсветка после компактизации не обещаются. В интерфейс не выводятся технические version/ordinal; snapshot хранит идентичность и достаточные проверяемые сведения для восстановления выбранного текста.

## Приёмка и статус

G0 — доказательство осуществимости, не приёмка R2. Затем RED→GREEN по G1–G5: coverage/order/duplicates/Unicode, publication corruption/crash/resume, retrieval/mail/ACL/citation/snapshot, maintenance/portable parity, bounded memory. Синтетические fixtures в git, частные документы и native результаты — только в P.

Перед G6 — новый общий app/profile/freeze для обеих flags, native full chunk projection audit A и untouched concept-input provenance, новый source/index oracle, qualified C, четыре fresh D2 стороны и E/060 disk-contention. Legacy canonical125 chunks сохраняются, но point count и полнота индексируемого текста считаются заново; сравнение flags не является сравнением со старым appv9. Все historical failed/invalid результаты сохраняются. Пороги p95 ratio≤1,15 и warm/cold RSS ratio≤1,20, load/coverage guards остаются прежними.

G0 и прежнее покрытие G1/G2a подтверждены; review выявил ложные header hints внутри fenced/indented code и отсутствие short-input resume binding. Источник не обрезается, но synthetic примеры получают2/3 ложные подсказки; изменённый short retry принят. Доказательство: P/g0-fragment-feasibility-v1/review-g1-g2-v1.json. Исправления G1/G2a предшествуют G2b publication и G3–G5. Header detection должен исключать code/ambiguous spans по тем же консервативным правилам, что compactor; новый input hash требует нового native proof.

Формат включается только после общей проверки publication/Pipeline/resume/readers/snapshots/restart/backfill/portable.
