## Цель и порядок поставки

Сначала обеспечить работоспособную установку текущего приложения в Kubernetes целевой платформы. Затем по отдельным этапам устранить ограничения архитектуры и разрешить независимые реплики frontend, backend API и обработчиков документов. Проверять каждый этап в домашней инфраструктуре до поставки в целевой контур.

Локальные `scripts/start-all.ps1` / `scripts/start-all.sh` и Docker Compose с режимами `bundled` и `external` сохраняются. Kubernetes становится дополнительным способом запуска того же продукта и тех же образов.

Первая поставка не зависит от реализации распределённой очереди, Redis, S3, нескольких backend или автоматического масштабирования. Допускается согласованное окно обслуживания при обновлении. Репликация не означает автоматически высокую доступность баз данных, файлового хранилища и модельных сервисов.

По [оценке и критериям обобщения](../../KUBERNETES_PLATFORM_QUESTIONS.md) выбраны
продуктовые направления: настройки/schema поддерживаемых профилей, общий OIDC,
versioned audit/JSON после commit и отдельное расширение Kubernetes external.
Критерий — одна поставка для нескольких инсталляций, отличающихся параметрами,
Secret/PVC references и проверенными adapters без правок Python/Next и форка
общих templates. kgateway/VSO/OpenSearch/корпоративные CI components — опциональные
adapters, а не обязательные зависимости каждой платформы. Их конкретные схемы
не становятся универсальными defaults. Поддержка любых IdP/CSI/CPU не обещается.

Готовые settings и compact/lifecycle не создаются заново. Для external требуется
отдельный ownership/backup/restore contract: существующий chart и operator
фиксируют bundled, один URL недостаточен. Общие OIDC/audit возможности можно
проектировать до выбора параметров конкретной среды; окруженческая приёмка
сохраняет её открытые вопросы. Outbox, trusted IP и zero-downtime не включаются
автоматически в небольшой пакет конфигурации. Распределение по задачам и критерии
приёмки находятся в разделе «Обобщение для нескольких платформ» основного плана.

Целевой контур состоит из трёх отдельных кластеров DEV, TEST и PROD. Хранилища базы знаний разворачиваются в составе приложения; доступ к настоящим LLM и embeddings есть только в PROD. Домашний стенд начинается с существующей VM `training-ubuntu`. Первая поставка использует **bundled** во всех трёх кластерах. Существующий Compose external сохраняется; расширение Kubernetes external не блокирует первую поставку.

## Требования целевой платформы

Ниже зафиксированы обобщённые технические требования трёх сред. Конкретные реквизиты, внутренние адреса, ссылки на закрытые порталы, имена организаций, учётные записи и пути секретов в этот документ не включаются. Версии API и возможности конкретного namespace проверяются при внедрении.

| Область | Подтверждено документацией | Решение в плане |
|---|---|---|
| Namespace | Отдельная заявка через MR для каждой среды, team связывает namespace с Vault | Подготовить три декларации, выбрать пул и квоты; отправка MR и заявки — отдельные действия при исполнении |
| Публикация | kgateway, общий Gateway `<gateway-namespace>/<gateway-name>`, ListenerSet и HTTPRoute | Платформенный overlay создаёт route/listener, не Ingress и не общий Gateway/controller |
| DEV TLS | TLS Secret создаёт cert-manager; ручное создание запрещено | Chart только ссылается на certificateRefs; ожидать Accepted/Programmed и появление Secret |
| TEST/PROD TLS | cert-manager отсутствует; нужен заранее полученный сертификат и TLS Secret | Подготовка платформой/оператором вне application chart, затем existing TLS secret reference |
| Секреты | Vault Secrets Operator, привязка namespace к пространству секретов команды, VaultStaticSecret с нужным vaultAuthRef | Runtime Opaque secrets поступают из Vault до миграции; ключи/пароли стабильны между обновлениями |
| Доставка | GitLab CI components, Helm chart и images в Artifactory, TEST/PROD получают прошедшие Security-Pipeline RC-артефакты | Сначала DEV build/проверки, затем продвижение тех же версий/digests через TEST в PROD |
| Наблюдаемость | Prometheus/Grafana; Logging Operator → OpenSearch, форма декларации namespace `logging.enabled: true` | Подключить существующие средства; проверить parser, доступ/retention и защищённый scrape; не устанавливать дубли операторов |


Детали маршрута: HTTPRoute указывает frontend Service в своём namespace и числовой port; HTTPS привязывается к ListenerSet. HTTP redirect задаёт hostname и parentRef sectionName=http. request timeout не меньше backendRequest; длительность SSE и лимит загрузки проверять по всей цепочке, не копировать пример `32Mi` в продукт с загрузкой до 100 МБ. Не добавлять автоматические повторы изменяющих POST на gateway.

Неизвестны фактические Kubernetes/Gateway CRD версии, StorageClass/CSI, квоты, UID policy, имена namespace/домены, права на backup и endpoints PROD моделей. Эти пункты остаются входным preflight, хотя общий платформенный путь уже подтверждён.

Уточнения из [сводки документации 04.10.2026](../../KUBERNETES_PLATFORM_QUESTIONS.md)
поддерживают собственный chart и позволяют выразить весь внешний маршрут в
frontend Service; обязательный прямой `/api` → backend не установлен.
Компактный Pod/Jobs, Recreate/окно остановки и bundled production storage остаются
предложениями до подтверждения допуска. Значения `32Mi`/timeouts, версии CI
компонентов и sample `on_success` не задают policy приложения. `linux/amd64`,
manual promotion и одинаковые digests — решения проекта; актуальная архитектура
узлов и применимость внешних обязательных gates проверяются в отдельной копии.
Миграция remote mirrors не означает переноса всех release repositories.
Пункты OIDC/audit/storage и гарантии доставки сводкой не закрыты.

### Уточнения актуального Gateway-контракта

- `180s` во внешнем балансировщике относится к простою HTTP на порту 80. HTTPS на 443 идёт TCP-туннелем с лимитом часа без данных; это не общий предел длительности HTTPS-ответа. Дополнительно действуют собственные request/streamIdle timeouts шлюза и приложения. Проверить SSE до первого события, поток с паузами, cancellation и загрузку через весь маршрут; heartbeat не отменяет общий request timeout шлюза.
- Новые домены сразу направляются на Gateway API. Переключение балансировщика заявкой требуется при миграции существующего домена с Ingress; не вводить эту заявку как безусловный блокер новой установки. Отдельно проверить DNS: wildcard зоны и индивидуальные записи имеют разный порядок подготовки.
- DEV TLS Secret создаёт cert-manager; старые шаблоны с ручным `kubectl create secret tls` в DEV неприменимы. TEST/PROD используют заранее подготовленный TLS Secret. Применять реальную CRD schema и условия Accepted/Programmed, не устаревшие примеры Ready или `spec.allowedRoutes`.
- DEV требует явный `imagePullSecrets` для закрытого registry. Для TEST/PROD руководство описывает анонимное чтение зеркала: подтвердить его из Pod, не переносить DEV credentials автоматически и не требовать лишний pull-secret. Chart должен поддерживать оба режима.
- Ротация Secret с env-переменными требует контролируемого пересоздания Pod по процедуре остановки/backup/запуска. Не менять password в Vault без согласованного изменения в уже инициализированном PostgreSQL; неизменный Helm manifest не доказывает обновление env.

## Модельные сервисы в трёх средах

| Среда | Хранилища | Модели | Что доказывает приёмка |
|---|---|---|---|
| Домашний стенд | Собственные bundled PG/Qdrant/PVC | Stub для повторяемых тестов; отдельный дополнительный прогон с домашними моделями | Установка, сбои, очередь, backup, функциональная интеграция; домашняя модель не эквивалентна PROD модели целевой платформы |
| DEV целевой платформы | Bundled, отдельные данные и секреты | Изолированный HTTP LLM stub + fake embeddings | Контракты HTTP/SSE, UI, SSO, миграции, обработка ошибок и маршрутизация |
| TEST целевой платформы | Bundled, отдельные данные и секреты | Тот же утверждённый stub image + fake embeddings | Репетиция установки/обновления/восстановления утверждённого RC; не качество RAG |
| PROD целевой платформы | Bundled, production PVC/секреты | Только реальные разрешённые LLM/embeddings endpoints | Ограниченная интеграционная приёмка на синтетических документах перед допуском реального корпуса |

Во всех целевых кластерах `ENVIRONMENT=production`: это режим защит приложения, а не название кластера. Для различения среды планируются отдельные `DEPLOYMENT_TIER=dev|test|prod|home|ci|local` и `MODEL_MODE=stub|live|unavailable`. Новые параметры обратно совместимы: default local/live сохраняет текущие способы запуска. В prod разрешён только live; запрещены fake embeddings и установленный stub. Проверки выполняются в Helm, preflight и runtime конфигурации. Профиль unavailable применяется для отрицательных тестов, не для приёмки генерации.

Существующий `docker-compose.ci-runtime.yml` отвечает только на model discovery и не годится для функциональных тестов чата/генерации. Нужен отдельный test-only image: GET `/v1/models`, POST `/v1/chat/completions`, SSE delta/final finish_reason/`[DONE]`, схемы генерации концептов/классификатора/перевода, сценарии 429/503, задержки и оборванного потока. Фикстуры и ответы явно тестовые. `EMBEDDING_PROVIDER=fake` сохраняет выбранную размерность; BM25 — основной поиск фикстур, dense проверяется только на транспорт/размерность, не семантику.

В ветке реализации этот stub уже создан. Home tracked-chat дополнен `/props`, `/apply-template`, `/tokenize` и использует `local_qwen` только с синтетическим счётчиком. Перед приёмкой DEV/TEST/PROD требуется матрица `documents/fast/full`: соответствующие выбранной модели context window, chat template/token counter, отсутствие/ошибка tokenizer и отмена с поздним ответом. Точный механизм каждого provider фиксируется перед реализацией его контракта; неподдерживаемый token budget даёт явный отказ, без снятия fail-closed guard. Синтетический счётчик доказывает транспорт/схему теста и запрещён для PROD, обычный SSE smoke не доказывает работоспособность tracked режимов.

Stub image не включается в application image; DEV/TEST deployment его явно подключает. Для TEST нужна отдельная разрешённая доставка его image через платформенный Security-Pipeline. Нельзя менять fake→live поверх существующего индекса: тестовые БД/PVC/Qdrant коллекции не продвигаются между кластерами. В PROD создаётся новый индекс на настоящих embeddings. Продвигается код/chart/image digest, а не runtime данные или секреты. PROD smoke не использует dev/test credentials, не восстанавливает их jobs и не объявляет валидной модель по одному GET `/models`.

| Liveness | Отдельного `/health/live` сейчас нет | Добавить дешёвую проверку HTTP процесса без внешних зависимостей |
| Frontend | `/health` rewrite фиксируется при сборке как `http://backend:8000` | Сохранить Service `backend` внутри namespace; не проверять готовность frontend через этот Service до готовности Pod |
| Хранилища | `validate_storage_mode`: bundled требует `postgres:5432` и `qdrant:6333`; external запрещает короткие Compose hostnames | Сохранить Service names в bundled; external задавать отдельными DNS/FQDN. Не ослаблять валидатор ради chart |
| Backup | `scripts/production/*` используют Docker Compose | Kubernetes нуждается в собственных orchestration-скриптах; повторно использовать формат/проверки где возможно |
| Безопасность | `SECURITY.md`, production auth checks, CSRF, diagnostic sanitizer | Новая топология не отключает эти контракты; изменение модели доступа сопровождается обновлением SECURITY.md |

Экспорт также содержит локальные download leases (`export_queue.py`), а загрузка, разметка, staging, чат и LLM-клиент — процессные блокировки/лимиты. Переноса одной `JobQueue` недостаточно для backend replicas.

## Предлагаемые варианты и выбор

1. **Один Pod приложения, два контейнера; PostgreSQL/Qdrant отдельно.** Минимум изменений для первой поставки, совместные тома диагностики, общий жизненный цикл frontend/backend. Выбран для этапа 1.
2. **Frontend и backend сразу в разных Pod.** Независимое обновление, но текущая диагностика требует дополнительного решения общего доступа/сбора файлов. Отложено до этапа 2.
3. **Сразу распределённые API и workers.** Правильная целевая архитектура, но заметно задерживает первый запуск и расширяет риски миграции. Разбито на этапы 3–5.

Chart: `deploy/helm/ai-knowledge/`; namespace принадлежит одной инсталляции приложения. Сначала доступны только `deployment.mode=compact`, `application.replicas=1`, `UVICORN_WORKERS=1`. Helm schema/template validation отклоняет несовместимые значения. Service `backend` не публикуется наружу.

## Первая поставка в целевой контур

### Приложение и хранение

Общий контракт расширения настроек описан в
[проекте пакета конфигурации](2026-10-04-kubernetes-configuration-design.md).
Новые probe timings, TrafficPolicy и runtime trust reference требуют рассмотрения,
подробного плана и реализации; текущая compact-приёмка их не подтверждает.
Сохраняются health paths, порты, единственный writer и production protections;
различия инсталляций проверяются на одинаковых образах.

- Один Deployment `application`, стратегия `Recreate`, два обычных контейнера frontend/backend. Приложение не зависит от порядка их старта.
- Service для frontend → 3000; Service `backend` → 8000. Публикуется только frontend через общий Gateway API. Базовый chart может работать без публикации; платформенный overlay содержит ListenerSet/HTTPRoute и необязательный TrafficPolicy. Создание Ingress/TLS Secret в этом overlay запрещено.
- `/data` находится на отдельном PVC. Диагностика — на другом PVC с отдельными подкаталогами backend/frontend/control; права и read-only mounts соответствуют текущему Compose. Подкаталоги создаёт непривилегированный initContainer с доступом к корню тома.
- Один Pod позволяет стартовать без RWX. Конкретные CSI, accessMode и возможность переподключения тома на другой узел проверяются до установки. Local-path/hostPath в домашнем тесте не подтверждают переносимость платформенного PVC.
- PVC приложения создаются отдельно от Helm release, chart получает `existingClaim`. Удаление release не удаляет пользовательские данные. Для bundled StatefulSets явно сохраняются storage claims; процедуру удаления/восстановления проверять отдельно.
- Режим `bundled`: оба хранилища устанавливаются в namespace приложения как одиночные StatefulSets с PVC; он выбран для первой поставки. Kubernetes `external` — дополнительная переносимость после первой поставки, когда оба endpoint управляются отдельно. Существующий Compose external обязательно проходит регрессию. Смешанный режим в первой версии не поддерживается.
- Образ и версии PostgreSQL/Qdrant согласуются с уже закреплёнными Compose версиями; не добавлять незафиксированные chart dependencies.
- В PROD LLM и embeddings — внешние HTTP API; DEV/TEST используют изолированный stub/fake профиль выше. Домашний стенд получает собственные БД/коллекции/каталоги; домашний модельный endpoint допускается общий только для дополнительной live-приёмки с ограничением нагрузки.

`Recreate` управляет обычным обновлением Deployment, но не является распределённой блокировкой при ручном удалении Pod или неопределённом состоянии узла. RWO также не гарантирует одного writer. До этапа распределённого владения запрещён сценарий принудительного запуска замены, пока старый экземпляр может продолжать работать. Runbook требует сначала подтвердить его остановку/изоляцию. Это ограничение первой поставки, а не обещание HA. См. [Deployment Recreate](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#recreate-deployment) и [режимы доступа PV](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).

### Конфигурация и probes

- ConfigMap содержит несекретные параметры; Secret с паролями/URL с credentials/APP_SECRET_KEY/SSO credentials передаётся через `existingSecret`. У целевой платформы его создаёт VSO, chart хранит только ссылки на VaultStaticSecret. Секретные значения не попадают в values, Git, отчёт preflight и логи команд. Переустановка сохраняет ключ сессий. Не применять vals-подстановку паролей в Helm values, если их можно получить через existingSecret: иначе значения попадут в Helm release history.
- `ENVIRONMENT=production` во всех трёх целевых кластерах. Production auth и HTTPS cookies остаются включены; корпоративный CA устанавливается для Node, Python/HTTP клиентов и build tooling без отключения TLS verification. Домашний test IdP имеет отдельный realm/client; auth-disabled допустим только в изолированном CI-тесте и не доказывает платформенную приёмку. Проверить доверенные CA в образах и не заменять автоматически поддерживаемые Python/Node версии на другой базовый образ.
- Контейнеры работают непривилегированно. Учитываются `runAsUser`, `runAsGroup`, `fsGroup`, writable mounts и фактические ограничения целевой платформы; начальный ориентир UID/GID 1000 не является обещанием совместимости с arbitrary UID/OpenShift.
- Backend startup/liveness обращаются к новому `/health/live`; readiness — к существующему `/health/ready` напрямую на Pod port 8000. Задержки и пороги выводятся из измеренного холодного запуска и времени readiness checks.
- Frontend startup/readiness/liveness используют TCP port 3000 на первом этапе. Работоспособность HTTP/SSO подтверждает smoke-тест. Rewrite `/health` не используется как frontend readiness: это может создать цикл через Service, который исключает ещё неготовый Pod.
- `requests`, `limits`, `terminationGracePeriodSeconds` фиксируются после малой нагрузочной приёмки; не поднимать `PIPELINE_MAX_WORKERS` и admission limits автоматически. Проверять также процессы парсера, временное место и `/tmp`.
- Приложение не обращается к Kubernetes API: ServiceAccount без автоматического токена. Оператору нужны ограниченные namespace-права; cluster-wide CSI, CNI, gateway и certificates — зона платформенной команды.
- NetworkPolicy описывает нужные ingress/egress: DNS, frontend→backend, PostgreSQL, Qdrant, IdP, LLM и embeddings. Эффективность доказывается сетевыми пробами на CNI с enforcement; наличие YAML не считается проверкой.

### Контракт выбранного synthetic model budget

Для DEV/TEST и домашнего stub выбран существующий transport `local_qwen`:
`LLM_MODEL=LLM_CHAT_MODEL=openai/test-stub`, endpoint из chart, `MODEL_MODE=stub`.
Это имя адаптера HTTP API, не утверждение о настоящей модели или точности tokens.
`/props` даёт synthetic `n_ctx=32768`; `/apply-template` сериализует полный
system/user prompt; `/tokenize` использует детерминированную тестовую формулу.
Каждый ответ помечен `test_only=true`. Счётчик учитывает output reserve + 256
и остаётся fail-closed при неподдерживаемом provider, отсутствующем endpoint или
неверной структуре. Маркированные synthetic ответы запрещены вне non-PROD stub.
Пустое/нестроковое template, неправильный context window или token IDs не
считаются проверенным бюджетом. Реальный `local_qwen` продолжает использовать
template/tokenizer своего сервера; непроверенные live provider не получают
эвристического fallback. Реальные профили PROD требуют отдельной model-matched
приёмки после получения endpoints и контракта.

`documents` возвращает источники без генерации и tokenizer. `fast/full`
проверяются через настоящий адаптер и HTTP/SSE stub; для full проверяется также
multi-batch map/synthesis на заранее известных synthetic цитатах. Отмена с
поздним ответом не переводит stopped attempt обратно в completed. Эти проверки
не закрывают SSO, Qdrant retrieval, качество RAG или точность live tokenizer.

### Установка, обновление и восстановление

Одна процедура оператора с явными `context`, `namespace`, release, values и image digests. Нельзя полагаться на текущий kube-context по умолчанию.

Дома процедуру выполняют скрипты; у целевой платформы те же шаги запускает GitLab pipeline с окруженческими runner tags и kubeconfig из Vault. Нужно проверить README и возможности утверждённого `cd-helm` компонента: он не считается доказательством нужного порядка остановки/backup/миграции. Если компонент не выражает порядок, добавить последовательные jobs с environment resource lock и платформенным kubectl-компонентом, а не скрывать миграцию в бесконтрольном startup hook. Образы и Helm chart собираются через BuildKit/Helm components и продвигаются через Security-Pipeline, без пересборки между TEST и PROD; registry host может меняться, содержимое сверяется по digest. Текущий GitHub CI остаётся контуром регрессии.

Разделение build/deploy проектов требует отдельного immutable `operator-tools.tar.gz` той же source revision с layout `scripts/kubernetes/` и нужными smoke fixtures. Backend operation scripts остаются в соответствующем backend image. Release manifest содержит `operator_tools` с `format=1`, `source_revision`, `archive_reference`, `sha256`, `supported_config_schema_versions`, `toolbox_image_digest`. Deploy-проект проверяет tools/chart/image/config identities до мутаций и работает без checkout исходников или ручной копии скриптов. Python/PyYAML/Helm/kubectl предоставляются закреплённым toolbox. Отсутствие tools, checksum mismatch, неподдерживаемая config schema или отсутствие зависимости останавливают доставку до миграции; комплект/toolbox также доступны через разрешённый air-gap путь.

Локальный контракт operator tools реализован в Kubernetes-ветке:
воспроизводимый allowlisted архив, release identity, standalone trusted
bootstrap и шаблон отдельного consumer pipeline. Начальный bootstrap поступает
из защищённого toolbox, а не из непроверенного архива; backend smoke fixtures
остаются в matching backend image. Исполнение overlay без исходников и
отрицательные сценарии подтверждены локально. Публикация immutable комплекта,
toolbox и работа через реальные platform components ещё требуют приёмки.

1. Read-only preflight проверяет ресурсы, права, доступность зависимостей, PVC, registry, TLS/SSO и соответствие выбранному профилю.
2. Для первой установки создаются PVC и инфраструктура, приложение выключено через `application.enabled=false`. Существующие storage passwords не меняются при повторном запуске.
3. Отдельный Job с backend image выполняет текущую проверку storage mode, ожидание Qdrant и `alembic upgrade head`. Запуск backend разрешается только после `Complete` этого Job и сверки Alembic head. Ошибка оставляет приложение выключенным и сохраняет доступную диагностику.
4. Для обновления сначала останавливается приложение; требуется подтверждённое завершение старого Pod, затем согласованный backup PostgreSQL + Qdrant + `/data`, затем миграция и запуск. Длительные задачи могут перейти в существующие paused/failed состояния; их поведение документируется и проверяется, автоматическое продолжение не обещается.
5. После запуска проверяются readiness, авторизованный upload/search/chat, диагностика и версии образов. Обновление получает отчёт с длительностью окна обслуживания и результатами проверок.
6. Backup/upgrade/restore сериализуются namespace operation lock; после прерывания операции нельзя автоматически снимать чужую/непроверенную блокировку и продолжать миграции.
7. `helm rollback` не откатывает схему и данные. Откат образа разрешён только при подтверждённой совместимости схемы; иначе восстановление согласованного backup в новую БД/коллекцию/PVC и новый namespace с последующим переключением трафика.

Для external storage заранее согласуются полномочия и ответственный за dump/snapshot/restore. Без выполненного restore drill этот профиль не считается готовым к платформенной поставке. Backup лежит за пределами исходных PVC и единственной VM; секреты восстанавливаются по отдельной защищённой процедуре. Независимые несогласованные snapshots трёх хранилищ не считаются backup приложения.

План задачи 6 отдельно проверяет off-VM destination, ACL/шифрование/retention, согласованное расписание и свежесть completed backup. `restore_without_source_vm` восстанавливает новый независимый target при недоступной исходной VM только из внешнего backup и отдельного защищённого источника секретов; проверяются PG/Qdrant/files, функциональный smoke и измеренные RPO/RTO. Home backup на диске VM вне kind закрывает только согласованность/restore приложения, не потерю этой VM. Непредоставленное внешнее хранилище сохраняет этот gate открытым.

## Последовательность этапов

| Этап | Результат | Условие завершения |
|---|---|---|
| 0. Контракт целевой платформы и домашний стенд | Проверенные требования DEV/TEST/PROD, kind на training-ubuntu | Малый Pod читает/пишет PVC, доступен registry и нужные конкретной среде API, подтверждены TLS/SSO и namespace-права |
| 1. Первая поставка | Helm compact, bundled PG/Qdrant, stub DEV/TEST, live PROD, миграции/backup/GitLab доставка | Домашняя матрица → DEV → TEST → PROD smoke; непустой restore drill подтверждён, реальные модели проверены отдельно |
| 2. Независимый frontend | Отдельный frontend Deployment, 2 реплики; backend остаётся 1 | Авторизация, SSE, версии сборок, диагностика каждой реплики и обновление проверены через балансировщик |
| 3. Отделение фоновой обработки | Роли API и worker, долговечная очередь, первоначально 1 API + 1 worker | Перезапуск API не останавливает worker; просроченный owner не публикует результат; непустая очередь проверена при upgrade/rollback поддерживаемых версий |
| 4. Реплики backend API | 2 API + 1 worker, общее состояние и файловый доступ | Переключение API сохраняет сессии, отмену, лимиты, экспорты и настройки; остановка API не повреждает задания |
| 5. Реплики workers и эксплуатация | Несколько workers, управляемые повторы и HA проверки | Сбой владельца задачи не приводит к потере задания или повторной публикации результата; измерены лимиты и восстановление |

Этап 1 — самостоятельная поставка. Этапы 2–5 не блокируют первый запуск. Каждый следующий этап имеет собственный подробный план перед реализацией: будущие внутренние API и миграции не замораживаются на основании неполного аудита.

### Этап 2

Убрать файловую связь frontend↔backend через общий каталог: выбранное направление — внутренний аутентифицированный протокол получения diagnostic control и отправки уже санитизированных событий. Отдельный instance ID, ограниченные очереди/пакеты, сроки действия capture, обработка недоступного collector без блокирования пользовательских запросов; политика просроченного разрешения на capture — fail closed. Не превращать это API в источник произвольного текста/путей.

Ввести поддержку `deployment.mode=split` только после проверки диагностики. Все frontend replicas используют одну сборку; проверить фактическое применение Next caches/Server Actions перед добавлением общей инфраструктуры. Учесть обновление версий, сохранение пользовательского состояния, logout/revocation и streaming. Общий cache добавляется только для реально используемого сохраняемого cache. [Требования Next.js к нескольким экземплярам](https://nextjs.org/docs/app/guides/self-hosting#multi-server-deployments).

### Этап 3

Сохранить компактный режим для локального запуска/Compose и добавить роли `combined`, `api`, `worker` в одном backend image. Все фоновые механизмы перечислить: pipeline, bulk jobs, raw exports, backfills, cleanup/purge, diagnostic bundle workers, translation jobs и восстановление при старте. API не должен запускать их неявно при импорте либо создании singleton.

Предпочтительный первый вариант долговечной очереди — PostgreSQL, уже входящий в production стек. До реализации сравнить с Redis на фактических транзакционных границах. Обязательны атомарное получение задания, lease/heartbeat, идентификатор владельца и fencing token, запрос отмены в БД, ограниченные повторы и идемпотентная публикация. Потерявший владение worker не вправе коммитить результат или писать активную версию в Qdrant/FS. Если атомарное ограждение внешних записей невозможно напрямую, использовать версии поколений и отдельный шаг публикации.

Эта минимальная защита реализуется уже в этапе 3 с первым worker: после восстановления просроченного lease старый процесс может возобновиться даже при nominal replicas=1. Этап 5 расширяет проверенные guards на несколько workers. Отказные тесты запрещают устаревший SQL commit/FS/Qdrant publish после нового claim и при гонке cancel/publish.

В подробном плане этапа 3 фиксируются versioned job payload и таблица совместимости API/worker/DB/config schema, порядок expand → upgrade → contract и допустимый rollback. Накопленные задания прежней поддерживаемой версии читаются новым worker; unknown job version не забирается и не удаляется. Ошибка миграции не запускает worker. Этап 4 повторяет проверки на mixed versions и running jobs: rolling update разрешён только для подтверждённых пар, иначе нужно maintenance/drain/миграция либо restore. Сам факт нескольких реплик не означает совместимость версий.

Начальная split конфигурация допускает 1 API + 1 worker с общим проверенным файловым хранилищем. Нужен RWX для разных узлов либо явно ограниченный режим размещения на одном узле; скрытая зависимость от local disk недопустима. Перенос на S3 — отдельное решение, поскольку staging/парсеру по-прежнему может требоваться локальный scratch.

### Этапы 4 и 5

До API replicas вынести в общий контур: rate/admission limits, блокировки загрузки/дедупликации/разметки, состояния и отмену чата, LLM concurrency budget, download leases экспортов/diagnostic bundles, cache/config invalidation, scheduler leadership. Авторизация и APP_SECRET_KEY согласованы; отзыв прав проверяется на обеих репликах. Backup охватывает новые таблицы очереди и идентификатор инсталляции; восстановленные тестовые jobs не начинают работу с production endpoints.

Для workers гарантировать at-least-once доставку и идемпотентный видимый результат, без обещания exactly-once внешних LLM вызовов. Повторы не должны удваивать индекс, снимать отмену или публиковать старую версию документа. Глобальный бюджет нагрузки сохраняется независимо от числа Pod. Масштабирование сначала ручное; HPA добавляется после измерений по длине/возрасту очереди и доступной мощности LLM/embeddings, а не только CPU API.

Отказ одного API оборвёт его активное SSE-соединение: требуется понятное завершение/переподключение и сохранность истории; прозрачное продолжение генерации не считается существующей возможностью. PDB, topology spread и распределение по узлам вводятся вместе с проверенной многорепличной конфигурацией. HA PostgreSQL/Qdrant/CSI и модельных endpoint оценивается отдельно по требованиям целевой платформы.

## Домашний тестовый контур

### Известные данные и допущения

По фактическому отчёту 03.10.2026 VM `training-ubuntu` имеет 4 vCPU / 6 ГиБ RAM / диск около 50 ГиБ. Основной одноузловой kind прошёл compact install/update/restore и отдельный home Gateway/IdP/HTTPS прогон. Второй kind Kubernetes 1.36.4 с Cilium 1.20.2 прошёл enforcement probes и остановлен после verified backup для экономии памяти; его данные сохранены. Исторические 8 ГиБ из записи 19.09.2026 не используются как текущий budget. Перед действиями повторно подтвердить идентичность VM, ресурсы и доступ; один VMID/старый DHCP адрес недостаточен. Полный browser/VSO/target/multinode/off-VM acceptance ещё не выполнен.

### Контур A для первой поставки

Переиспользовать эту VM по подтверждённому выбору пользователя, после read-only инвентаризации. Измеренные 4 vCPU / 6 ГиБ / около 50 ГиБ использованы для малого synthetic corpus, не тяжёлой параллельной обработки; влезание и свободное место проверяются перед каждым прогоном. Предлагаемый бюджет полноценного функционального стенда: **4–6 vCPU, 16 ГиБ RAM, 120–160 ГиБ SSD**, stub или внешние домашние LLM/embeddings. Это плановая оценка с Kubernetes/image/backup запасом, не измеренная гарантия. Тяжёлые сценарии выполняются последовательно; остановленный Cilium kind требует restart и повторных smoke/probes.

Развернуть:

- kind с одним узлом и закреплённым node image; версия Kubernetes соответствует поддерживаемой версии целевой платформы, а не просто самой новой установленной версии kubectl;
- изолированные namespace для последовательного воспроизведения dev/test/prod-sim; PostgreSQL/Qdrant каждого окружения — bundled, перенос данных между ними запрещён; отдельный будущий Kubernetes external smoke не блокирует целевой платформы;
- PVC provisioner для функциональных тестов; каталог данных на диске VM и резервные копии вне удаляемого kind-кластера;
- Gateway API CRDs и совместимый kgateway с аналогичными ListenerSet/HTTPRoute. Домашние домены/CA отличаются от целевых. Сначала допустим SSH-туннель/port-forward, но он не заменяет финальный Gateway тест. При нехватке RAM расширить VM либо признать проверку маршрута невыполненной;
- registry либо импорт собранных образов в kind; отдельно проверить реальное скачивание с `imagePullSecrets` для платформенной поставки;
- изолированный Keycloak realm/client, тестовые пользователи и redirect URIs; если доступного IdP нет — отдельный тестовый экземпляр. Дома Secret допустимо подготовить локально; платформенную VSO интеграцию окончательно проверять в DEV, не ставить весь Vault ради первого smoke;
- CNI с NetworkPolicy enforcement для сетевой приёмки; стандартный kind CNI не принимать за доказательство enforcement;
- небольшой набор DOCX/XLSX/PDF/MSG, контрольный RAG-набор, backup destination и сбор метрик Pod/дисков/ошибок.

Не менять работающий Compose staging, целевые данные, домашний DNS/VPN и модельные службы ради создания стенда. Проверить пересечение Pod/Service CIDR с LAN/VPN. Доступ к Kubernetes API — через локальное подключение/SSH, без публикации в Интернет. kind поддерживает несколько контейнерных узлов, но они не дают независимых физических ресурсов. [Конфигурация kind](https://kind.sigs.k8s.io/docs/user/configuration/).

### Контур B перед приёмкой реплик

Планировать отдельные VM: **1 control-plane: 2 vCPU / 4 ГиБ / 32 ГиБ; 2 worker-узла: каждый 4 vCPU / 8 ГиБ / 80 ГиБ**. Итого 10 vCPU, 20 ГиБ RAM и 192 ГиБ дисков до общего хранилища. Это резерв для согласования после инвентаризации Proxmox, не заявленные свободные ресурсы.

Дистрибутив/версия/CNI/CSI по возможности совпадают с целевым контуром. Установщик выбирается после подтверждения его конфигурации; произвольный k3s не объявляется эквивалентом другой платформы. Для переноса Pod между worker-узлами нужен подходящий CSI; для совместной записи API/workers — RWX или согласованный новый storage backend. Отдельный storage VM/NAS при необходимости планируется дополнительно, ориентир 2 vCPU / 4 ГиБ и 100–200 ГиБ; общий диск одной VM остаётся SPOF.

Проверки: drain, остановка worker VM, недоступный storage, потеря соединения с БД/LLM, рестарт во время обработки/скачивания, восстановление owner lease, обновление смешанных версий. Один control-plane позволяет тестировать приложение при доступном control-plane; для проверки HA самого control-plane нужны 3 control-plane VM. Все VM на одном Proxmox-хосте не доказывают устойчивость к отказу физического хоста.

## Данные целевой платформы, необходимые до первой установки

| Требование | Решение при отсутствии информации |
|---|---|
| Kubernetes distribution/version, CPU architecture, Pod Security/UID policy | Установка блокируется до записи совместимого профиля; не обещать универсальную поддержку |
| PostgreSQL/Qdrant и backup ownership | Bundled выбран пользователем; подтвердить допускаемые StatefulSets/PVC и место хранения резервных копий |
| CSI/StorageClass/accessMode, capacity, reclaim и restore | Проверить небольшим disposable PVC; не экспериментировать на данных приложения |
| Gateway, DNS, TLS/CA, максимальный upload/таймаут SSE | Общий kgateway подтверждён; определить домены/сертификаты/CRD версии и проверить маршрут каждой среды |
| Registry/network isolation/proxy, доступ к IdP/LLM/embeddings | Проверить из Pod; при air-gap подготовить зеркала образов и chart без внешних загрузок при установке |
| Namespace RBAC/quota, maintenance window, RPO/RTO | Зафиксировать до release; не назначать численные SLA без согласования и замеров |
| Нагрузка и фактический объём документов | Измерить на репрезентативной выборке до фиксации requests/limits/PVC |

Отсутствие этих сведений не мешает подготовить chart и домашние тесты. Оно блокирует утверждение совместимости и установку в платформенный production.

## Критерии первой поставки

Детальные проекты контрактов задачи 5а:
[OIDC](2026-10-04-oidc-compatibility-design.md) и
[аудит/stdout](2026-10-04-audit-delivery-design.md).
Они ещё не реализованы. Дополнительные примеры chart/deploy/stdout сопоставлены
с общим решением в [обезличенном отчёте](../reports/2026-10-04-deployment-examples-review.md).
Их runtime ports, RollingUpdate, прямой API route, fixed ConfigMap keys и
внешние реквизиты не становятся контрактом этого приложения.

Общий toolbox поставляется рецептом `deploy/ci/operator-tools/Dockerfile`:
Debian Python 3.11+ по digest, linux/amd64, PyYAML 6.0.3, Helm v4.3.0 и
kubectl v1.37.0 с обязательными SHA и проверкой реальной версии. Разрешённые
HTTPS mirrors настраиваются при сборке; TLS не отключается, redirect не
переносит credentials и не понижает протокол. CA и package configuration
передаются build secrets; public CA сверяется со своим SHA cache revision.
Runtime UID/GID 1000 и trusted bootstrap не зависят от скачивания инструментов.
Локальная acceptance использует точный image ID, offline/read-only consumer
с одними release artifacts и пять fail-before-extraction сценариев. Она не
подтверждает registry publication или provenance. Эти проверки, защищённый
promotion и инфраструктурные реквизиты принадлежат отдельной окруженческой копии.

Работает bundled дома и последовательно в DEV/TEST/PROD целевой платформы. Выполнены установка с нуля, повтор установки без потери данных, обновление, отказ миграции, перезапуск Pod и согласованное восстановление непустого backup. Через браузер пройдены SSO, загрузка, генерация, поиск, чат/SSE, просмотр исходника, экспорт, диагностика и корзина. DEV/TEST проходят на явно тестовых ответах; реальная модельная интеграция и релевантность проверяются в ограниченной PROD приёмке отдельно. Не потеряны концепты/чанки/связи источников и права доступа. Нет зависимости readiness/liveness от доступности внешнего LLM. Сохранены существующие Compose bundled/external CI и локальные launchers. Отчёт отдельно перечисляет реальные проверки, симуляции и непроверенные свойства.

Дополнительно закрыты применимые требования матрицы поставки: общий линтер блокирует доставку, артефакты проходят применимый security pipeline и доступны в целевых registry, OIDC совместим с зарегистрированными клиентами. Принят профиль аудита и подтверждены его события, каналы и гарантии; БД + stdout, durable retry и доверенный IP являются критериями только согласованного профиля, а не следствием наличия logging stack. Подтверждена пригодность bundled PostgreSQL/Qdrant для PROD и закрыты применимые формальные условия ввода в эксплуатацию. Неисполненное согласование или непройденная проверка остаётся блокером, даже если домашний smoke успешен.
