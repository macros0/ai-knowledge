# Составной ответ чата по всем найденным источникам

**Дата:** 29.09.2026.
**Статус:** спецификация для проверки пользователем; код функции ещё не изменён.

## 1. Цель и согласованные правила

Чат показывает найденные источники сразу после поиска и обрабатывает моделью **каждый** источник, прошедший действующие проверки видимости, происхождения письма, словарных совпадений и точного названия объекта. Порог 70% пока не используется. «Все» означает весь набор, возвращённый текущими поисковыми ветками Qdrant (`SEARCH_PER_BRANCH_TOP_K`), а не полный перебор корпуса. Существующий срез `top_k` и ранний суммарный лимит символов в `merge_and_format` не должны удалять блоки из нового режима.

Если блоки не помещаются в одно окно контекста, чат обрабатывает их последовательными вызовами LLM, затем собирает единый ответ. Источники получают постоянные номера `[N]` до первого вызова LLM; ответ и сохранённая история используют те же номера. Использование источника означает, что его текст вошёл хотя бы в один завершённый вызов модели. Если блок пришлось разделить, обработанным он считается только после всех его частей. Источник не обязан появиться в итоговых цитатах: модель может признать его не относящимся к ответу. Каждый блок содержит нынешнюю ограниченную выдержку из концепта или чанка (`CHAT_CONCEPT_MAX_CHARS`/`CHAT_CHUNK_MAX_CHARS`); обработка всех найденных блоков не означает чтение каждого документа целиком.

Пользователь может нажать «Остановить» в карточке ответа. Потеря фокуса окна чата, скрытие вкладки и уход со страницы также ставят работу на паузу. Завершённые порции сохраняются. После возвращения работа **не продолжается автоматически**: пользователь нажимает «Продолжить» либо задаёт новый вопрос. Новый вопрос окончательно закрывает прежний незавершённый ответ. Простое чтение источников в том же окне не останавливает генерацию и не меняет фокус или прокрутку.

Наблюдение на локальном корпусе 29.09.2026: для «Покажи справочник причин больничного листа» без нынешних ранних обрезок получено 28 блоков после фильтров, из них 10 с относительной оценкой не ниже 0,70. Их тексты занимают шесть окон по `CHAT_MAX_CONTEXT_CHARS=16000`; потребуется как минимум шесть вызовов обработки и один вызов объединения. Эти числа характеризуют текущий корпус и не являются тестовым инвариантом. Показанный UI процент — нормированный RRF балл относительно лучшего результата, а не вероятность истинной релевантности.

## 2. Выбранный подход

Выбран **последовательный составной ответ с сохраняемыми контрольными точками**. Один HTTP шаг обрабатывает одну порцию или один этап объединения; после успешного шага результат фиксируется в БД. Это удерживает каждый вызов в существующем бюджете одного интерактивного обращения к локальной модели и позволяет явно остановиться между шагами. Одновременные вызовы модели не используются: локальный интерактивный слот сейчас один.

Один длинный NDJSON запрос со всеми вызовами проще, но теряет готовую работу при уходе пользователя и упирается в текущие 180 секунд сервера/210 секунд клиента. Фоновая задача, продолжающая работу после ухода, противоречит согласованной паузе. Обе альтернативы исключены из первой реализации.

### Поиск и формирование порций

1. Сохранить существующие `prepare_query`, dense/BM25, каноническую проверку `load_visible_retrieval_hits`, `drop_unmatched_blocks`, `drop_partial_title_matches` и `filter_mail_scope_blocks`. Строгий `mail_mode` применяется к каждой ветке и при дополнительном чтении доказательств авторства.
2. Для нового режима разрешить `merge_and_format` вернуть все блоки из ограниченного поискового набора без суммарного лимита `chat_max_context_chars`. Срез `merged[:req.top_k]` не применяется. Старый режим API с `top_k` остаётся доступным существующим клиентам; UI чата отправляет явный `source_scope=all_retrieved` и убирает выбор количества источников. Поведение `/search` не меняется.
3. После фильтров присвоить каждому блоку глобальный номер от 1 до `N`, построить снапшот источников и сразу вернуть его клиенту. Порции пакуются по фактической длине `format_context`, включая XML метаданные, происхождение письма, экранирование и глобальные номера. Порядок блоков соответствует ранжированию. Один блок, превышающий окно, делится по безопасным границам текста на фрагменты с **одним и тем же номером источника**; текст не отбрасывается молча. Пустые после фильтров результаты сохраняют нынешний ответ «нет источников» без LLM.
4. Суммарное число порций не ограничивается отдельным скрытым `top_k`: верхняя граница задаётся шириной поисковых веток и размером их блоков. Перед стартом API сообщает рассчитанное число шагов и не обещает завершение за 180 секунд целиком.

### Обработка и объединение

Промпт обработки порции отвечает на исходный вопрос только по её блокам и возвращает компактные факты с глобальными номерами источников и короткой подтверждающей выдержкой из соответствующего блока. Сервер проверяет структуру, принадлежность каждого номера порции и точное вхождение выдержки в текст блока. Неподтверждённые факты не попадают в сохранённый результат. Если ответ модели обрезан или не проходит проверку, шаг повторяется с меньшей порцией либо завершается исправимой ошибкой; прогресс предыдущих порций сохраняется. Пустой список фактов допустим: источник обработан, но не пригодился для ответа.

После завершения всех порций модель объединяет проверенные факты в один ответ на языке вопроса с действующим fallback локали UI. Если сводки не помещаются в окно объединения, применяется такой же последовательный уровень сокращения сводок; на каждом уровне номера и факты остаются проверяемыми. Итоговые `[N]` допускаются только для номеров, прошедших обработку и присутствующих во входных фактах объединения. Сервер валидирует ссылки перед публикацией ответа. При невозможности получить валидный итог показывается ошибка, а не убедительно выглядящий неполный ответ. Если все блоки помещаются в одно окно, используется нынешний прямой ответ LLM с теми же проверками номеров, без промежуточных фактов и дополнительного объединения.

Вопросы об авторстве остаются на специальном доказательном пути `authorship_evidence`: каждый доступный исходный фрагмент обрабатывается порциями, модель выбирает только точные выдержки, сервер проверяет выдержки против исходного текста, а окончательный ответ собирается детерминированно. Обычное объединение пересказов не должно приписывать авторство отправителю письма или автору цитируемого вопроса.

## 3. Сохранение, API и жизненный цикл

Добавить отдельное состояние `chat_answer_runs` с UUID запуска, владельцем `user_id`, привязанным `session_id` и сообщением ответа, снимком запроса и фильтров, нумерованными источниками, порциями контекста, проверенными результатами завершённых шагов, номером следующего шага, версией/lease и статусом. Контекст и промежуточные факты доступны только серверу и владельцу запуска; `GET` для UI возвращает источники, прогресс и безопасный код ошибки, но не скрытые тексты порций. Содержимое порций хранится временно: после успешного завершения или окончательного отказа оно удаляется, для приостановленных и исправимо ошибочных запусков действует срок хранения 7 дней; UI показывает истечение срока и предлагает новый вопрос. Удаление треда очищает связанные незавершённые запуски.

Начало запуска создаёт или проверяет принадлежащий пользователю тред и сохраняет пару сообщений: вопрос и пустой ответ со статусом генерации и источниками. Так источник и кнопка «Продолжить» доступны после перезагрузки страницы. Итоговая запись обновляет этот ответ атомарно ровно один раз. У повторного запроса шага с тем же `run_id` не должно быть второго вызова LLM после уже сохранённого результата или второго сообщения в истории.

Предлагаемый контракт: `POST /chat/runs` создаёт запуск и возвращает `run_id`, `session_id`, источники и число шагов; `GET /chat/runs/{id}` возвращает состояние только владельцу; `POST /chat/runs/{id}/step` выполняет **один** шаг и отдаёт прогресс либо итог через текущий поток с heartbeat; `POST /chat/runs/{id}/pause` отмечает паузу и прерывает активный вызов; `POST /chat/runs/{id}/abandon` окончательно закрывает черновик. Изменяющие запросы используют текущие auth/CSRF правила. Старые `/chat` и `/chat/stream` остаются для клиентов без нового режима.

Статусы: `preparing → running → paused → running → synthesizing → completed`; исправимый сбой переводит в `failed`, из которого «Продолжить» повторяет только незавершённый шаг. `abandoned`, `expired` и `stale` не возобновляются. Один пользовательский тред имеет не больше одного незавершённого запуска. Новый вопрос сначала помечает старый запуск `abandoned`, затем создаёт новый. Одновременные/повторные `step` защищаются атомарной версией и lease, поэтому два окна не запускают один шаг дважды. После перезапуска backend незавершённый lease истекает, а запуск становится `paused` без потери зафиксированных порций.

При «Остановить», `window.blur`, `visibilitychange` или уходе со страницы клиент посылает `pause` и отменяет текущий fetch. Если отмена пришла во время ответа модели, неполный результат этого шага не фиксируется; уже завершённые шаги остаются. Если сигнал `pause` не дошёл из-за закрытия страницы, сервер не начинает следующий шаг сам, а lease переводит запуск в `paused`. Возвращение в чат читает статус и источники из БД и **не отправляет** `step`, пока пользователь не нажмёт «Продолжить». Перед каждым продолжением сервер заново проверяет видимость и активное поколение источников; при удалении или замене любого из них переход в `stale` предотвращает смешение старых фактов с новым корпусом.

## 4. Интерфейс

В карточке текущего ответа сразу видны источники и состояние: «Поиск источников», затем «Обработано X из Y порций», «Объединяю ответ», «Остановлено», «Ошибка на порции X», «Ответ готов». Во время работы рядом со статусом находится «Остановить», при паузе или исправимой ошибке — «Продолжить». Кнопка возобновляет сохранённый запуск, а не запускает новый поиск. Когда пользователь вводит новый вопрос, предыдущий запуск закрывается; его карточка остаётся с источниками и пометкой «Остановлено».

Для каждого источника показывать состояние «ожидает обработки», «обработан» или «не обработан из-за остановки/ошибки». Нынешнее `in_model_context` нельзя заранее выставлять `true` всем: это ложно при паузе. История до нового поля сохраняет нынешнюю совместимость. Видимый процент переименовать в «оценка поиска относительно лучшего результата», без утверждения о вероятности релевантности.

Внутренние факты и промежуточные ответы модели пользователю не показываются как готовый ответ. Финальный текст появляется на этапе объединения и заменяется авторитетным результатом только после успешной проверки и сохранения. Кнопки, прогресс, источники и поток ответа не вызывают прокрутку чата и не переводят фокус с открытого списка источников. Ручное открытие/закрытие списка сохраняется между шагами. Локализовать состояния и ошибки на русском и английском.

## 5. Ошибки, ограничения и проверка

Сбой одного вызова, превышение времени или недействительный JSON оставляют запуск и источники видимыми, сохраняют законченные порции и показывают безопасный локализованный код этапа без ответа провайдера. При ручном продолжении повторяется только незафиксированный шаг. Таймаут 180 секунд и браузерный 210 секунд относятся к **одному** `step`, а не ко всему составному ответу. Истечение срока хранения или изменение исходных документов требует нового запуска; старые промежуточные факты не объединяются с новыми источниками. Ограничение ширины поиска объясняется в UI: «все найденные» не означает все документы базы.

При реализации проверить:

- синтетические 1, 2 и много порций, переполнение одним большим блоком, переполнение сводок при объединении, сохранение всех блоков после фильтров и постоянных номеров `[N]`;
- строгие режимы писем, удалённые/обновлённые документы, специальные вопросы об авторстве и недопустимые ссылки, в том числе ссылка из одной порции на номер другой;
- остановку во время LLM, после порции и во время объединения; ручное продолжение после закрытия/возврата окна, перезапуска backend и повторного `step`; отсутствие второго сообщения и чужого доступа к запуску;
- UI кнопок, прогресса и источников, новый вопрос после остановки, сохранение позиции прокрутки и фокуса на источнике, русский/английский текст;
- реальный приёмочный запрос про справочник причин больничного листа с письмами и без них: сравнить список после фильтров, число реально обработанных блоков, цитаты итогового ответа и время каждого шага. Не принимать сам красивый текст ответа за доказательство полноты обработки.

Продуктовые тесты и миграции пока не выполнялись. Реализация должна включать Alembic миграцию новой таблицы, целевые backend/frontend тесты и браузерную проверку в аутентифицированном UI. Независимые грязные изменения в общем `main` сохраняются; при коммите реализации добавляются только относящиеся к ней файлы.
