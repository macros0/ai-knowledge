# Массовая выгрузка исходных документов — дизайн

**Статус:** согласовано 2026-09-13; реализация не начата.

## 1. Цель и границы

Добавить администраторам фоновую выгрузку до 1000 исходных документов суммарным объёмом до 1 ГиБ. Результат формируется как несколько ZIP-частей не более 250 МиБ каждая и доступен 24 часа.

В экспорт входят только исходные файлы из `data/uploads/<doc_id>.<ext>`. OKF-концепты, чанки, вложения, staging и производные бандлы не включаются.

Функция не меняет документы и не требует four-eyes. Она считается контролируемой операцией массового вывода данных и доступна только роли `admin`.

## 2. Принятые ограничения

| Параметр | Значение по умолчанию |
|---|---:|
| Максимум документов | 1000 |
| Максимальный суммарный размер | 1 ГиБ (1 073 741 824 байта) |
| Максимальный размер ZIP-части | 250 МиБ (262 144 000 байт) |
| Активных заявок одного администратора | 1 |
| Ожидающих export-задач во всей системе | 3 |
| Одновременно формируемых экспортов | 1 |
| Созданий на администратора | 3 в скользящий час |
| Срок доступности результата | 24 часа |
| Общая квота готовых экспортов | 5 ГиБ |
| Резерв свободного места после сборки | 2 ГиБ |

Все значения задаются через `Settings` и переменные окружения. Увеличение лимитов требует повторного нагрузочного прогона.

## 3. Архитектура

### 3.1 Поток данных

1. Admin выделяет документы и отправляет `POST /api/documents/bulk-export` с `doc_ids`.
2. Backend удаляет повторяющиеся ID с сохранением порядка и выполняет единый preflight: формат ID, наличие активной записи, наличие исходного файла, фактический размер файла, лимиты пользователя и системы, квота и свободное место.
3. В одной транзакции создаются `Job(job_type="bulk_export", status="queued")` и обязательная audit-запись `document_bulk_export_requested`.
4. ID задачи попадает в отдельную in-memory очередь export-worker. Один worker последовательно собирает все части в `data/exports/<job_id>.building/`.
5. После успешной сборки каталог атомарно переименовывается в `data/exports/<job_id>.ready/`; затем в одной транзакции Job становится `completed` и пишется `document_bulk_export_completed`.
6. Admin видит части в панели задач и скачивает каждую через `GET /api/jobs/<job_id>/export/<part_number>`.
7. Перед отдачей файла backend синхронно фиксирует `document_bulk_export_download_started`. При недоступном аудите данные не отдаются.
8. По истечении 24 часов либо по ручному удалению ready-каталог выводится из доступа, Job сохраняется, а удаление фиксируется в аудите.

### 3.2 Отдельная очередь

Export использует таблицу `jobs` и существующие admin API/UI статусов, но отдельный `ExportQueue` и отдельный worker-поток. Это не позволяет чтению 700 МБ конкурировать за единственный worker с удалением и длительной LLM-перегенерацией.

Существующий `JobQueue` обязан владеть только `bulk_delete` и `bulk_regenerate`: recovery, pending-count и execution фильтруются по `JOB_TYPES`. Без этого после рестарта queued export ошибочно попадёт в ветку перегенерации.

Export-worker владеет только `bulk_export`. При старте он:

- удаляет собственные незавершённые `.building`-каталоги;
- переводит собственные `running`-задачи в `failed` с audit-событием;
- возвращает собственные `queued`-задачи в export-очередь;
- запускает очистку истёкших артефактов.

Горизонтальное масштабирование не вводится: приложение остаётся в принятом single-process/single-replica режиме.

## 4. Preflight и разбиение

Preflight завершается до создания Job. Ошибка любого документа отклоняет всю заявку.

Проверяются:

- список не пуст и содержит не более 1000 уникальных ID;
- каждый ID соответствует формату документа;
- каждая запись существует и имеет `deleted_at IS NULL`;
- ровно один исходный файл найден в корне `uploads_dir` по `<doc_id>.*`;
- найденный путь после `resolve()` остаётся внутри `uploads_dir` и является обычным файлом;
- фактический `stat().st_size` не превышает 250 МиБ;
- сумма фактических размеров не превышает 1 ГиБ;
- у пользователя нет queued/running export;
- за последний час пользователь создал менее трёх export-задач;
- число queued/running export-задач меньше трёх;
- объём ready-артефактов плюс оценка новой выгрузки не превышает 5 ГиБ;
- после записи оценки останется не менее 2 ГиБ свободного места.

Документы разбиваются жадно в порядке запроса. Следующий файл добавляется в текущую часть, если сумма размеров не превысит 250 МиБ; иначе начинается следующая часть. ZIP-служебные структуры и `manifest.json` оставляют небольшой запас: полезный размер части ограничивается `part_size_bytes - 1 МиБ`.

## 5. Формат артефакта

Имя части:

```text
documents-export-<job_id>-part-001-of-003.zip
```

Архив создаётся с `zipfile.ZIP_STORED` и `allowZip64=True`. PDF, DOCX и XLSX уже используют внутреннее сжатие; повторный deflate не оправдывает нагрузку CPU.

Путь документа внутри ZIP — в корне архива:

```text
<safe-original-filename>
```

`safe-original-filename` строится только из basename, без каталогов, управляющих символов и специальных сегментов `.`/`..`.
При коллизии имя получает детерминированный суффикс перед расширением:
`<stem>__<doc_id><extension>`; manifest хранит фактическое имя.

Каждая часть содержит `_manifest.json`:

```json
{
  "job_id": 42,
  "part_number": 1,
  "parts_total": 3,
  "documents": [
    {
      "doc_id": "03713ad7b0db416c",
      "filename": "Регламент.docx",
      "archive_path": "Регламент.docx",
      "size_bytes": 2032928
    }
  ]
}
```

Job не хранит абсолютные серверные пути. `result` содержит только безопасные метаданные:

```json
{
  "processed": 1000,
  "total_bytes": 734003200,
  "artifact_status": "available",
  "expires_at": "2026-09-14T12:00:00Z",
  "parts": [
    {
      "number": 1,
      "filename": "documents-export-42-part-001-of-003.zip",
      "size_bytes": 261000000,
      "document_count": 342
    }
  ],
  "errors": []
}
```

После expiry/manual delete `artifact_status` меняется на `expired`/`deleted`, а `parts` сохраняются как исторические метаданные без download URL.

## 6. API и авторизация

### `POST /api/documents/bulk-export`

- dependency: `require_role("admin")`;
- body: существующий `BulkOperationRequest`;
- success: `202` и сериализованный Job;
- `400`: пустой список или неверный ID;
- `409`: удалённый документ, отсутствующий/неоднозначный файл, активная задача пользователя;
- `413`: больше 1000 документов, файл больше лимита части или сумма больше 1 ГиБ;
- `429`: три создания за скользящий час; ответ содержит `Retry-After`;
- `503`: export-очередь заполнена либо обязательный аудит недоступен;
- `507`: нарушена квота ready-артефактов или резерв свободного места.

### `GET /api/jobs/<job_id>/export/<part_number>`

- dependency: `require_role("admin")`;
- Job обязан иметь `job_type="bulk_export"`, `status="completed"`, `artifact_status="available"` и неистёкший `expires_at`;
- часть выбирается по номеру из Job.result, а путь заново строится внутри exports root;
- перед FileResponse фиксируется обязательный `download_started`;
- ответ: `application/zip`, `Content-Disposition: attachment`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`;
- `404`: задача/часть не существует;
- `409`: задача ещё не готова;
- `410`: результат истёк или удалён;
- `503`: audit-write не выполнен.

Событие `download_started` является каноническим событием вывода данных. `FileResponse` не обещает достоверно различать полное скачивание и обрыв клиента, поэтому событие `download_completed` в первую версию не входит.

### `DELETE /api/jobs/<job_id>/export`

- dependency: `require_role("admin")`;
- удаляет только готовые export-артефакты;
- Job и исторические метаданные остаются;
- операция фиксируется как `document_bulk_export_deleted`.

## 7. Аудит

Добавляются action types:

- `document_bulk_export_requested`;
- `document_bulk_export_completed`;
- `document_bulk_export_failed`;
- `document_bulk_export_download_started`;
- `document_bulk_export_expired`;
- `document_bulk_export_deleted`.

`requested` хранит полный массив doc_ids, count, total_bytes, parts_estimated и лимиты. Остальные события ссылаются на `job_id`; download дополнительно хранит part_number, filename и size_bytes.

Job transition и соответствующий audit append выполняются через `audit.record_in_session()` в одной SQL-транзакции. Если транзакция completion не фиксируется, ready-каталог удаляется, а Job остаётся recoverable как running. Если audit download-start не фиксируется, FileResponse не создаётся.

Создавать 1000 audit-строк на одну read-only выгрузку не требуется: точный состав неизменно хранится одной JSON-записью requested. Существующий per-document аудит массовых мутаций не меняется.

## 8. Очистка и гонки

ExportQueue ведёт in-process lease-счётчик скачиваемых частей. Cleanup и manual delete не трогают часть с активным lease. `BackgroundTask` FileResponse освобождает lease после завершения ответа; при обрыве процесс также освобождает его в cleanup callback.

Expiry/manual delete выполняются так:

1. Под общим export-lock ready-каталог переименовывается в `.deleting` и перестаёт быть доступен новым скачиваниям.
2. В одной транзакции обновляется `artifact_status` и добавляется audit-событие.
3. При ошибке транзакции каталог возвращается в `.ready`.
4. После commit `.deleting` удаляется. Ошибка физического удаления не возвращает доступ; следующий cleanup повторяет удаление.

Истёкший артефакт не удаляется без audit-записи. Это может временно удержать место при недоступной БД, но сохраняет обязательность аудита.

## 9. UI

Администратор может выделить до 1000 документов. Для editor остаётся лимит выделения 50.

Лимиты действий разделяются:

- экспорт: до 1000, только admin;
- теги: до 50;
- удаление: до 50;
- перегенерация: до 20.

При превышении лимита конкретная кнопка отключается и показывает причину; само выделение не сбрасывается. Кнопка «Выгрузить исходники» подтверждает количество документов и отправляет задачу.

AdminPanel отображает `bulk_export`, прогресс `processed/total`, общий объём, expiry и отдельную ссылку на каждую готовую часть. Скачивание выполняется обычной ссылкой на same-origin endpoint, без `fetch().blob()`, чтобы браузер не держал 250 МиБ в памяти. Автоматический запуск нескольких скачиваний не используется.

SecurityPanel получает названия всех новых audit actions и продолжает экспортировать их в CSV.

## 10. Проверка и эксплуатационные критерии

Функциональные критерии:

- viewer/editor/security получают 403 на create/download/delete; admin получает доступ;
- 1000 документов принимаются, 1001 отклоняется;
- 700 МиБ разбиваются примерно на три части, каждая не превышает 250 МиБ;
- дубли ID и одинаковые имена не создают дубликатов/коллизий;
- deleted/missing/ambiguous source отклоняют заявку целиком;
- частичный результат никогда не публикуется;
- restart корректно разделяет ownership JobQueue и ExportQueue;
- expiry/manual delete безопасны при активном скачивании;
- все обязательные audit events содержат согласованные поля;
- отказ audit-write блокирует создание или начало скачивания.

Нагрузочная приёмка на целевой машине использует 1000 синтетических файлов общим объёмом 700 МиБ. Во время сборки параллельно выполняется baseline-набор поисковых запросов.

Критерии:

- дополнительный RSS backend не превышает 150 МиБ;
- ни один ZIP-процесс не загружает весь файл/архив в память;
- поиск не получает 5xx;
- p95 latency поиска ухудшается не более чем на 20% относительно baseline;
- после expiry/failure в exports root нет незарегистрированных ready/building файлов;
- каждая 250-МиБ часть скачивается через Next API proxy и production reverse-proxy без буферизации всего ответа.

## 11. Миграции и откат

Миграция БД не требуется: `jobs.job_type`, `jobs.status`, `jobs.params`, `jobs.result` и audit action_type являются строками/JSON без DB enum или нового столбца.

Откат выполняется конфигурационным флагом `BULK_EXPORT_ENABLED=false`, который скрывает UI и заставляет create endpoint отвечать 404/feature-disabled. Уже готовые части остаются доступны администраторам до TTL, чтобы отключение новых заявок не обрывало согласованную выгрузку. Полное аварийное прекращение выдачи выполняется отдельным `BULK_EXPORT_DOWNLOAD_ENABLED=false`.

При откате кода queued/running bulk_export Job переводятся служебным rollback-скриптом в failed, а ready/building каталоги удаляются с обязательной audit-записью. Qdrant, LLM, документы и исходные файлы не изменяются.
