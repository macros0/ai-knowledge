# Обработка таблиц: проект решения

Дата: 2026-10-09. Статус: R1 разрешён и реализован в `main`; результаты и ограничения в [отчёте R1](../reports/2026-10-09-table-processing-r1.md). Структурный R2 и точные операции R3 остаются будущими этапами.

## Цель и согласованный охват

Надёжно извлекать Excel, включая XLSX-вложения в DOCX, сохранять значения и происхождение ячеек, делать широкие таблицы пригодными для поиска и проверяемого ответа. Общие механизмы классификации, разбиения, диагностики и поиска применяются также к уже распознанным таблицам DOCX/PDF. OCR и новое распознавание геометрии PDF не входят.

Пользователь выбрал: «Excel и общие механизмы; точные запросы отдельным этапом». Планирование не разрешает изменение реализации, перегенерацию корпуса, commit, push или deployment.

## Подтверждённая исходная точка

Контрольный локальный документ A: 106 табличных блоков; два широких блока XLSX — 316 столбцов × 344 строки и 172 × 397. Это строки текущего Markdown-представления: после восстановления шапок часть может оказаться заголовками, а не данными.

Два отдельных запроса к local_qwen воспроизвели finish_reason=length при 512 выходных токенах: модель перечисляла сотни индексов description_cols. В build_row_concepts этот список не определяет сохранённые ячейки: сохраняются все колонки. Это дефект контракта ответа, отдельный от переполнения входного контекста.

В БД сохранены 344/397 строковых концептов и по одному обзорному. Мультимножества ожидаемого и сохранённого содержимого строк совпали. Это доказывает сохранность строк ПОСЛЕ парсинга, но не корректность исходных шапок, формул или поиска. У второго блока только 9 непустых заголовков из 172.

Текущий xlsx_parser использует read_only=True, data_only=True, первую непустую строку как шапку, пропускает пустые строки и рендерит лист целиком в Markdown. Структура Excel теряется до генерации. Существующие source_id, поколения публикации, программное извлечение строк и строгие JSON-проверки сохраняются.

## Подходы

1. Только поднять лимит ответа: небольшой патч, но стоимость зависит от ширины, а шапки и поиск остаются прежними.
2. Компактный классификатор и структурные таблицы с производными поисковыми фрагментами — рекомендуемый вариант: проверяемые значения и координаты, независимые проверки полноты и поиска.
3. Сразу агент SQL/Python: преждевременно без надёжной структуры. Ограниченный табличный исполнитель выделяется в следующий проект.

## Архитектура

Оригинал → структурная таблица → нормализованные шапки → компактная классификация → строки/группы колонок → существующие concept/chunk индексы → контекст ответа → ссылка на исходные ячейки.

Каноническое представление хранит значения, типы, координаты и происхождение. Поисковое представление производно: может опускать пустые ячейки и повторять ключ строки, но не заменяет оригинал.

Предлагаемые структуры docparser.table_model:

- TableCell: адрес A1, raw_value, display_text, тип, formula/cached_value при наличии, состояние value|blank|formula_missing|error и merge anchor.
- TableColumn: исходный индекс/буква, путь заголовка и координаты элементов шапки. Одинаковые имена разных колонок не схлопываются.
- TableRow: исходный номер строки и разреженная карта ячеек.
- TableDescriptor: source_id, table_id, sheet_index/name, диапазон, строки шапки, columns, версия схемы/нормализатора, метод и предупреждения.
- TableRef: generation_id, source_id, table_id, row_number, исходные индексы колонок; для продолжения длинной ячейки — диапазон текста.

Table ID детерминирован в пределах поколения по source_id, индексу листа и исходному диапазону; стабильность между изменёнными файлами не обещается. DOCX использует структурный номер таблицы/строки/ячейки; PDF не получает выдуманные Excel-адреса.

Таблицы передаются порциями через TableSink. Block.meta содержит дескриптор/ссылку, не вторую копию таблицы. Публичный parse_document сохраняет Markdown-совместимость; backend использует структурный режим parse_document_result. Вложения наследуют sink, сохраняя свой source_id.

Предлагаемое хранение: document_tables и document_table_rows с doc_id + generation_id. Candidate сохраняется до публикации и недоступен пользовательскому поиску. Nullable JSON table_refs в концептах/чанках связывает их с канонической таблицей. Новые поля совместимы с legacy без массового backfill. Публикация, cleanup, backup и restore учитывают новые записи.

## Правила Excel

- Чтение ограничено по памяти; merge/форматы/диапазоны извлекаются из OOXML с ZIP/XML-защитой. Не загружать все книги целиком ради merge.
- Текст объединённой шапки распространяется только внутри её диапазона; уровни соединяются сверху вниз, соседние повторы убираются.
- Excel Table имеет приоритет; обычные листы анализируются по геометрии/merge/типам. Несколько таблиц на листе сохраняются. Пустая строка не является единственным основанием границы.
- Неоднозначная шапка сохраняет спорные строки и координатные имена колонок с warning; LLM не разрешено молча удалить предполагаемую шапку.
- Blank, 0, False, пустая строка формулы и отсутствующий кэш различаются. Сохраняются исходное число, формат кодов и отображаемые ведущие нули.
- Формулы/макросы/внешние ссылки не исполняются. Формула без кэша даёт явное состояние. Вертикальный merge данных сохраняется как отношение, без бесконтрольного размножения значений.
- Скрытые строки/колонки остаются в прежнем охвате извлечения, признак скрытия сохраняется. Markdown/HTML в значениях экранируется.

## Классификация и проекции

Новый table-classification ответ содержит способ извлечения, колонку названия и тип концепта. description_cols не генерируется. Старый кэш не удаляется глобально; новый ключ включает версии, модель, prompt hash и хэш всей отправленной выборки.

Preview ограничен. Предлагаемые исходные параметры: 12 колонок × 3 строки, 160 символов одной ячейки, 12 000 символов всего user input; индексы колонок исходные. Это параметры приёмки, не гарантия вместимости модели: токенный бюджет проверяется отдельно. Ограничение preview не ограничивает сохраняемые данные.

Небольшая строка — один фрагмент. Сверхширокая — несколько по группам колонок с повторением ключа строки/пути шапки. Длинная ячейка получает продолжения с точными диапазонами текста. Каждая часть имеет собственный fragment_id и общую идентичность строки. Это необходимое исключение из совета не разрезать строку, если она шире окна.

В поисковый текст добавляются название листа/таблицы и заголовки из источника. LLM-сводка не требуется в первом выпуске. Сначала измеряется существующий BM25+dense+RRF на новом представлении; бонусы всем таблицам и повышение top_k без гипотезы не вводятся.

## Качество, UX и ссылки

Постоянный отчёт на таблицу хранит метод, версии, покрытие строк/ячеек, header status и безопасный код причины; переживает staging cleanup. Неизвестное покрытие — null, не 100%. Логи/публичная диагностика не содержат тексты ячеек, промпты и provider traceback.

Различаются подтверждённый пропуск, неоднозначная структура и резервный метод при проверенном покрытии. Последний не доказывает правильность шапки. Старое предупреждение не снимается без новой проверки.

Переход из ответа показывает конкретные ячейки того же поколения. Старый snapshot не перенаправляется на новую версию; после удаления старого поколения источник явно недоступен. ACL/trash/source scope действуют и для табличных endpoints.

## Выпуски и критерии

R1: компактный классификатор, широкие regression fixtures, сохраняемая диагностика. R2: структура Excel, шапки, хранение поколений, проекции, ссылки, корпусная приёмка и управляемая миграция. R3: отдельная спецификация точных фильтров/подсчётов после R2; разрешённые типизированные операции, без произвольного кода модели.

Обязательны полное покрытие непустых ячеек на размеченных fixtures либо явный пропуск, правильные типы/нулевые значения, сохранение повторных строк, точные ссылки, отсутствие междокументного/межверсионного смешения. Метрики поиска/ресурсов фиксируются до изменений.
