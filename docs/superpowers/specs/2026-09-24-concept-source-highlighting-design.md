# Подсветка места происхождения концепта — дизайн

## Цель и существующий путь

Пользователь открывает источник из ответа чата и попадает на страницу OKF-концепта. На странице концепта уже есть переходы к «Весь документ» и к связанному чанку. После перехода пользователь должен сразу видеть исходное место, на котором основан концепт: страница прокручена к нему, место устойчиво подсвечено. Путь из чата к концепту сохраняется. Чисто чанковые источники чата, у которых нет концепта, продолжают вести к чанку.

Под «документом» в этой доработке понимается существующая страница извлечённого Markdown-текста `/documents/{doc_id}/fulltext`, собранного из `document_chunks`. Подсветка в нативном PDF/DOCX/XLSX потребует отдельной модели координат и просмотрщиков форматов и в этот объём не входит.

## Поведение интерфейса

На странице концепта рядом с текущими переходами появляется блок «Место в источнике» с кратким исходным фрагментом, состоянием точности и действиями «Показать в документе» и «Показать в чанке». Оба действия передают в URL только `doc_id` и `concept_slug`, без текста цитаты. Прямой переход, перезагрузка и браузерная навигация назад сохраняют результат.

Обе страницы назначения загружают сведения о месте концепта. При точной привязке раскрывают скрытую часть большой таблицы, если она содержит цель, прокручивают первый фрагмент примерно к центру видимой области и подсвечивают соответствующий абзац, строку таблицы, блок комментария или иной ближайший визуальный блок. Подсветка сохраняется до ухода со страницы и при переключении между форматированным и raw-видом. Для нескольких мест показывают счётчик «1 из N» и кнопки перехода между ними. Обычные переходы на документ или чанк без `concept` сохраняют прежний вид. Ручной URL с концептом и чужим номером чанка переводит на связанный с концептом чанк.

Точность выражается четырьмя состояниями:

| Состояние | Условие | Поведение |
|---|---|---|
| `exact` | Есть сохранённые диапазоны, совпали хэш и текст чанка | Подсветка конкретных блоков; навигация между диапазонами |
| `recovered` | Диапазоны отсутствуют (`source_spans = NULL`), а полный текст концепта дословно и однозначно найден в текущем чанке | Подсветка с пометкой «Фрагмент найден в тексте»; эта привязка не выдаётся за сохранённое подтверждение |
| `chunk` | Есть только `chunk_index` либо точная привязка устарела | Прокрутка к началу чанка и надпись «Точное место не определено»; весь чанк не выдаётся за точную цитату |
| `unavailable` | Нет связанного чанка или его текста | Документ/концепт остаётся доступным; показывается причина без фиктивной подсветки |

Для старых концептов без диапазонов действует `chunk` либо `recovered` при однозначном дословном совпадении полного текста. Массовая повторная генерация существующих документов не нужна. Если документ регенерирован и прежние диапазоны не соответствуют текущему хэшу чанка, UI деградирует до `chunk`, а не восстанавливает привязку по тексту концепта.

## Контракт данных

У `OkfConcept` появляется nullable JSON-поле `source_spans`. Каждый элемент — полузакрытый диапазон `[start, end)` в Python Unicode code points исходного **сохранённого** текста собственного чанка и SHA-256 этого текста. `chunk_index` остаётся отдельным существующим полем. Диапазоны отсортированы, не выходят за границы чанка и не берутся из пересказанного `content` концепта. Ровно этот текст сохраняется в `DocumentChunk.content` и выдаётся страницами просмотра.

Новый read-only ответ `/api/documents/{doc_id}/concepts/{slug}/source-location` возвращает `status`, `chunk_index`, валидные диапазоны и короткие цитаты, вычисленные сервером из текущего чанка. Он проверяет принадлежность концепта документу, наличие документа и чанка, диапазоны и `content_hash`; не возвращает серверные пути и не доверяет URL-диапазонам. Для просмотра всего документа нужен ответ со списком чанков в порядке `chunk_index`; существующий plaintext `/fulltext` сохраняется для совместимости.

При генерации программных концептов из таблиц и комментариев диапазон определяется по исходному чанку до замены блока заглушкой. Для LLM-концептов модель возвращает до трёх коротких дословных фрагментов-оснований, отдельно от формулировки концепта. Каждый фрагмент должен однозначно находиться в исходном чанке; неподтверждённый или неоднозначный фрагмент отбрасывается. Отсутствие точной привязки не останавливает генерацию концептов. Сохранение в staging, финализация в PostgreSQL и `resume` переносят диапазоны без пересчёта по новому тексту.

## Отрисовка и устойчивость

Frontend применяет диапазоны к исходному тексту чанка, не к объединённой строке `/fulltext`. Весь документ выводится по чанкам с устойчивыми DOM-якорями. Markdown остаётся форматированным. Для подсветки достаточно ближайшего семантического блока; точные границы исходного фрагмента и цитата остаются в данных. Большие таблицы по-прежнему нарезаются до Markdown-парсинга; для целевой строки хранится соответствие исходных строк нарезанным частям и автоматически раскрывается нужный хвост. Смещения Unicode преобразуются на клиенте перед работой со строками JavaScript, поскольку их индексы используют UTF-16.

Проверить как минимум: текст с emoji, несколько одинаковых цитат, концепт с несколькими основаниями, строку после 300-й в большой таблице, комментарий, таблицу, устаревший хэш, старый концепт только с `chunk_index`, отсутствующий чанк, обычный переход без `concept`, прямой URL и браузерный Back. Тесты должны проверять видимый результат и прокрутку, а не только наличие CSS-класса в исходнике.

## Не входит в эту доработку

- Перенаправление цитаты `[N]` из чата сразу в документ.
- Подсветка поверх изображения страницы PDF или в нативном DOCX/XLSX.
- Обязательная регенерация старых концептов или подсветка по пересказу.
- Новая индексация Qdrant: диапазоны читаются из PostgreSQL по концепту.
