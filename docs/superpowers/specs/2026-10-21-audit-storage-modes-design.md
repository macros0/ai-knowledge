# Три режима аудита: локальный журнал и внешний канал

Дата: 21.10.2026. Статус: согласовано; реализация в ветке `codex/audit-storage-modes`.
Основание: текущий checkout main, HEAD `c1b321f`, и согласование в чате.
Изменение `backend/pyproject.toml`, существовавшее до этой работы, не относится к проекту.

## 1. Согласованная цель

Заказчик выбирает только БД, только внешний аудит либо оба канала. Полное
отключение аудита недопустимо. Техническая очередь внешнего канала остаётся
в БД. Во всех режимах одинаковый набор событий, включая вход, выход и отказы
доступа; обязательный security-аудит становится строгим и в режиме только БД.
Последнее отдельно подтверждено пользователем при планировании.

Внешний канал означает приложение → JSON в stdout → сборщик → OpenSearch.
Приложение подтверждает только запись в stdout, а не получение индексом.
Существующий выбор native/logstash сохраняется.

«Только внешний аудит» означает отсутствие новых строк постоянного журнала
`audit_log`. Это не отсутствие SQL-записей вообще: остаются outbox, данные
приложения и необходимые для его функций версии/результаты операций.

## 2. Что установлено по текущему коду

- `services/audit.py:record_in_session` всегда создаёт AuditLog; при durable
  добавляет AuditOutbox в ту же транзакцию.
- `db/models.py:AuditOutbox.audit_id` одновременно PK и FK на `audit_log.id`.
  Самостоятельная запись outbox сейчас невозможна.
- `audit_runtime.delivery_status` вычисляет возраст pending через JOIN с журналом;
  preflight проверяет INSERT журнала и права его sequence даже для внешнего канала.
- `audit_security.enabled` привязан к stdout. От него зависят auth-события,
  строгая запись login/logout и часть security transaction boundaries.
- `processing_scope.append_scope_audit` напрямую создаёт AuditLog, обходя общий
  сервис и outbox. Этот путь должен участвовать в выборе каналов.
- `locale_service.stopwords_history/rollback_stopwords` читают из AuditLog полные
  снимки импорта. `scripts/migrate_glossary_identities._previous_result` использует
  журнал как подтверждение уже применённой миграции.
- `audit_schema` и model-free `audit_hold` строго проверяют текущую схему.
  Миграция 066 вызывает функции из runtime-модуля: изменение этих функций без
  изоляции прежнего контракта может сломать воспроизводимость старой миграции.
- Автоматической очистки outbox и журнала сейчас нет. `audit_retention_days`
  не означает работающий сборщик мусора.

## 3. Конфигурация и варианты решения

Рекомендуется добавить `AUDIT_DB_ENABLED` с default `true`, сохранить
`AUDIT_STDOUT_MODE=disabled|durable` и валидировать их совместно.
Это сохраняет действующие deployment-конфигурации без переименования переменных.

| Пользовательский режим | AUDIT_DB_ENABLED | AUDIT_STDOUT_MODE | Новые AuditLog | Новые outbox |
|---|---|---|---|---|
| Только БД (default) | true | disabled | Да | Нет |
| Только внешний аудит | false | durable | Нет | Да |
| Оба канала | true | durable | Да | Да |
| Запрещено | false | disabled | Запуск отклоняется | Запуск отклоняется |

Альтернативы: единый `AUDIT_MODE=db|external|both` проще сам по себе, но требует
правил совместимости с существующим stdout-флагом; два независимых переключателя
без общей валидации допускают запрещённый четвёртый режим. Их не выбираем.

Одна функция вычисляет эффективный режим; остальной код не повторяет комбинации
флагов. Валидация до startup seeds, фоновых работ и пользовательских операций.
Неверные значения и запрещённая комбинация не получают молчаливого fallback.
Менять режим можно только конфигурацией развёртывания и перезапуском.

В Helm добавить `runtime.auditDbEnabled`, проверки типов/комбинации и запрет
дублирования `AUDIT_DB_ENABLED` через `runtime.config`. Default values сохраняют
только БД. Обновить `.env.example` и deployment-примеры всех трёх режимов.

## 4. Независимое событие и очередь

Создавать данные события, UTC timestamp и UUID event_id до выбора получателей.
Формирование события не должно требовать добавленной в session строки AuditLog.
Журнал сохраняет прежние подробные old/new/meta; внешний payload сохраняет
существующую очистку по разрешённым полям. Равенство аудита означает одинаковые
факты/типы событий, а не выдачу полного внутреннего снимка во внешний канал.

Outbox v2 получает собственные `id` (целочисленный PK), `event_id` (unique),
`created_at`, неизменяемый canonical payload и прежние поля доставки. FK на журнал
не нужен: при двух каналах корреляция по event_id. Выборка, marker, retry, hold и
возраст очереди используют только outbox. Canonical/wire schema событий не меняется.

Запись выполняется через один `record_in_session`:

- Только БД: вставка AuditLog, без outbox.
- Только внешний аудит: вставка outbox, без AuditLog.
- Оба: обе вставки в одной транзакции; ошибка любой вставки откатывает обе.

Существующие обязательные security-операции коммитятся вместе с выбранными
получателями. Прочие domain transaction boundaries проверяются по местам вызова;
рефакторинг не объявляет автоматически атомарными все бизнес-операции.
HTTP-запросы не ждут stdout или OpenSearch. Ошибка обязательной SQL-записи запрещает
успех связанной операции; отказ доступа сохраняет 401/403/redirect при сбое аудита.

Сохранить ограничения denial path: admission, deadlines, cleanup ownership,
неподдержанные DB profiles, отсутствие выдачи доступа при ошибках. Их preflight
распространяется на режим только БД, поскольку auth-аудит в нём тоже включён.
Transport/preflight stdout и запуск dispatcher по-прежнему нужны только durable.
Серверный request_id/actor context должен формироваться во всех трёх режимах.

Прямую вставку из processing_scope перевести на общий сервис с сохранением
транзакции, actor и разрешённого request context. Повторно проверить все места
создания/чтения AuditLog и пользователей результата `record/append`: SQL `id`
может отсутствовать в external-only; нельзя подставлять вместо него outbox.id.
Сохранить прежние поля результата, nullable `id` и отдельный event_id; публичные
строки истории БД сохраняют свои настоящие id.

Счётчик recorded учитывает одно событие после root commit, не два получателя.
Rollback/savepoint rollback не увеличивает счётчики. Payload и SQL-параметры
не попадают в status/диагностические ошибки.

## 5. Функции, которые сейчас используют журнал как рабочие данные

Нельзя реализовать external-only скрытым сохранением части AuditLog либо чтением
из outbox для пользовательской истории. Outbox содержит очищенный payload,
не является хранилищем версий и имеет собственный жизненный цикл.

Внести два узких изменения в обязательный объём:

1. Выделить таблицу снимков импорта стоп-слов: locale, kind, before/after words,
   actor, timestamp, метаданные импорта и идентификатор для существующего history/
   rollback API. Импорт записывает снимок и аудит в одной транзакции. Перенести
   имеющиеся снимки из AuditLog без удаления исходных записей и с сохранением
   старых history id; новые id выдаёт собственная sequence после перенесённого max.
   Сохранить preview/CAS, проверку locale/kind и существующие правила пустого отката.
2. Выделить таблицу результатов миграции идентичностей глоссария с уникальным
   checksum плана и result_checksum. Применение, результат и аудит атомарны.
   Повторный запуск читает эту таблицу. Перенести исторические подтверждения
   детерминированно (прежний выбор последней записи на checksum); противоречивые
   или неполные данные требуют диагностики, без выдуманных успешных результатов.
   Обновить изолированную simulation_session для новых моделей.

Это сохранение существующего поведения, не новая универсальная система истории.
Таблицы работают одинаково во всех режимах; права соответствуют исходным
domain API, а не открывают техническую очередь пользователям.

## 6. Переключение режимов и интерфейс

Режим влияет только на новые события после перезапуска. Старый AuditLog остаётся
доступным роли security. История не переносится в OpenSearch, события external-only
не достраиваются задним числом в AuditLog при возврате локального журнала.

При отключении stdout ранее созданные pending сохраняются без отправки; CLI
показывает приостановленную доставку и остаток. Повторное включение durable
продолжает pending с исходными event_id/time/payload. Held автоматически не снимается;
stdout_written автоматически не переигрывается. Переключение both ↔ external
не меняет уже существующие задания. Изменение формата сохраняет текущий контракт.

Добавить защищённый `GET /audit/config` (роль security, Cache-Control: no-store):
effective_mode, db_enabled, stdout_mode, stdout_format. Не включать секреты,
адрес индекса или недоказанное «OpenSearch подключён». Существующий `/audit`
и клиентский `listAudit` сохраняют формат и фильтры.

SecurityPanel показывает локализованные RU/EN режим и пояснение. В external-only:
«Запись локального журнала отключена. Новые события направляются во внешний
канал аудита. Здесь доступна сохранённая история». При пустой истории пояснять
отсутствие локальных записей, не утверждать отсутствие событий вообще.
Экспорт CSV и агрегаты явно относятся к показанным локальным записям, не к полному
внешнему аудиту. Управление блокировками остаётся доступным по прежним правам.
При ошибке загрузки режима показывать неизвестное состояние, не подразумевать DB.

## 7. Миграция, права, восстановление

Новая версия схемы после актуального Alembic head (перепроверить при реализации).
Не менять смысл ранее выпущенной 066: выделить её v1 helper/контракт и сохранить
воспроизводимость цепочки fresh install → v1 → v2, включая историю миграций.
Runtime проверяет v2; operator hold явно распознаёт поддержанные v1 и v2,
не принимает произвольную drifted-схему.

Миграция при остановленных writers переносит все строки outbox, сохраняя payload
байт-в-байт, event_id/time, status, attempts, retry time, errors и marker. Старый
audit_id можно перенести в новый id, после чего корректно выставить sequence.
Timestamp/event_id извлекать и сверять с текущими данными; при нарушении контрактов
отказаться до частичного переключения. Никаких новых pending из старого AuditLog.
В той же поставке мигрировать функциональные snapshots/receipts из раздела 5.

Поддержать PostgreSQL, SQLite и отдельный dev/create_all migration tool.
Создание новых таблиц через create_all не исправляет существующую схему.
Проверить transactional rollback миграции и повторный безопасный запуск.

Preflight прав соответствует выбранным каналам: external-only не требует INSERT
или USAGE sequence AuditLog, но требует INSERT/SELECT и sequence outbox, UPDATE
только delivery columns. Чтение старого журнала для UI может требовать SELECT.
DB-only требует запись журнала и права для bounded security path; запись outbox
не требуется. Права на рабочие domain-таблицы проверяются отдельно. DELETE журнала
или outbox приложению не добавляется.

Restore сохраняет обязательный hold pending до первого запуска writers.
Старый бинарник не считать совместимым с v2: его строгий schema validator
отвергнет её даже при disabled. План отката — до запуска новой версии восстановить
проверенную копию до миграции в отдельное окружение; после появления новых событий
предпочесть исправление вперёд. Автоматический downgrade, потеря новых событий и
создание фиктивных AuditLog ради старого FK запрещены. Процедура возврата к backup
должна явно учитывать новые данные и не объявляться без потерь.

## 8. Хранение очереди и границы объёма

Автоматическая очистка не входит в этот этап. Не удалять pending/held и не
использовать stdout_written как подтверждение доставки OpenSearch. Существующий
status сохраняет counts/age/errors, расширяется эффективным режимом и фактом
приостановки pending. Очередь продолжит занимать место, включая stdout_written;
external-only убирает дублирование постоянного журнала, но не весь рост БД.

Отдельный следующий проект — согласованная retention/replay/GC политика очереди
с учётом сборщика и целевого хранилища. В этом этапе нет прямого клиента OpenSearch,
нового ACK-протокола, изменения формата payload, фонового backfill, настройки
каналов через UI, изменения количества workers или deployment в среду заказчика.

## 10. Критерии приёмки

- Три разрешённые комбинации валидны в Settings и Helm, четвёртая отклоняется
  до запуска workers. Старая конфигурация выбирает прежние каналы; усиление
  auth-аудита в DB-only явно описано как согласованное изменение поведения.
- Одинаковые сценарии дают одинаковые типы/количество событий в выбранных
  каналах; external-only не создаёт ни одной новой AuditLog, включая scope changes,
  auth, background и operator paths. Both сохраняет одинаковые event_id/time.
- Отказ каждой вставки и rollback/savepoint не оставляют половины пары или
  ложных счётчиков. Login/logout/block/unblock сохраняют выбранную атомарность;
  denied request не превращается в success при неисправной БД.
- Импорт/история/rollback стоп-слов, старые history id и идемпотентная миграция
  глоссария работают во всех режимах, включая их переключение.
- Для каждой пары переходов проверены новые события, pending, held и written:
  нет удаления, неожиданных replay/backfill или появления новых локальных строк.
- SQLite и отдельный PostgreSQL: fresh chain, v1 upgrade, dev drift tool,
  preservation counts/bytes/states, отказ неизвестной схемы, sequence и минимальные
  права; старый бинарник безопасно отказывает на v2. Основная БД не используется.
- Process tests: restart, частичный stdout write, ошибка marker, недоступный sink,
  retry/dedup identity, hold после restore. Проверить native и logstash.
- API/UI: прежние security/RBAC, сохранённая история, пустое/ошибочное состояние,
  корректные RU/EN сообщения, CSV/агрегаты только по локальной выборке.
- Пройти профильные backend tests, frontend tests/build, обязательные project
  checks по AGENTS.md. Полный regression и реальные средовые проверки отражать
  отдельно, не заменять их количеством узких tests.
- Для отдельной интеграционной приёмки external-only: synthetic request → outbox
  → stdout → тестовый OpenSearch по event_id; AuditLog delta = 0. Проверка обеих
  копий в both. Запуск в целевом окружении заказчика — отдельная приёмка;
  прежние отчёты не подтверждают новую v2 автоматически.

## 11. Текущий статус

Согласованы три режима, сохранение SQL-очереди и единый набор событий со строгим
обязательным security-аудитом. Пользователь разрешил автономную реализацию в
отдельной рабочей ветке. Реализация выполняется в `codex/audit-storage-modes`;
состояние проверок и средовые границы см. в отчёте
`../reports/2026-10-21-audit-storage-modes-acceptance.md`. Основная БД не мигрируется.
