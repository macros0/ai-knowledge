# Оптимизация подготовки и отображения источников чата — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Выполнение начато 02.10.2026 по явному указанию пользователя автономно выполнять план.

**Goal:** Устранить лишнюю работу при подготовке и отображении 167–200 источников, сохранив полный результат поиска, выбор источников и отзывчивость чата.

**Architecture:** Сначала измерить отдельно сервер, передачу событий и React. Изолировать ввод вопроса, сообщения, текст ответа и список источников; сохранять ссылки на неизменившиеся данные и размонтировать содержимое свёрнутого списка. Затем сокращать подтверждённые повторные чтения на сервере внутри того же согласованного снимка БД, сохраняя глубину и правила поиска.

**Tech Stack:** Next.js 16, React 19, NDJSON streaming, FastAPI, SQLAlchemy/PostgreSQL, Qdrant, существующий Node test runner и pytest.

**Spec:** Требования, факты диагностики и рекомендуемое поведение зафиксированы ниже в этом документе. Исходный сценарий пользователя: «ЭЛН», глубина 200, 167 источников, задержка при подготовке данных для отображения.

## Ограничения

- Число найденных источников не зависит от лимита контекста LLM. Сохраняются `in_model_context`, нумерация, ссылки, выбор документов/фрагментов и ответ по выбранным.
- `search_depth` в новых режимах ограничивает итоговые фрагменты после merge/filter; legacy `top_k` сохраняет отдельный контракт.
- Не снижать глубину 200, не обрезать список до 20/40 результатов, не исключать замечания или письма ради скорости.
- Не менять ранжирование, sparse-токенизацию, RRF, фильтры и границы текстов. Реиндексация не требуется.
- Сохранять проверки владельца попытки, видимости, активной генерации, почтовой принадлежности и исходных цитат. Не переносить выдачу selectable-источников перед сохранением их ссылок в БД.
- Не менять общий `MarkdownViewer` для всех экранов ради локальной оптимизации чата без отдельного доказательства необходимости.
- Существующие незакоммиченные изменения в рабочем каталоге не включать в реализацию. Особенно это касается `globals.css`, переводов и соседних планов.
- Новые библиотеки виртуализации и глобального состояния на первом этапе не нужны.

Разложение первого прогретого запроса 200:

|---|---:|---:|---:|
| 200 | 158 | 38 мс | 27 мс |

Повторная работа подтверждена, но **состав, порядок и scores между проходами различаются**, несмотря на одинаковый count. Проверено сравнением идентичностей блоков `(doc_id, source_slug, chunk_index, kind)` и scores. Поэтому ранняя остановка по неизменившемуся числу или даже кратковременной стабильности выдачи не является безопасной оптимизацией. BM25 даёт столько же источников, но равенство содержания/ранжирования hybrid не доказано; переключать режим пользователю автоматически нельзя.

cProfile показал около 0,52 с в composite search и 0,37 с в hydration при общем времени около 0,99 с под профилировщиком; заметна конвертация protobuf payload в Qdrant client. Это вложенные времена — складывать их со всеми вложенными строками профиля нельзя. SQL выполняется пакетами, признаков запроса в БД на каждый отображаемый источник в этом пути не найдено.

### Подтверждённая работа интерфейса и транспорта

- В DOM источников 950 элементов при 158 строках; всего на странице 1157 элементов. После сворачивания `details.sources` остаются те же 158 строк и 950 элементов. Это измерение DOM, а не длительности React commit.
- `ChatPanel.jsx:368` отображает всю ленту внутри одного компонента. Его `query` меняется на каждый ввод; там же выполняются группировка документов, выбор доступных индексов и создание JSX всех строк.
- `ChatPanel.jsx:391` создаёт новые `remarkPlugins` и `components` для Markdown ответа. Сам ответ не отделён мемоизированной границей; неизменившиеся ответы также попадают в повторный обход. Snippet источника — обычный текст, **не 158 отдельных Markdown-парсеров**.
- `chatAnswerState.mjs:30` при получении `sources` заменяет массив целиком и автоматически раскрывает список до первого ручного переключения. `ChatPanel.jsx:475–530` монтирует все строки независимо от `sourcesOpen`.
- На каждый `delta`/`progress` вызывается `setMessages`; отдельного ограничения частоты обновления текста нет. React может объединять часть обновлений, поэтому число событий не равно автоматически числу commits.
- Один JSON response с 158 источниками занимает около **196 268 байт** в измеренном формате `json.dumps(ensure_ascii=False)`. Массив sources — 196 010 байт; значения snippet суммарно около 50 КБ, source_path около 22 КБ, tags около 16 КБ. Это размер JSON до сжатия, а не измеренный сетевой трафик.
- `chat.py:537` сохраняет sources и ссылки на evidence перед первой выдачей. `chat.py:748` сохраняет и отправляет весь список после обработанного пакета, `chat.py:599` обновляет его в конце; финальный `result` также содержит sources. Для `full` объём зависит от числа пакетов.
- `snapshot_blocks` уже исключает `content` и `concept_content`: предположение о сохранении полного текста всех фрагментов в каждом checkpoint здесь неверно.
- Qdrant dense/BM25 уже используют ограниченный payload selector; повторно предлагать «убрать content из всех результатов» как отсутствующую оптимизацию нельзя. У graph expansion отдельный `with_payload=True`, но в этом сценарии его время мало.
- `.env` задаёт `BACKEND_URL=http://127.0.0.1:18000`; известный IPv6-fallback через localhost не подтверждён как причина этого запроса. Прокси передаёт `upstream.body` потоком.

**Пределы вывода:** UI и размер DOM проверены, но React Profiler, long tasks, задержки ввода, задержка первого paint и production build в этой диагностике не измерены. Нельзя утверждать, что найдена единственная причина пользовательского подвисания, или обещать конкретный процент ускорения UI. Live `fast/full` с длительной генерацией не профилировались.

## Выбор подхода

1. **Рекомендуется сначала:** изоляция рендера, стабильные props, отсутствие скрытых строк в DOM, объединение частых текстовых delta. Минимальные изменения привычного поведения; полный список по-прежнему раскрывается автоматически.
2. **При оставшейся задержке первого показа:** отображение порциями по 40 с «Показать ещё» и «Показать все». Данные и выбор остаются полными. Это уже видимое изменение UX; включать отдельным решением после измерений.
3. **Полная виртуализация или новый протокол sources-delta:** резерв для длинных историй/сотен пакетов, если первые этапы не достигают критериев. Дополнительные сложности: строки переменной высоты, фокус, поиск браузером, совместимость истории и клиент/сервер. В базовую реализацию не входят.

## Review Focus

- При выборе последнего источника, скрытии списка и повторном открытии выбор и номер сохраняются — этапы 2 и 3.
- `result` приходит при ещё не выведенных delta; остановка и новая попытка не получают старый хвост — этап 3.

- Длинная история, смена языка, клавиатурный фокус и переход к запросу продолжают работать после размонтирования строк — этапы 2 и 5.

## Этап 4. Сократить повторную загрузку метаданных на сервере

Этап независим от UI. Начать с изменения внутри одной транзакции; не вводить кэш текстов между запросами или проходами поиска.
