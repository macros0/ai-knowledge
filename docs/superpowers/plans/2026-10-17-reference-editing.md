# План реализации защиты совместного редактирования справочников

> Для выполнения по задачам использовать `superpowers:executing-plans`. Делегирование не требуется этим планом. План утверждён пользователем; реализация выполнена автономно в `codex/reference-editing` и затем перенесена в main по отдельному разрешению. Отметки отражают проверенные части, незавершённая приёмка остаётся открытой.

**Цель:** устранить подтверждённые случаи перезаписи данных и добавить ограниченные по времени блокировки редакторов справочников.

**Архитектура:** общая строка состояния ресурса в БД хранит ревизию и временную аренду. Все изменяющие пути проверяют состояние внутри короткой транзакции; существующие доменные версии сохраняются. Общий frontend hook управляет арендой, а редакторы сохраняют черновик и разрешают конфликты.

**Технологии:** текущие Python/FastAPI/SQLAlchemy/Alembic, PostgreSQL и SQLite для тестов, Next.js/React, существующие pytest и `node:test`. Новые сервисы хранения, Redis и WebSocket не требуются.

**ТЗ:** [Техническое задание](../specs/2026-10-17-reference-editing-design.md), требования R01–R18, приёмка AC01–AC35. Связанный план: `docs/superpowers/plans/2026-10-17-hybrid-attachment-processing.md`, T25/T26 и A60–A68.

Статус на 18 октября 2026: интеграция `ac6b40f` завершена, изменения перенесены в локальный main, тестовая схема обновлена064→065, аренды включены. Пользователь отдельно разрешил локальный коммит и миграцию всех тестовых БД. Check-project, webpack build, backend/parser/PG и повторный scope idle/preview пройдены; настоящий двухпрофильный UI fault/role этап остаётся отложенным. Подробности и исторические результаты — в [отчёте](../reports/2026-10-17-reference-editing-acceptance.md).

## 1. Общие ограничения

- Работать с проверенным состоянием проекта. В исходном checkout есть посторонние изменения; не включать их в эту работу.
- Перед реализацией выбрать подходящий изолированный checkout. Унификацию состава выполнять после сверки фактически интегрированной версии T25/T26; не копировать незавершённую ветку обработки вложений вместе с несвязанными изменениями.
- Срок аренды 180 секунд; heartbeat 60 секунд; бездействие 600 секунд; предупреждение 60 секунд; polling занятой видимой карточки 30 секунд.
- Серверное время авторитетно. Истёкшая аренда не возрождается продлением; старое поколение не может снять новую аренду.
- Черновик справочника остаётся в памяти открытой страницы при конфликте, потере сети и таймауте. Для состава сохраняется autoclose T26 и серверный сохранённый draft. Автоматического перезаписывания свежих данных старым черновиком нет.
- Существующие проверки версий глоссария/разработок, preview merge, RBAC, audit, ограничения использования и семантика корзины сохраняются.
- Токены не попадают в URL, audit, логи и сообщения ошибок. Изменения безопасности сопровождаются обновлением `SECURITY.md`.
- В SQL-транзакции нет LLM, HTTP, Qdrant, ожидания человека. Синхронизация индекса запускается после commit.
- Тестовые БД и файлы изолированы от рабочей БД/корпуса. PostgreSQL-тесты требуют отдельной явно тестовой БД.
- Каждая задача заканчивается проверяемым результатом. Commit/push/deploy выполняются только в рамках отдельно предоставленной авторизации; автоматических коммитов этот план не предписывает.
- Требование ревизии нельзя отключать вместе с флагом пользовательских аренд. Старый backend не должен писать в БД одновременно с новым протоколом.
- Унификация состава сохраняет autoclose T26, document write lock, wire API и durable operation ownership. Флаг справочников и административный revoke не распространяются на состав; worker lease 60/20 с и preview TTL 15 минут остаются отдельными.

## 2. Пять особых направлений проверки

1. Потерянный ответ и поздний запрос старой вкладки: тесты задач 3 и 5 обязаны доказать, что новый владелец и данные не затронуты.
2. Появление ручной правки между отбором кандидата и ответом LLM: задача 4 проверяет текст, ревизию, происхождение и audit.
3. Смешанная массовая операция: задача 6 проверяет точный список кандидатов и явные причины частичных пропусков.
4. Ресурс отсутствовал при чтении или был удалён/восстановлен: задачи 2, 3 и 4 проверяют первоначальное создание, ревизию и недействительность старой сессии.
5. Другая транзакция/процесс и обратный порядок блокировок: задачи 0, 6 и 10 проверяют реальные PostgreSQL-гонки; отсутствие ошибок в одном процессе недостаточно.

Команды `python -m pytest` выполняются из `backend` интерпретатором окружения проекта. Тесты используют отдельные временные каталоги в соответствии с `pyproject.toml`; для одновременных прогонов задаются разные `--basetemp`. Параллельный запуск не должен очищать каталог другого прогона.

Новый PostgreSQL-набор использует отдельную переменную `REFERENCE_TEST_POSTGRES_URL`. Fixture проверяет имя тестовой БД, например префикс `test_reference_`, до любого удаления таблиц. Не передавать рабочий `DATABASE_URL`. Отсутствие тестовой БД может дать skip локально, но является незакрытым обязательным gate при итоговой приёмке.

Тесты времени используют подставляемые часы; тесты гонок — барьеры/события. Длительные реальные ожидания 3/10 минут не нужны для unit-тестов, но один реальный браузерный сценарий бездействия включается в протокол приёмки.

Существующий regex-тест `developmentUpdate.test.mjs` не доказывает отсутствие потери изменений. Его нужно дополнить или заменить проверкой модели конфликта и реального пользовательского потока.

## 7. Решения, предлагаемые к утверждению

1. Сочетать обязательную проверку версии с арендой только для длительных редакторов.
2. Использовать карточку термина/правила/разработки/тега как единицу аренды; для наборов — язык и тип набора.
3. Принять сроки 180/60/600/60 секунд и сохранять черновик после истечения.
4. Разрешить административный отзыв конкретного поколения с обязательной причиной и audit.
5. Сначала исправить подтверждённые перезаписи, затем подключить единый механизм и остальные справочники.
6. Выпускать с закрытой на время переключения записью справочников; не поддерживать смешанных старых и новых backend-писателей.
7. Унифицировать стиль, таймеры и транспортный lifecycle с T25/T26 состава через адаптеры. Сохранить его autoclose, текущую схему/API и независимую блокировку выполняющейся операции; не переносить административный revoke справочников на состав автоматически.

Утверждение этого плана определяет объём реализации. На этапе подготовки документов commit, push и миграция не входили в объём. Последующие разрешения на локальный main/commit/тестовую миграцию зафиксированы в актуальном протоколе.

Историческая контрольная точка до разрешения main/миграции: реализация/автотесты/доступная браузерная приёмка завершены. Совокупные пункты с целевой копией БД/rollout и default Turbopack не помечены выполненными: целевой выпуск не разрешён, локальный junction ограничивает Turbopack (webpack production build passed).
