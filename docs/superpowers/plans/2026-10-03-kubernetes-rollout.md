# Kubernetes: домашний стенд и комплект для переноса

> Исполнение: последовательно по четырём задачам ниже; использовать superpowers:executing-plans.
> Основные задачи выполнены последовательно; итоговое независимое review по executing-plans проведено один раз. Развёртывание выполнено после «продолжай».

**Редакция:** 10.10.2026. Объём выбран пользователем: рабочий домашний Kubernetes-стенд и комплект для переноса; приёмка PROD отдельно.

**Цель:** воспроизводимо запустить существующее приложение дома, проверить его работу и сохранность данных, передать тот же комплект для дальнейшего внедрения.

**Архитектура:** compact/bundled: один Pod приложения с frontend и backend, один backend worker, отдельные PostgreSQL и Qdrant, постоянные тома. Обслуживание с остановкой приложения; операции выполняет один оператор. Первый стенд — существующая Ubuntu VM с kind. Модельные заглушки допустимы с явной отметкой в результате.

**Технологии:** существующие FastAPI, Next.js, PostgreSQL, Qdrant, Docker, Helm и Kubernetes. Новых инфраструктурных подсистем этот этап не требует.

**Контекст:** [исходный дизайн](../specs/2026-10-03-kubernetes-deployment-design.md), [инструкция развёртывания](../../KUBERNETES_DEPLOYMENT.md), [домашняя приёмка](../reports/2026-10-03-kubernetes-home-acceptance.md).

## Что изменилось

Этот документ заменяет прежнюю очередь и критерии завершения первой поставки.
Полная предыдущая редакция, включая незакоммиченные уточнения, сохранена в
[архиве](2026-10-03-kubernetes-rollout.archive-2026-10-10.md).
Старые документы описывают более широкий замысел: их OPEN/REQUIRED, C1–C6,
R1–R6, P1–P3 и TLS T1–T6 не добавляются автоматически к этому этапу.
Обязательства конкретной production-среды остаются в её отдельной приёмке.

Прежние результаты проверок сохраняют свои ограничения. Отложенное требование
не становится выполненным, старый FAIL не превращается в PASS. Незавершённый
автоматический lifecycle не объявляется готовым благодаря ручной процедуре.

## Оставляем обязательным

- Одна application replica, один backend worker, `Recreate`; без HPA и параллельных операторских операций.
- Существующие auth/роли/CSRF и проверки секретов сохраняются. Секреты не попадают в Git, архив поставки и логи; используются отдельные настройки стенда.
- Перед миграцией, backup и restore приложение остановлено, завершение прежних writers подтверждено. При неизвестном состоянии узла/операции работа останавливается для ручного разбора; автоматический resume не обещается.
- Backup содержит согласованные PostgreSQL, Qdrant и файлы. Restore — только в новый namespace с новыми томами; исходные данные и копия сохраняются. Пользовательские PVC не удаляются вместе с release.
- Обычное обновление сохраняет `APP_SECRET_KEY`. При явном DR — контролируемая ротация, очистка восстановленных сессий/flows и новый вход по [политике восстановления](../../KUBERNETES_SESSION_RECOVERY.md). Копия не получает production endpoints/секреты и не запускает старые задания автоматически.
- Локальный запуск и Compose сохраняются. Документы и примеры обезличены. Изменения реализации, затрагивающие безопасность, сопровождаются обновлением `SECURITY.md`.

## Четыре задачи до завершения

### 1. Зафиксировать минимальный комплект

**Использовать:** существующую ветку `codex/kubernetes-rollout`, chart `deploy/helm/ai-knowledge`, образы приложения и `scripts/kubernetes/` в Kubernetes worktree.

- [x] Выбрать один совместимый набор уже существующих исходников, chart и образов; записать ревизию, digests и один домашний values-файл без секретов.
- [x] Проверить, какие команды этого набора действительно работают. Незавершённые private-кандидаты не переносить целиком ради закрытия их внутренних очередей.
- [x] В `docs/KUBERNETES_DEPLOYMENT.md` оставить один поддерживаемый путь: проверенные команды или конкретная последовательность ручных действий. Ручной путь не отключает существующие guards; отказ команды разбирается, а не обходится флагом.

**Готово:** известен один комплект и точный способ его установки. Повторная инвентаризация всех исторических snapshot не нужна.

### 2. Запустить и проверить приложение дома

**Использовать:** выбранный chart/values, существующий домашний kind, `docs/KUBERNETES_HOME_ACCESS.md`.

- [x] Проверить достаточность ресурсов и выполнить чистую установку: хранилища → миграция → приложение. Дождаться Ready с ограниченным ожиданием.
- [x] Через браузер пройти вход, загрузку одного небольшого контрольного документа, обработку, поиск и открытие источника. Проверить ответ чата/поток; при stub отметить, что качество реального LLM не проверено.
- [x] Пересоздать Pod приложения; убедиться, что документ, поиск и вход продолжают работать с прежними томами.

**Готово:** приложение доступно, контрольный сценарий проходит, данные переживают пересоздание Pod. Допустим существующий домашний маршрут или локальный port-forward; подключение новой платформенной сети не требуется.

### 3. Один раз проверить обслуживание и восстановление

**Использовать:** проверенные команды `scripts/kubernetes/`, нативные инструменты PG/Qdrant и конкретный runbook в `docs/KUBERNETES_DEPLOYMENT.md`. Допускается ручная последовательность без разработки универсального recovery controller.

- [x] На остановленном приложении сделать согласованную копию PostgreSQL, Qdrant и файлов, записать версии и контрольные суммы, сохранить копию вне исходной VM.
- [x] Выполнить одно обновление приложения с миграцией при необходимости. Проверить прежний документ и поиск. Один контролируемый отказ миграции должен оставить приложение остановленным и данные доступными для восстановления.
- [x] Восстановить копию в новый namespace/тома с тестовыми endpoints; перед стартом выполнить политику сессий и проверить состояние восстановленных заданий. Проверить содержимое документа, поиск, источник и новый вход. Исходную установку не изменять.
- [x] Записать фактические команды, время остановки/восстановления и ручные действия. Для несовместимой миграции путь возврата — проверенная копия в новом target; автоматический downgrade БД не требуется.

**Готово:** один непустой backup/restore и одно обновление проверены на выбранном комплекте. Не требуется матрица всех обрывов, потерянных ACK, перезапусков оператора и отказов узлов. Если операция прервана, автоматическое продолжение не поддерживается; сначала ручная сверка и подтверждение остановки writers, затем отдельная операция на чистом target.

### 4. Передать воспроизводимый комплект и закрыть этап

**Результат:** chart, ссылки/digests образов, пример values, совместимые необходимые scripts и краткий runbook; один итоговый отчёт в `docs/superpowers/reports/2026-10-03-kubernetes-home-acceptance.md`.

- [x] Выполнить `helm lint`, render выбранного домашнего values и существующие проверки затронутых chart/scripts. Если менялся код приложения — соответствующие регрессионные тесты. Полные обязательные проверки репозитория выполняются перед коммитом/публикацией по обычным правилам, без отдельной новой release-матрицы этого плана.
- [x] Проверить, что инструкция использует только содержимое комплекта, доступные образы и явно заданные настройки: без private-каталогов, временных source mounts и секретов разработчика.
- [x] В итоговом отчёте указать комплект, результаты задач 2–3, ограничения, что проверено со stub и что ещё требуется для конкретной среды. Не создавать новый отчёт на каждый вспомогательный шаг.

**Готово:** другой оператор может повторить проверенный путь по инструкции, состав комплекта зафиксирован, все четыре результата подтверждены. Интеграция в main, коммит и публикация выполняются по отдельной авторизации; их отсутствие не скрывается в отчёте.

## Отложено и не блокирует этот план

- Автоматическое продолжение после аварии, универсальный журнал every-effect, передача владения, protected promotion/admission/activation и полная матрица crash/ACK/fencing. Уже действующие защитные проверки не отключаются.
- Дополнительные PostgreSQL TLS/PKI/CRL-профили и ротации; домашний профиль фиксируется явно. Требование TLS конкретной среды проверяется перед её внедрением.
- Универсальная совместимость IdP, trusted-IP, новые гарантии audit outbox/collector. Действующие вход, роли и аудит сохраняются.
- Kubernetes external, несколько frontend/API/workers, распределённая очередь, HA, zero downtime и нагрузочная приёмка.
- Vault/VSO, Gateway конкретной платформы, registry mirrors, GitLab promotion, внешние линтеры/согласования и DEV → TEST → PROD. Это отдельная работа по требованиям выбранной среды.
