# Будущая доработка: проверка чанков перед генерацией

Проект по предложению пользователя 26.09.2026. Это архитектурная доработка
pipeline, staging, прав и UI; реализация сейчас не начата. Перед выполнением
нужны согласованный design, benchmark detector и исполняемый план.

**Цель:** проверять все чанки DOCX/XLSX/PDF/EML/MSG перед генерацией;
подозрительные источники обрабатывать после решения администратора.

## Предлагаемый поток

1. Разобрать документ ограниченным worker и сохранить канонический текст,
   дерево и чанки нового поколения в staging.
2. Проверить каждый чанк и filename/source metadata, которые увидит генератор.
   Gate действует до генерации и LLM-классификатора таблиц, также для вложений.
3. При признаках риска сохранить причину/фрагмент и перевести новое поколение
   в «Ожидает проверки администратора». Освободить slots; не держать поток
   в ожидании решения и не заменять ожидание автоматическими retry.
4. Администратор видит точный фрагмент, место в исходнике, цепочку вложений
   и причину. Разрешает генерацию проверенного поколения либо отклоняет её
   с причиной. Решение не изменяет оригинал и канонические координаты.
5. После разрешения продолжить из checkpoint с обычной защитой генератора.
   После отклонения сохранять явный статус; не объявлять неполное поколение done.

Рекомендуется приостановить новое поколение целиком до решения по всем
подозрительным чанкам. Предыдущее опубликованное поколение остаётся доступным.
Pending/rejected новые чанки **не публикуются в Qdrant/RAG**: иначе сырой
dual-index обойдёт ожидание админа даже при отсутствии концептов.

## Проверка риска и ограничения

Сравнить локальные правила, отдельный классификатор и их сочетание на
размеченном корпусе. Измерить пропуски, ложные блокировки, задержку и затраты;
пороги и provider выбрать по результату. Внешний/LLM-классификатор сам может
поддаться инструкции из проверяемого текста; его output должен быть ограничен
схемой и валидироваться. При сбое проверки сохранять «Проверка не завершена»
с повтором/админским решением; не считать сбой признаком безопасности.

Отрицательные контроли: обычные пользовательские инструкции, SQL/код,
регламенты и учебные цитаты prompt injection. Признак риска — попытка управлять
генератором/его ответом или вызвать действие вне задачи. Одних ключевых слов
недостаточно; язык RU/EN, обфускация, sender и filename входят в benchmark.

Решение привязать к doc_id/generation_id/source_id/chunk_index, SHA256 текста
и видимых metadata, detector/policy version, модели и prompt fingerprint.
При изменении данных разрешение становится устаревшим. RBAC admin и доступ
к документу проверяются при записи, вместе с CSRF, trash/purge и актуальностью
поколения. Decision+enqueue атомарны и идемпотентны; аудит хранит кто/когда/почему.
Editor/viewer, bulk resume и regenerate не обходят gate.

Ожидание переживает restart/backup/restore. Legacy checkpoints без результата
проверяются до следующей генерации; bulk resume не запускает pending автоматически.
UI показывает отдельный статус и причины RU/EN, с доступом с клавиатуры.

Подтверждение админа разрешает обработку; оно не доказывает, что модель
проигнорирует вредоносную инструкцию. Сохраняются system/user boundaries,
ограниченный schema, запрет внешних действий и проверка цитат/полноты до
публикации. Дословная цитата подтверждает наличие текста, но не весь смысл
концепта. Будущий gate не закрывает текущий A02 и проблему авторства.
Такой набор независимых мер соответствует
[OpenAI: Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety);
это применение общего принципа к нашему pipeline, не готовая Agent Builder интеграция.

## Этапы будущей реализации и проверки

- [ ] Benchmark detector: явные/обфусцированные атаки, RU/EN, metadata,
  delimiters, вложения и отрицательные контроли; найденные A02 regressions.
- [ ] Данные/миграции: pending/approved/rejected/check_failed, hashes/audit,
  SQLite/PostgreSQL, legacy/dev-drift, заполненная база и backup/restore.
- [ ] Pipeline RED→GREEN: pending не вызывает LLM/классификатор и не создаёт
  опубликованные точки; все форматы, siblings, fresh/resume/regenerate/restart.
- [ ] Admin API RED→GREEN: роли/CSRF, stale hash, trash/purge, double-click,
  два администратора; ровно один enqueue, решение и аудит сохраняются атомарно.
- [ ] UI: очередь проверки, source location/причина, approve/reject, RU/EN,
  keyboard/focus, восстановление после сбоя.
- [ ] E2E: риск→ожидание→restart→approve→одна генерация; reject→нет публикации;
  изменение текста→старое разрешение отвергнуто. Одобренная атака остаётся
  данными; выполнение её указаний не маскируется успешным админским кликом.
- [ ] Нагрузка: ограниченная очередь, освобождение slots, timeout, безопасные
  логи/аудит; финальные suites/browser checks Windows/Linux и отдельное ревью.

Текущие модели, флаг импорта и генерация не изменяются этим документом.
