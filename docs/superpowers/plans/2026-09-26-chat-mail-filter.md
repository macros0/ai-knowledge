# Фильтр писем в чате — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Статус:** отложено. Пользователь попросил сохранить план на будущее; реализация и миграция индекса не начаты.

**Goal:** добавить в чат три режима поиска: «С учётом писем», «Без писем», «Только письма», учитывая все вложения писем на любой глубине.

**Architecture:** определять принадлежность к письму по каноническому дереву источников PostgreSQL, записывать служебный признак в payload концептов и чанков Qdrant и применять фильтр до поиска. Дополнительно проверять результаты по БД перед сборкой контекста, чтобы устаревший payload не нарушал выбранный режим.

**Tech Stack:** Next.js / React, FastAPI / Pydantic, SQLAlchemy, PostgreSQL, Qdrant.

**Spec:** согласованные требования в разделе ниже. Основа импорта описана в [outlook-mail-ingestion-design](../specs/2026-09-25-outlook-mail-ingestion-design.md).

## Согласованные требования

Пользователь: «все что внутри письма считаем частью письма».

| Режим UI | Значение API | Источники |
|---|---|---|
| С учётом писем | `all` | Все источники; режим по умолчанию |
| Без писем | `exclude` | Только источники, которые не являются письмом и не находятся внутри письма |
| Только письма | `only` | Письма и любые их вложения, включая документы и вложенные письма |

Пример: DOCX → письмо → DOCX → PDF. Внешний DOCX относится к обычным документам; письмо, внутренний DOCX и PDF относятся к письму. Для MSG → DOCX вся ветка относится к письму. Письмо внутри таблицы классифицируется по тем же правилам.

Признак определяется происхождением источника, а не расширением файла, пользовательскими тегами, заголовком, словами текста или предположением LLM. Наличие письма внутри DOCX не делает весь внешний DOCX письмом.

## Global Constraints

- Фильтр действует одновременно для concept- и chunk-точек, dense, BM25 и расширения поиска.
- Переключение режима не меняет права доступа, корзину, фильтры тегов, разработки и языка; условия комбинируются через AND.
- Не требуется смена модели, генерация концептов или пересчёт эмбеддингов; существующим точкам обновляется только payload.
- Признак наследуется всеми потомками письма, независимо от типа и количества уровней вложенности.
- Новое поле запроса: `mail_mode: Literal["all", "exclude", "only"] = "all"`; неизвестное значение возвращает 422.
- Служебный payload: `mail_scope: "mail" | "document" | "unknown"`, `mail_scope_version: 1`. Отсутствующее поле эквивалентно `unknown`.
- Строгие режимы исключают `unknown`; режим `all` сохраняет текущее поведение. Это предлагаемая политика для старых данных, которую надо подтвердить перед реализацией и пояснить в интерфейсе.
- Каждый запрос фиксирует выбранный режим; переключение во время ответа влияет только на следующий запрос.
- Работа выполняется отдельно для основной и измерительной базы с их собственными конфигурациями и коллекциями.
- Коммит и push выполняются только по отдельному запросу пользователя.

## Текущее состояние и точки изменений

Проверено по коду 26.09.2026; перед реализацией повторно проверить актуальные интерфейсы.

- `backend/app/db/models.py`: `DocumentSource` содержит тип, metadata и parent_source_id; чанки и концепты имеют source_id.
- `backend/app/services/source_store.py`: чтение цепочек источников; письмо обозначается kind="mail" либо metadata.mail=true.
- `backend/app/services/retrieval_hydration.py`: каноническая гидратация и добавление source_path/mail_fragment в результаты.
- `backend/app/services/vector_store.py`: запись обоих типов точек, общий pre-filter, search_composite и расширение поиска.
- `backend/app/models/schemas.py`, `backend/app/api/chat.py`: контракт и обработка запроса чата.
- `backend/app/services/context_builder.py`: сборка основного текста и дополнительных фрагментов источников.
- `frontend/src/components/ChatPanel.jsx`, `frontend/src/context/ChatContext.js`, `frontend/src/lib/api.js`: управление режимом и отправка запроса.
- `frontend/src/i18n/locales/ru.js`, `frontend/src/i18n/locales/en.js`, `backend/app/i18n/ui_en.json`, `backend/app/i18n/ui_keys.json`: тексты и словарь ключей.

## Review Focus

1. Отсечение после получения top-k теряет подходящие источники: нужен pre-filter всех поисковых веток.
2. Устаревший payload, графовое расширение или сиблинг не должны возвращать исключённое письмо.
3. Документ внутри письма наследует принадлежность письму; внешний документ её не наследует от потомка.
4. Повреждённое дерево и старые плоские чанки не должны ошибочно считаться обычными документами.
5. Дополнительный mail_fragment и метаданные цепочки не должны обходить режим «Без писем».

## Критерии готовности и оценка

Готовность: все доступные точки классифицированы либо явно unknown; строгие режимы не пропускают противоположную ветку через поиск или контекст; вложения наследуют признак письма; all сохраняет прежний результат без дополнительных ограничений. Основной и измерительный контуры проверены независимо.

Предварительная оценка: 1–2 рабочих дня при полном дереве источников. Ремонт происхождения старых плоских чанков оценивается отдельно после dry-run. Оценка не является подтверждением полноты текущего корпуса.
