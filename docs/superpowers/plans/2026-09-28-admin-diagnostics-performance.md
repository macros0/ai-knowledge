# Отдельная задача: производительность временной диагностики

Решение владельца от 28.09.2026: оптимизацию p95 вести отдельно от внедрения
административного сбора логов. Текущая функциональная приёмка не должна
выдавать превышение за выполненный критерий. Значения в `config.py` по
умолчанию отключают capture/bundle/download; production env-примеры явно
включают эти возможности. Подробный сбор начинается только по действию
администратора, временно и с ограничением квот/срока, но при включении
задержка запросов может возрасти.

## Подтверждённая отправная точка

- Сценарий: `/api/search` через HTTP TestClient, вместо Qdrant — 10-мс заглушка;
  три серии с прогревом по 30 с и >=200 запросами, один ZIP в третьей серии.
- После выноса ZIP в дочерний процесс Windows p95: 14,545/15,988/19,496 мс
  (baseline/capture/capture+build), то есть +9,9%/+34,0%.
- Docker Desktop Linux, spool во внутренней файловой системе контейнера:
  14,976/17,700/20,625 мс, то есть +18,2%/+37,7%.
- Независимый CT 102 на Proxmox, выбранный владельцем синтетический корпус:
  один опубликованный документ, SQL-чанк и Qdrant-точка, HTTP `POST /api/search`
  через frontend, отдельные PostgreSQL/Qdrant и fake embedder. После 30 с
  прогрева по 200 успешных запросов p50/p95 составили 18,26/19,92 мс без
  сбора, 20,54/23,46 мс при capture и 27,60/33,35 мс при capture+ZIP:
  p95 +17,8%/+67,4%. ZIP построен с корректным CRC и без gaps; все запросы
  третьей серии начались до готовности ZIP. Момент старта дочернего процесса
  отдельно не измерялся. Это проверенный синтетический сценарий, а не замер
  production SLA; подробности в отчёте приёмки.
- В двух локальных сериях пакет построен, `dropped=expired_queue=drain_timeouts=0`.
  Сырые результаты: `%TEMP%/diag-process-full-0928/result.json` и
  `%TEMP%/diag-process-linux-full.json`.
- Прежние варианты и пределы стенда приведены в
  `docs/superpowers/reports/2026-09-27-admin-diagnostics-acceptance.md`.

## План работ

1. На Linux staging зафиксировать аппаратные ресурсы, версию образа и режим
   хранения. В дополнение к уже снятому одно-документному замеру подготовить
   репрезентативный **синтетический** корпус с несколькими документами и
   запросами разной сложности по выбору владельца. Снять повторяемые серии
   baseline/capture/capture+ZIP: прогрев >=30 с, >=200 одинаково распределённых
   запросов в каждой, одинаковый параллелизм. Отдельно сохранить 10-мс
   заглушку как стресс-тест фиксированных расходов. Не использовать данные
   production для замера и не переносить конфиденциальный корпус.
2. Профилировать путь успешного запроса при capture: выбор активной сессии,
   формирование/валидацию/кодирование события, очередь, writer и блокировки.
   Разделить стоимость CPU, диска, планировщика и операции сборки ZIP. Сохранить
   профили без текста документов, исключений и секретов.
3. По результатам профиля выбрать минимальное изменение. Кандидаты:
   уменьшение синхронной работы на успешном пути без ослабления проверки до
   записи; ограничение частоты успешных событий при сохранении ошибок;
   управление приоритетом дочерней сборки; отдельный I/O worker. Не принимать
   оптимизацию по одному удачному замеру.
4. Для каждого изменения сначала добавить регрессионный тест на выбранный
   контракт: ошибки сохраняются полностью, sampling явно учитывается,
   переполнение не скрывается, приватность проверяется до постоянной записи,
   квоты и SQL-аудит публикации ZIP сохраняются. Затем повторить профильные
   тесты, полный backend и нагрузочные серии на том же стенде.
5. Приёмка: p95 относительно baseline <=+10% при capture и <=+20% при
   capture+ZIP; RSS backend <=+128 МиБ, Node <=+32 МиБ; без новых business 5xx,
   непреднамеренных потерь событий и повреждений ZIP. Зафиксировать p50/p95,
   распределение, счётчики recorder и SHA ревизии. Если типовая нагрузка
   выполняет критерий, а 10-мс стресс-тест нет, явно согласовать область
   применимости порога с владельцем до изменения критерия.

Эта задача не меняет границы доступа, состав диагностического пакета и
функциональную семантику временного сбора.
