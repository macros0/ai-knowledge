Классификатор получает ограниченный JSON preview с исходными индексами.

индексами `columns[].index`; legacy Markdown использует прежний отдельный промпт. Python
переносит значения всех строк и колонок; небольшая таблица `whole` помещается в
один фрагмент, большая раскладывается на строки/части. Длинная ячейка получает
точные диапазоны текста. Расчёт token budget без tokenizer консервативный
(`estimated`, UTF-8 bytes), а не подтверждённый подсчёт токенов провайдера.
Неоднозначная шапка сохраняет все физические строки и координатные названия.
Покрытие ячеек не доказывает семантическую правильность шапки.

Кандидат скрыт до успешной публикации. Публикация проверяет SQL digest, portable
manifest, полный набор ссылок на ячейки и части текста, файлы и точки Qdrant;
переключение активного поколения и канонических концептов/чанков атомарно.
Сохранённый ответ содержит ограниченный фрагмент и SHA-256, привязанный к
конкретному поколению. Если это поколение очищено, источник недоступен.

Миграция схемы и корпуса выполняется отдельно. Alembic revision
`050b1c2d3e4f` добавляет `document_tables`, `document_table_rows` и nullable
`table_refs`, а также nullable `document_generations.table_schema_version`
(признак использования структурного маршрута); она не запускает регенерацию и не меняет существующие поколения.
Revision `060b1c2d3e4f` добавляет производную `cells_projection`: PostgreSQL
хранит generated JSONB array потенциальных кодовых ячеек с исходными индексами
колонок; SQLite использует virtual generated JSON. SQL-фильтр допускает любую
строку с тремя последовательными ASCII-цифрами; прежний Python strip/fullmatch
окончательно проверяет идентификатор, включая пробелы вокруг значения. Каноническая
`cells` остаётся JSON: её представление чисел и контрольные суммы не меняются.
Проекция не загружается с ORM-строками и не возвращается при пакетной вставке.
На существующей схеме050 нужна явная060 до запуска нового табличного поиска;
`create_all` её не выполняет. PostgreSQL построит проекцию существующих строк
и потребует дополнительный диск и блокировку таблицы; сначала измерьте это на копии.
Откат060 удаляет только проекцию; для возврата к старому runtime используйте
предыдущую версию поискового кода. Отдельная050 по-прежнему запрещает destructive
schema downgrade после записи канонических таблиц.
Перед обновлением примените миграцию на копии БД и выполните schema drift checks.
`create_all` не обновляет колонки уже существующих таблиц. Нельзя штамповать
отстающую dev-БД без отдельной сверки её реальной схемы.

## Порядок пилота

1. Зафиксировать code/parser/classifier/model/prompt/config versions и исходные
   SHA-256. Остановить изменения выбранных документов на время согласованного
   backup DB + uploads/OKF artifacts + Qdrant. Для bundled production использовать
   существующие `scripts/production/backup-bundled.sh` и `restore-bundled.sh`.
2. Restore в отдельную DB, data directory, Compose project и Qdrant collection.
   Проверить totals, SHA-256 оригиналов и артефактов, ссылки старых чатов и поиск
   прежних поколений. Снимок только pointer не является backup.
3. Применить аддитивную схему к восстановленной копии. Выбрать A, обычный
   справочник, сложную шапку, DOCX со вложением и контроль без таблиц. Не направлять
   integration tests в рабочий корпус.
4. Выполнить dry-run, затем одну ограниченную партию через существующую очередь.
   Пайплайн готовит и проверяет кандидат до атомарной публикации. При сбое прежний
   источник остаётся доступен. Повторный `--resume-run` читает тот же job, а не
   создаёт регенерацию заново. Four-eyes и rate limits сохраняются.
5. Проверить всю замороженную матрицу T0: отдельно candidate/context recall и
   правильное значение + источник. Live ответы повторить три раза; сохранить
   каждый неуспех. Ресурсные gates: p95 ≤ baseline × 1.15 при ≥30 одинаковых
   запросах, peak RSS ≤ baseline × 1.20. Измерить rows/fragments/points/disk.
   Failed и unknown не превращаются в passed изменением порога.
6. Следующая партия допускается после отчёта предыдущей. Один успешный пилот
   не означает миграцию всего корпуса.

Из корня с настроенной **изолированной** runtime конфигурацией:

```powershell
$env:PYTHONPATH = "$PWD/doc-parser/src;$PWD/backend"
.\backend\.venv\Scripts\python.exe backend/scripts/reprocess_table_documents.py --dry-run --doc-ids-file data/pilot-doc-ids.txt --limit 5
```

По умолчанию выполняется dry-run; run manifest записывается в
`data/table-migrations/<run-id>.json`. Он содержит IDs и версии, без текста ячеек.
Для записи нужны явный `--apply`, `--api-base http://127.0.0.1:<port>/api/` и
`TABLE_MIGRATION_AUTHORIZATION` с действующим заголовком Authorization администратора.
Секрет не передавать аргументом CLI, не записывать в manifest или отчёт.
После запуска повторять ту же команду с `--resume-run <run-id>` для проверки
состояния. Мигратор проверяет совместимость backend через защищённый runtime API.

Потеря ответа POST оставляет `submission=unknown`. Автоматический повтор блокируется:
найдите созданный job в администраторской очереди и задайте `--job-id <id>` вместе
с `--resume-run`. ID принимается только для bulk_regenerate с точным набором
документов этой партии. Не создавайте новую партию, пока исход не выяснен.

Состояния manifest: `planned`, `prepared`, `verified`, `published`, `failed`,
`rolled_back`. `verified` подтверждает таблицы и generic format1 готового кандидата по
хэшированному publication artifact; `published` требует активное поколение со
структурной схемой и проверку generic-фрагментов по каноническим чанкам.
Повреждённые content/descriptor/hash и отсутствие parents не подтверждаются. `rolled_back` только наблюдает
возврат прежнего active после публикации; этот статус не выполняет и не доказывает
согласованный restore. Отбор текущей версии основан на parser/schema/format1 provenance;
отдельный отбор по будущей версии classifier, ширине или семантике шапки пока
не реализован.

## Откат

Отключить новый маршрут для новых заданий, отменить queued migration jobs штатным
admin API и дождаться остановки running jobs. Восстановить согласованный backup
DB + Qdrant + uploads/OKF в отдельную среду, проверить прежние источники и перевести

`pilot accepted`, `corpus migrated`. Отсутствующие проверки указываются явно.


## Checkpoint таблиц

Подготовка source/table metadata сохраняется пакетами по 256 записей; завершённый
фрагмент обновляет свою запись в SQLite/PostgreSQL. Непустые ссылки на ячейки
хранятся в `data/staging/<doc_id>/table_refs_<sha256>.json`; в БД записано относительное
имя. Файл проверяется по SHA-256, ограничен 4 MiB и входит в общий backup каталога
`data`. Старые inline table_refs совместимы. При восстановлении незавершённой
генерации нужны и БД, и каталог staging; отсутствующий/повреждённый файл вызывает
ошибку, а не публикацию без ссылок. Сохранившиеся raw-входы и завершённые checkpoint
при resume должны совпадать с повторным разбором оригинала.


## Версии исправлений parser v27 / normalizer4

Для новых разборов `PARSER_VERSION=mail-sources-v27-tables-v1`, structural
normalizer4. Persisted table schema остаётся1. Старые checkpoints не смешиваются

Для исправления старой шапки или display-кода нужен повторный разбор оригинала
в новом поколении; обычный reindex не пересчитывает канонические ячейки.

Числовой нулевой формат применяется и к целому OOXML-значению, записанному как

остаётся данными, имена берутся из декларации колонок либо координат, адреса
шапки не выдумываются. Адресный контекст допускает такую таблицу только с
подтверждённой explicit declaration нового нормализатора.

Ссылка на продолжение длинной ячейки загружает одну строку/колонку со смещением.
Соседние строки читаются отдельным запросом без этого смещения; неподходящий
диапазон и удалённое поколение по-прежнему дают явный отказ.

## Уточняющие идентификаторы в поиске

Для явно указанных целых идентификаторов с названиями полей (например,
код либо код и БЕ) табличные фрагменты с точными значениями в одной физической строке
получают приоритет перед неполными табличными совпадениями до среза контекста.
Числа в закрытых кавычках имени поля остаются частью имени. Конкретная
однословная leaf-колонка имеет приоритет перед общим начальным словом в
названиях соседних колонок той же группы шапки; уточняющее окончание названия
(например, «БЕ» в «Код БЕ») сохраняется.
Значения читаются только по нужным каноническим row/column парам текущего
видимого поколения, название
поля — из последнего уровня шапки. Общая надпись над таблицей, номер строки,
дробное/знаковое число и значение чужой колонки не подтверждают совпадение.
Неоднозначный запрос сохраняет исходный порядок. Фрагменты и ссылки не
удаляются; порядок прозаических/mail/review блоков сохраняется. Это уточнение
поискового контекста; операции полной выборки и подсчёта относятся к R3.


## Физический батч Ollama

`EMBEDDING_OLLAMA_NUM_BATCH` задаёт число токенов физического батча native Ollama,
а `EMBEDDING_BATCH_SIZE` — число текстов в запросе. Если первая настройка не задана,

необрезанный вход из 2303 токенов с HTTP413. Эта настройка не меняет контекст,

подтвердила 2303 токена/1024 измерения, батч из 64 текстов и сохранность короткого вектора; это
не полная RSS/p95-приёмка. Перед внедрением проверять реальные длинные входы,
расход памяти и ресурсные gates на выбранном provider/model/config.


## Generic chunk parts: текущая интеграция R2

Изолированный candidate marker1 публикует несколько проверяемых частей длинного
или нормализованного обычного чанка. Сохранённый текст и ссылка остаются привязаны
к исходному chunk_index/source; части имеют собственные score и evidence identity.
Поиск читает выбранные SQL части пакетами≤256, возвращает только канонический текст
и bounded display title. Цитата восстанавливается по fragment offsets/hash;
смена поколения или повреждённый snapshot возвращает409. Legacy NULL и TableRef
идут по прежним маршрутам. `CHUNK_INDEX_PROJECTION_ENABLED=false` по умолчанию сохраняет NULL для новых
поколений. При явном включении сервер выбирает format1 для новых кандидатов;
продолжение сохраняет исходный NULL/1. Включение требует
`SEARCH_INDEX_CHUNKS_ENABLED=true`. Формат выбирает серверная конфигурация;
клиентские payload его не задают. Core maintenance/export и SQLite backup restore проверены focused suites; private PostgreSQL/files/Qdrant restore проверен на mixed fixture. Production rollout/cutover выполняется отдельной командой; итоговая resource/quality acceptance R2 пока открыта.

До запуска нового ORM на существующей БД нужна061 (nullable generation marker,
материализованные parts), для полных длинных title —062 (section_title→TEXT).
Обе миграции отделены от миграции корпуса.062 сохраняет текущие title/NULL/content;
PostgreSQL ALTER потребует блокировку таблицы, SQLite batch migration перестроит
её. Сначала проверяется копия БД и schema drift, create_all не заменяет миграции.

Откат062 запрещён при любом canonical title длиннее1024символов. Обрезать title
для отката нельзя.061 запрещает downgrade при любом non-NULL marker, включая
inactive/abandoned/all-short. Очистка inactive generation должна согласованно
удалять её файлы, точки и SQL данные с проверкой ссылок; active marker вручную
не обнуляется. Совместимый возврат требует проверенного reader либо согласованного
backup, восстановленного в отдельной среде. Portable/operational rollback R2 ещё
подлежит общей приёмке.


Maintenance для marker1 восстанавливает только опубликованные same-ID parts,
проверяет canonical/parent/descriptor hashes и дополняет scoped group metadata
без повторного embedding готовых частей. Repair создаёт новое поколение с тем же
trusted format marker; SQL projection rows готовятся до длинного read snapshot,
чтобы избежать nested-writer deadlock SQLite. Sparse rebuild использует полные
представления частей. Integrity различает число canonical chunks и index points.

OKF export сохраняет полный section_title и chunks/projection.json с версией,
route, hashes и fragment_count. Существующего публичного импортера OKF нет;
наличие export не означает готовую операцию импорта. SQLite DB backup/rebuild
проверен изолированно. Для operational restore PostgreSQL требуется согласованный
набор DB, canonical files и Qdrant. Private mixed target подтвердил тот же active generation,18point payloads и13snapshots через native pg_dump/files SHA/Qdrant snapshot в отдельном процессе; это не полный production Compose rollout/rollback и не проверка памяти всего корпуса.


## Схема и порядок возврата для generic format1

Это план внедрения; production cutover не выполнялся и требует отдельной команды.
Private PostgreSQL прошла fresh Alembic chain и populated050 backup→restore→062,
проверку ORM, drift0, допустимый populated downgrade/reupgrade и восстановление
pre-upgrade backup. Actual production lifespan на private PG/Qdrant прошёл ready200,
поиск/snapshot без create_all и повторного embedding готовых points. Контролируемые
060/062 disk/contention proofs завершены; это не оценка стоимости на production-корпусе. Новый ORM до061 получает missing-column error даже при
выключенном writer: миграция должна предшествовать запуску нового backend.

1. До обновления остановить новые задания и дождаться завершения или штатной
   паузы уже работающих. Зафиксировать release/runtime/config identities и
   согласованный backup PostgreSQL, canonical files и Qdrant. Сохранить expected
   manifest для проверки restore, totals поколений/частей и старых chat snapshots.
2. Восстановить backup в новый Compose project/data directory согласно
   `docs/PRODUCTION_DEPLOYMENT.md`. Bundled использует штатные backup/restore
   scripts; external требует согласованного backup владельца инфраструктуры.
   Исходный работающий контур сохраняется до завершения проверки.
3. На копии сверить Alembic revision с реальной схемой; применить060/061/062.
   Измерить transient disk peak, длительность lock и concurrent-reader contention.
   Не использовать stamp или create_all вместо проверки drift. Проверить ORM,
   integrity expected manifest, поиск и старые snapshots до обработки документов.
4. Первый запуск нового backend сохраняет `CHUNK_INDEX_PROJECTION_ENABLED=false`
   (новый writerNULL). Только после приёмки и отдельной команды на rollout
   включить `CHUNK_INDEX_PROJECTION_ENABLED=true` в выбранной серверной
   конфигурации пилота; admin runtime должен вернуть chunk_projection_version=1.
   Schema upgrade
   отдельно от включения format1 и отдельно от регенерации корпуса. На пилоте
   проверить публикацию candidate, same-ID repair/backfill, точные источники,
   fixed queries, p95 и обе warm/cold RSS пары. Партии расширяются после отчёта.
5. Возврат зависит от сохранённых данных. До non-NULL marker и при title≤1024
   допускается только проверенный schema downgrade. После любого marker1
   (включая abandoned/all-short)061 откат заблокирован; при длинном title062
   сужение заблокировано. Удалять или обнулять active markers ради downgrade нельзя.
   Сохранять совместимый reader либо восстанавливать согласованный pre-upgrade
   backup в другом контуре с проверкой integrity/search/snapshots перед cutover.

До внедрения на целевом корпусе повторяется именно operational preflight: проверка
согласованного backup/restore, schema drift, свободного диска/WAL и окна блокировки.
Private результаты доказывают механизм, но не задают запас диска или время для
другого объёма данных.062 на synthetic2048chunks/16MiB не переписала relation:
18,0224MB до/после, тот же filenode; ожидающая AccessExclusive DDL блокировала
новый reader около0,81s при искусственно удерживаемой транзакции. На практике
сначала убрать длинные транзакции, ограничить lock_timeout/statement_timeout,
а при timeout отменить rollout и сохранить прежнюю рабочую версию. Не снимать
блокировки убийством чужих процессов и не запускать повторный upgrade вслепую.

Backfill/sparse private stress1078→25070parts прошёл с батчами≤64. Полный repair
одного документа проверен отдельно на native PG/Qdrant с fake embeddings:
2×0,9→2×4,5MB canonical body, RSS379→578MB. Repair читает canonical документ целиком;
из этого не следует постоянная память для произвольного документа. Источники
вставляются по parent edges, не по лексикографическому порядку ID. Для metadata
с escaped NUL PostgreSQL использует построчный raw-JSON fallback: память зависит
от крупнейшей записи; на32×8MiB stress RSS снизился887→354MB, но время выросло
1,38→6,10s. Этот компромисс сохраняется в release notes.

На16.10.2026 ограниченная очередь проверки завершена: A20 20/20, original19×3
57/57, A15 15/15 с ручной проверкой, четыре bounded resource fixtures. C21
сохраняется по неизменной retrieval-области. Прежняя полная warm/cold RSS-приёмка
большого документа остаётся неподтверждённой; пользователь запретил суточные

замеров не запускать. Исключение по полному RSS не согласовано. Частные resource proofs
не подтверждают общий peak pipeline. Актуальные scope/disposition и результаты —
в плане и отчёте от16.10.2026. Наличие OKF export не предоставляет публичный importer.
