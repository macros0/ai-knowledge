Дата: 04.10.2026. Список для согласования совместимости общего решения с
целевой платформой. Отличия от примеров сами по себе не означают несовместимость.
Ответы определяют необходимые адаптации. Реальные адреса, аккаунты, токены
и пути секретов в этот документ не включаются.

## Что уточнения меняют в плане

- **Частично раскрыты пункты 1, 3, 4, 6, 10, 12–15.** Свой chart предусмотрен
  процессом доставки; требования заменить Next статическим Nginx или выделить
  внешний `/api` → backend не установлены. Compact и frontend-only маршрут
  остаются предлагаемым решением до проверки полного workload contract.
- **Публикация:** новые Ingress не создаются; применяется Gateway API,
  порядок TLS различается между DEV и TEST/PROD. API версии и timeout значения шаблонов
  сверяются с установленными CRD и действующей policy, а не становятся defaults.
- **Операционная подготовка:** в декларации namespace требуется правильная
  форма `logging.enabled: true`; проверяется платформа Logging Operator →
  OpenSearch, VSO и подключение защищённых метрик. Это не разрешение устанавливать
  дополнительные операторы или выдавать приложению credentials индекса.
- **Доставка:** проверяются inputs конкретных версий компонентов, CI Lint,
  доступность release digests и разрешённые CA/mirrors. Миграция remote mirrors
  не означает переноса всех release repositories. `manual` и `linux/amd64`
  остаются решениями проекта, пока их обязательность не установлена отдельным
  действующим контрактом; примеры `on_success` не отменяют принятую policy.
- **Остаются открытыми пункты 2, 5, 7–9, 11**, а также нераскрытые части
  остальных: компактный Pod/Jobs, остановка backend, storage/RPO/RTO, OIDC,
  профиль аудита и гарантии доставки. Наличие PROXY protocol не доказывает
  доверенный IP. Новые public/PKCE, outbox и HMAC параметры не вводятся в runtime
  только на основании этой сводки.

Ни один составной вопрос полностью не закрыт. Эта сверка обновляет документы,
но не подтверждает admission, CI execution или промышленную готовность.

## Цена адаптации и что стоит обобщить в продукте

Оценка от 04.10.2026 — инженерный ориентир для выбора решения, не договорная
смета и не подтверждение требований заказчика. Сложность вопроса для платформы
и цена изменения нашего продукта оцениваются отдельно: например, согласование
окна недоступности может быть долгим, хотя код Recreate уже есть.

**Единица оценки:** человеко-день (ч.д., 8 часов). Диапазоны включают разработку,
целевые автоматические проверки, review и документацию в доступном тестовом
контуре. Это трудозатраты команды, не календарный срок и не время работы агента.
Ожидание ответов/доступов, работа администраторов заказчика, инфраструктура,
лицензии и платные модельные вызовы не включены. Деньги считаются по согласованной
дневной ставке; без неё рублёвая цена не задаётся. Для бюджета после выбора
варианта разумно отдельно заложить резерв 30–50% до окруженческого discovery.

**Шкала:** настройка готового — обычно до 1 ч.д.; малая доработка — 1–3;
средняя — 3–10; большая — более 10 и отдельный этап проектирования/приёмки.
Интервалы, пересекающие границы, отражают неопределённость. Ноль разработки
не означает нулевую стоимость настройки и проверки у заказчика.

### От какой реализации считаем

Проверены текущий `main` и исходники checkout `codex/kubernetes-rollout`
(базовый commit `f551f5f` плюс рабочие изменения). Ветка ещё не интегрирована
в `main`. В ней уже есть compact chart, Recreate, bundled PG/Qdrant, lifecycle
backup/restore, Gateway/VSO/NetworkPolicy, release manifest/operator archive,
CI templates и toolbox с BuildKit secret mounts для CA/pip config. Эти работы
повторно как разработка с нуля не оцениваются. Интеграция ветки — отдельная
предварительная оценка **1–3 ч.д.**, если не выявятся значимые конфликты
и регрессии; её учитывают один раз, а не в каждой строке.

В `values.yaml` уже настраиваются UID/GID, resources, nodeSelector/tolerations,
image digests/pullSecrets, ссылки на PVC/Secret, Gateway host/TLS/request
timeouts и VSO binding. Probes, compact topology, один backend и Recreate
не являются свободно переключаемыми режимами. В runtime уже есть настройки
upload/LLM timeouts, mapping групп и TTL сессии. Public/PKCE/UserInfo profiles
реализованы и локально проверены в рабочей ветке; конкретная IdP registration
остаётся окруженческой проверкой. [OIDC отчёт](superpowers/reports/2026-10-04-oidc-compatibility-acceptance.md)
отделяет packaged suites/Keycloak matrix от целевой приёмки. Для следующего
этапа выбран durable outbox с повтором; [audit план](superpowers/plans/2026-10-04-audit-outbox.md)
исполняется: ядро runtime реализовано в рабочем дереве, локальная приёмка и оставшиеся gates — в [отчёте](superpowers/reports/2026-10-04-audit-outbox-acceptance.md). Доверенный IP — отдельный adapter.
Локальная приёмка не заменяет платформенную.

### Что разумно сделать общим заранее

1. **Пакет небольших улучшений конфигурации — ориентир 4–7 ч.д. один раз.**
   Описать поддерживаемые profiles и precedence, добавить только отсутствующие
   типизированные probe/traffic overrides и проверку согласованности лимитов,
   дать обезличенные примеры existing Secret/CA/scrape. Это общий пакет
   пересекающихся работ из пунктов 1/4/6/14/15, а не сумма всех строк и не
   реализация всего их расширенного объёма. Использовать готовые settings;
   не создавать вторую систему конфигурации. Применимые проверки и документация
   входят в оценку; отсутствующие metrics/OIDC/audit сюда не входят.
2. **OIDC compatibility profile — ориентир 6–10 ч.д. общим пакетом пунктов 7–8.**
   Public/PKCE/token auth method и authoritative UserInfo полезны нескольким
   заказчикам. Существующий confidential flow сохраняется; профиль выбирается
   явно и проверяется. Немедленный revoke, refresh/back-channel logout и
   поддержка любого IdP в этот пакет не входят.
3. **Аудит — выбрать один объём после согласования семантики.** Общая schema,
   auth события, transaction boundaries и best-effort JSON stdout — ориентир
   **7–14 ч.д.**; та же основа с durable outbox и recovery — **12–24 ч.д. всего**,
   а не дополнительно к 7–14. Оба варианта не обещают downstream ACK.
   Доверенный IP добавляется отдельно только при подтверждённом upstream contract.

Приоритет — интегрировать уже сделанное и подготовить небольшой пакет settings;
OIDC и audit выполнять отдельными проверяемыми изменениями. Kubernetes external
storage имеет смысл как общее расширение, если хотя бы один целевой заказчик
его требует. Zero-downtime, distributed workers, HA storage и универсальный
прямой API маршрут не стоит включать в стартовую поставку «на всякий случай».

**Граница обобщения:** стандартные runtime settings и проверенные profiles
живут в общем продукте; kgateway TrafficPolicy, VSO, ScrapeConfig и корпоративные
CI inputs — в опциональных adapters, отключённых там, где соответствующих API
нет. Конкретные CRD schemas и значения не становятся универсальными defaults.
Новые настройки не отключают production auth/TLS/CSRF, не разрешают неподдержанные
replicas и не превращают failed gate в passed. Каждая поддерживаемая комбинация
добавляет постоянную цену regression/support; обещать все сочетания не нужно.

### Что всё равно требуется от заказчика и как считать итог

Даже после обобщения нужны конкретные решения: допуск workloads/Jobs, окно
обслуживания, storage/RPO/RTO, регистрация и claims IdP, audit event/failure policy,
сетевая граница доверия IP, разрешённые CI/registry/CA, модельные capabilities.
Настройка позволяет выполнить эти требования после ответа, но не выбрать их
за владельца платформы.

Итог для выбранного объёма = интеграция существующей ветки (один раз) + выбранные
общие пакеты (один раз для продукта) + adapter конкретного заказчика + его
окруженческая приёмка. Повторное развёртывание у другого заказчика обычно
переиспользует общие пакеты; его adapter и проверки оплачиваются отдельно.
Для совместимого compact/bundled профиля с готовыми доступами предварительно
отвести **3–6 ч.д. на совокупную инфраструктурную приёмку DEV/TEST/PROD**:
auth/route/upload/SSE, admission, logs/metrics, backup/restore. Содержательная
live-model приёмка **3–7 ч.д.** указана отдельно в п. 15. При строгих RPO/RTO,
большом корпусе или сложной сети приёмку переоценить после discovery.

Диапазоны таблицы альтернативны и пересекаются; единой суммой всех 15 строк
пользоваться нельзя. Для каждой выбранной работы фиксируются исходное требование,
минимальный достаточный вариант, что включено, критерий проверки, одноразовая
часть продукта и повторяемая часть заказчика. Отсутствие ответа не означает
необходимость немедленно реализовать самый дорогой вариант. Эта оценка не
разрешает менять runtime или уже согласованные gates; реализация — отдельная задача.

## Уже известные условия

- Три независимых кластера: DEV, TEST, PROD; доступы к платформе существуют.
- PostgreSQL и Qdrant планируются внутри поставки, с независимыми данными
  каждой среды. Допуск этой схемы и эксплуатационные условия уточняются ниже.
- Настоящие LLM и embeddings доступны только в PROD; DEV/TEST используют
  synthetic profile без ослабления production auth protections.
- Здесь развивается общее решение; окруженческая интеграция выполняется
  в отдельной копии.
- Первая версия использует один backend process; реплики frontend/API/workers
  предусмотрены после отделения состояния и владения задачами.

Предлагаемая стартовая схема: HTTPS Gateway → Next frontend/proxy → внутренний
backend; компактный Pod с frontend/backend, отдельные bundled PG/Qdrant,
постоянные тома и разовые maintenance/migration Jobs. Это предложение для
согласования, а не утверждение о требованиях платформы.

**Найдено в документации:**

- Внешний HAProxy: `timeout connect` — 5 с; `timeout client/server` — 180 с

- В DEV TLS выпускает cert-manager по ListenerSet: срок 90 дней, перевыпуск

  платформы, TLS Secret создаётся вручную. Источник:
  «ListenerSet и TLS» (раздел `kubernetes/gwapi-listenerset/`).

**Остаётся уточнить и проверить:** действующие route/policy приложения,
max upload, место и режим буферизации multipart, SSE/heartbeat и cancel.
Описание WebSocket в документации не является приёмкой SSE. Доставка доверенных

для подписанного context Next→backend или предписан другой transport?

**Влияние:** реализуемость trusted-IP profile. HMAC после Next не доказывает
источник IP до Next. **Подтверждение:** sanitization order, allow/deny probes
и отказ spoofed headers на каждом доступном пути.

**Найдено в документации:** диагностический путь через NodePort Gateway
обходит внешний балансировщик; на listener'ах включён PROXY protocol.
Документация показывает проверку такого пути клиентом с `--haproxy-protocol`.
Legacy Ingress и HTTPRoute могут сосуществовать во время миграции, пока
балансировщик не переключён; новый Ingress создавать нельзя.
Источники: «диагностика Gateway» (раздел `kubernetes/gwapi-overview/#diagnostics`),
«сосуществование Ingress» (раздел `kubernetes/migration-gwapi/`).

**Остаётся уточнить:** сетевой допуск к NodePort, доверенные отправители PROXY
protocol, очистка/формирование IP headers и ограничения всех альтернативных
маршрутов. Само наличие PROXY protocol не доказывает подлинность клиентского IP.
Enforcing NetworkPolicy и relay credential Next→backend документацией не определены.

## Вопросы перед продвижением в TEST и PROD

### 13. Какие CI компоненты и gates обязательны

- [ ] **Дорабатываем для обобщения (в план):** стабильные команды build/package/
  deploy/restore и release manifest сохраняются общими; runner tags, repositories
  и ссылки на защищённую конфигурацию задаются параметрами. Корпоративные components
  подключаются adapters к этим командам. Проверить CI Lint/job graph, целостность
  digests и обязательные gates; готовые toolbox/operator scripts переиспользовать.

Разрешены ли pinned Python/Helm/kubectl toolbox и lifecycle Jobs? Какие
build/security/lint/promotion/restore gates, protected/manual rules и allowed
runner policies действуют? Как передавать одни digests, chart/operator archive
между code/deploy projects и обеспечивать retention артефактов?

**Влияние:** адаптация переносимых templates. **Подтверждение:** разрешённые
component inputs, schema/passport и merged GitLab CI Lint/job graph.

**Найдено в документации:** описаны ci-buildkit, cicd-helm-charts, cd-helm
и cd-kubectl. Helm рекомендуется для доставки. Сборка собственного chart
включает `helm lint`, `trivy config`, package/push; релизный путь включает
Security-Pipeline. Через него проходят артефакты перед попаданием в КСПД:
для Docker описаны SonarQube + Harbor, для Helm — SonarQube.
Общие runners используют Docker executor на Linux с тегами по средам.
Есть компонент проверки MR approvals; `manual` для PROD показан в примерах
доставки, что само по себе не устанавливает обязательную policy проекта.
Источники: «каталог компонентов» (раздел `gitlab/cicd-components/`),
«Helm CI» (раздел `ci/helm-semantic/`),
«Security-Pipeline» (раздел `security/security-pipeline/`),
«runners» (раздел `gitlab/runners/`),
«approvals» (раздел `ci/approve/`),
«Helm CD» (раздел `cd/helm/`).

**Остаётся уточнить:** допуск pinned toolbox и lifecycle Jobs, полный набор
обязательных gates, protected/manual rules, перенос одних digests и retention.
Нужны README/inputs выбранных версий компонентов и CI Lint/job graph проекта;
наличие примеров на портале этого не подтверждает.

**Дополнение по sample-проектам:** реальные `.gitlab-ci.yml`, выбранные версии
компонентов и расхождения с README/порталом разобраны в разделе
«Проверка примеров CI/CD» ниже. Это примеры конфигураций, не результаты запуска
нашего pipeline и не полный обязательный CI contract.

### 14. Как доставляются Secrets, образы, packages и CA

- [ ] **Дорабатываем для обобщения (в план):** единый contract existing Secret,
  trust bundle, registry/pullSecrets и mirrors/proxy; VSO и другие подтверждённые
  способы доставки подключать опциональными adapters. Готовые CA/BuildKit secret
  mounts переиспользовать, описать ротацию с управляемым restart. Hot rotation
  и поддержка любых secret backends не входят автоматически в этот пакет.

Какие утверждённые механизмы runtime Secrets/kubeconfig/registry access и
trust bundle доступны? Какие mirrors/proxy/air-gap ограничения действуют?
Можно ли использовать BuildKit secret mounts; как выполняется ротация без
вывода содержимого секретов в логи?

**Влияние:** окруженческие adapters. Реальные endpoints/passwords/Vault paths
задаются защищённо. **Подтверждение:** delivery/trust contract и connectivity probes.

**Найдено в документации:**

- Vault интегрирован с Kubernetes во всех средах через VSO. Параметр `team`
  при создании namespace запускает привязку через Stem; VaultStaticSecret
  задаёт синхронизацию секрета, `vaultAuthRef: default` обязателен.
  TLS не следует доставлять через VSO: отдельная процедура — в пункте 6.
  Источник: «Vault в Kubernetes» (раздел `vault/kubernetes/`).
- Для CI/CD kubeconfig хранится в Vault. cd-helm описывает получение
  registry-токена из Vault и подстановку значений через `vals eval`.
  Хранение и ротацию секретов команда организует самостоятельно.
  Источники: «Helm CD» (раздел `cd/helm/`),
  «Vault» (раздел `vault/access/`).
- Для внутренних HTTPS-ресурсов в образах должны быть корпоративные CA:
  предлагаются готовый базовый образ или перенос сертификата через stage
  `distroless-ca`. Источник:
  «корневые сертификаты» (раздел `ci/ca-certs/`).
- Описаны зеркала внешних пакетов/образов и миграция remote repositories
  из Artifactory в Registry (Artifact Keeper), с рекомендацией virtual
  repositories. Это отдельная миграция зеркал; из неё не следует перенос
  всех проектных release repositories.
  Источники: «Registry» (раздел `artifactory/remote-registry/`),
  «миграция зеркал» (раздел `artifactory/migration-remote/`).

**Остаётся уточнить:** BuildKit secret mounts, фактическая связность/mirrors
и air-gap ограничения каждой среды, механизм ротации приложения без раскрытия
секретов в логах. Реквизиты задаются в защищённой конфигурации отдельной копии.

### 15. Как принимаются модели и мониторинг в PROD

- [ ] **Дорабатываем для обобщения (в план):** документированный contract

  Стабильные metrics и защищённый scrape contract с опциональными manifests.
  Готовые settings сохранить; качество моделей, нагрузка и переиндексация
  при смене dimensions остаются отдельными сценариями приёмки.

Какие model/tokenizer capabilities и embedding dimensions доступны? Каковы
лимиты, таймауты, ожидаемая нагрузка и окно live smoke? Как монитор получает

**Влияние:** доверенный model budget, совместимость индекса и observability.
DEV/TEST synthetic profile не проверяет качество моделей. **Подтверждение:**

### Что примеры уточняют в открытых вопросах

- **Пункты 1, 2, 4 — chart и workload contract.** Собственный chart является
  конкретным sample-проектом. Его Deployment содержит один контейнер, параметры
  image/ports/resources/imagePullSecrets, но не задаёт strategy, probes,
  securityContext, PVC или Jobs. Это не универсальный контракт для нашего
  приложения и не подтверждение допуска Recreate, двух контейнеров либо bundled
  storage. Go-сервис имеет `/health` и порт по умолчанию 8080; шаблон Deployment
  не подключает этот endpoint к probes. Переносить его порт и ресурсы к нам
  без расчёта не требуется.
- **Пункты 3, 4, 6 — публикация.** В sample-chart сохранён `templates/ingress.yaml`,
  но `ingress.enabled: false` по умолчанию. Проверенный `values-dev.yaml`
  deploy-helm его не включает; Gateway API ресурсов в этих трёх шаблонах нет.
  Следовательно, пример не демонстрирует актуальную внешнюю публикацию через
  Gateway и не разрешает создавать новый Ingress вопреки действующей документации.
- **Пункт 13 — версии и promotion.** Портал показывает cicd-helm-charts `3.1.2`,
  оба sample chart уже используют `3.1.4`. В deploy-helm CI указано
  `chart-version: "v1.0.1"`, тогда как README описывает `1.0.1`. Нельзя молча
  нормализовать такой префикс: перед использованием нужна сверка реального
  OCI artifact и inputs выбранной версии компонента. Образ в values задаётся
  через tag `1.0.0`, не через digest; пример не доказывает сохранение одного
  digest между средами. Helm/kubectl примеры настроены только на DEV с
  `on_success`, поэтому не задают protected/manual policy TEST/PROD.
- **Пункты 13, 14 — архивы и секреты.** Пример proprietary показывает маршрут
  готового ZIP; сборка нашего operator archive, checksums, retention и restore
  gates остаются отдельной задачей. Deploy README описывают JWT-доступ к Vault
  и `dry-run: "true"`; README Helm описывает `vals eval`. Однако проверенный
  `values-dev.yaml` содержит только replica/image/service overrides, без
  `ref+vault` значений. Поэтому это описание возможностей компонента, а не
  выполненная проверка подстановки секретов; содержимое секретов не читалось.
- **Пункт 14 — корпоративный CA.** Механизм копирования CA подтверждён
  Dockerfile nginx. Примеры используют `distroless-ca:2.0.1`, тогда как
  текущая страница портала показывает `2.1.1` и другой repository. Для адаптера
  нужно выбрать разрешённый доступный образ; старые pins/mirror paths из sample
  не становятся актуальными реквизитами среды. BuildKit secret mounts примерами
  не подтверждены.
- **Пункт 15 — scrape.** `deploy-kubectl` даёт конкретный пример
  `monitoring.coreos.com/v1alpha1` ScrapeConfig: `staticConfigs`, `/metrics`,
  интервал `30s`, цель — exporter на VM. Это sample-настройка, не обязательный
  интервал. TLS/auth для защищённых audit endpoints, выбор ScrapeConfig
  экземпляром Prometheus, alert thresholds и модельная приёмка остаются открытыми.

Примеры не закрывают storage/RPO/RTO, OIDC/claims, audit schema и гарантии
доставки, trusted IP и согласованное окно недоступности. Состав частично
раскрытых пунктов после этой проверки не изменился.
