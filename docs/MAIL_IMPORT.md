# Операторская процедура импорта сохранённых Outlook-писем

Эта процедура относится к ручной загрузке выбранных пользователем файлов
`.eml` и `.msg`. Сервис не подключается к Outlook, Microsoft Graph, PST/OST
или почтовому ящику. Текущий набор форматов и проверенных ограничений указан в
[MAIL_FORMAT_SUPPORT.md](MAIL_FORMAT_SUPPORT.md).

## Включение новых standalone-писем

Для production флаг `MAIL_IMPORT_ENABLED` по умолчанию имеет значение `false`. До выполнения
приёмки API отклоняет новые `.eml` и `.msg` кодом `mail_import_disabled` до
записи файла на диск. Вложенные письма в новых DOCX/XLSX/PDF сохраняются в
исходных bytes для скачивания, но их тела не извлекаются и не попадают в поиск;
родительский документ продолжает обрабатываться и получает предупреждение
`mail_import_disabled`. Уже обработанные документы и их дерево источников при
выключенном флаге остаются доступны.

Это требование относится к production. В текущей локальной разработке по
указанию пользователя `MAIL_IMPORT_ENABLED=true` сохраняется во время приёмки.

В production включать флаг допускается только после успешной приёмки из плана Outlook mail
ingestion и фиксации её результата. Для выбранного runtime env-файла задайте:

```text
MAIL_IMPORT_ENABLED=true
```

Затем штатно перезапустите backend и проверьте один синтетический EML upload.
Не включайте флаг как способ восстановить старые документы: для них существует
отдельный управляемый reparse ниже.

### Dev PostgreSQL schema drift

`create_all` не добавляет колонки в уже существующие таблицы. Сначала проверьте
выбранный runtime, фактическую схему и `alembic_version` без изменений:

```powershell
# Из backend/, DATABASE_URL должен указывать на проверяемую dev-базу.
& .\.venv\Scripts\python.exe -m scripts.migrate_mail_schema
```

Скрипт показывает `missing`, `conflicts`, `alembic_versions` и `ready`.
Exit 1 при `ready=false` означает обнаруженное расхождение. Он сравнивает все
типы изменений в таблицах mail/publication, включая типы, nullable, индексы и FK;
это не аудит всей схемы приложения.

После проверенного backup и остановки writers сначала повторите процедуру на
отдельной копии. Если `conflicts` пуст, адресное применение выполняется так:

```powershell
& .\.venv\Scripts\python.exe -m scripts.migrate_mail_schema --apply
& .\.venv\Scripts\python.exe -m scripts.migrate_mail_schema
```

`--apply` разрешён только при `ENVIRONMENT=development`. Он создаёт лишь известные
новые source/generation tables, добавляет недостающие nullable mail/checkpoint
колонки и их индексы. Определения существующих колонок, данные и `alembic_version`
не изменяются. Повторное применение — no-op. Любой несовместимый diff блокирует
работу до первого DDL; это не универсальный автоматический repair произвольной схемы.
Не ставьте вручную `alembic_version` и не запускайте вслепую `alembic upgrade head`
на старом dev-кластере: его revision может не соответствовать `create_all`.

Read-only проверка текущего dev-кластера 26.09 выявила отсутствующие
`document_generations.publication_hash` и `document_staging.generation_id`, а
также nullable drift `created_at` в `document_chunks`/`okf_attachments`.
Revision — `f0a1b2c3d4e5`, NULL timestamps в обеих таблицах — 0 на момент проверки.
Автоматическое применение отказало бы из-за conflicts; **live repair не выполнялся**.
Для этого конкретного старого drift после повторной проверки копии и backup
оператор может сначала привести nullable к моделям:

```sql
BEGIN;
ALTER TABLE document_chunks ALTER COLUMN created_at SET NOT NULL;
ALTER TABLE okf_attachments ALTER COLUMN created_at SET NOT NULL;
COMMIT;
```

Команды идемпотентны и проверяют существующие данные: при появившихся NULL они
должны отказать, а не заполнять даты выдуманными значениями. Затем повторяется
dry-run адресного скрипта. Эта процедура не является разрешением менять live
корпус в рамках текущей приёмки; результат сверки сохранён в локальном артефакте
`tests/tmp/mail-v15/dev-schema-audit.json`.

Позднее 26.09 по отдельному прямому поручению пользователя рабочая
`okf_knowledge` :5432 исправлена: verified pg_dump/restore copy, две недостающие
колонки и три старых nullable drift, включая `attribute_values.sort_order`.
Полная metadata теперь совпадает, существующие строки всех38 таблиц сохранены,
backend восстановлен. Историческое «live repair не выполнялся» выше относится
к предыдущей приёмке. Alembic revision не переписывался.
[Отчёт обслуживания](superpowers/reports/2026-09-26-dev-mail-schema-repair.md)
содержит backup, точные изменения и границы проверки второй базы.

## Поиск кандидатов среди старых документов

Из каталога `backend/`, при доступных БД, Qdrant и настройках приложения:

```powershell
& .\.venv\Scripts\python.exe scripts/reparse_mail_documents.py `
  --report ..\tests\tmp\mail\reparse-candidates.json
```

Это dry-run: он не меняет БД, Qdrant, файлы и не запускает LLM. В отчёте нет
текста писем; для каждого кандидата есть только `doc_id`, имя, размер, статус
и уровень уверенности.

- `confirmed_standalone_mail` — исходный документ имеет расширение `.eml` или
  `.msg`.
- `embedded_ole_candidate` — DOCX содержит CFB/OLE-объект под
  `word/embeddings`. Это не доказательство, что объект является MSG: скан не
  распаковывает Ole10Native/Package и ограничен 10 000 ZIP-members.

Отсутствие кандидата не доказывает отсутствие почтового вложения в старом
документе. Скан используется для оценки объёма, а не для удаления или
перезаписи данных.

Для проверки конкретного активного документа `--doc-id` повторяется:

```powershell
& .\.venv\Scripts\python.exe scripts/reparse_mail_documents.py `
  --doc-id <document-id> --doc-id <document-id> --report report.json
```

`--limit` ограничивает кандидаты после стабильной сортировки по ID и удобен
для малой пробной выборки.

## Управляемая регенерация

Полная регенерация создаёт отдельное поколение и заново выполняет
parse → chunks → LLM → index. Прежнее опубликованное поколение остаётся
доступным до успешного переключения. Ошибка или отмена кандидата не разрешают
смешивать его источники с опубликованными. Нехватка места переводит обработку
в `paused/storage_full`: освободите место и используйте штатный resume.
Регенерация может потреблять LLM-квоту и создаёт очередь, поэтому сначала
сохраните и проверьте dry-run отчёт.

Для самостоятельных EML/MSG после согласованной выборки используется:

```powershell
& .\.venv\Scripts\python.exe scripts/reparse_mail_documents.py `
  --doc-id <document-id> --apply --timeout 3600 --report reparse-result.json
```

DOCX с `embedded_ole_candidate` намеренно не запускаются этой командой. После
отдельной проверки кандидатов допускается явное расширение области:

```powershell
& .\.venv\Scripts\python.exe scripts/reparse_mail_documents.py `
  --limit 10 --apply --include-embedded-candidates --report reparse-result.json
```

Скрипт вызывает только штатные `Pipeline.regenerate()` и `wait_for()`; он не
пишет SQL, Qdrant или storage напрямую. В отчёте `regenerated` означает, что
очередь завершилась, а `final_status` должен быть проверен отдельно: `done`
может содержать штатный `problem` и не равен автоматическому подтверждению
качества. `error` сохраняет ошибку одного документа и не прерывает отчёт для
остальных.

## Откат и наблюдение

При проблеме в production выключите `MAIL_IMPORT_ENABLED`, остановите новые задания
регенерации и сохраните JSON-отчёты. Не удаляйте additive-колонки или дерево
источников ради быстрого возврата: старый бинарник может читать существующие
данные только после проверки его совместимости. Восстановление выполняют из
backup в новом каталоге и новой БД, затем проверяют источники, скачивание и
поиск на тестовой выборке. Во время текущей локальной приёмки флаг остаётся
включённым по указанию пользователя.

### Parser-version checkpoint

После добавления диагностики применяются миграции `fb0b1c2d3e4f` (колонки
`documents.parser_version`, `documents.parse_warnings`) и `fc0b1c2d3e4f`
(`document_staging.parser_version`). Для старого dev-кластера адресный repair
добавляет эти nullable-колонки только после проверки фактической схемы.

Текущая версия парсера `mail-sources-v21` получает суффикс `-mail-disabled` при
выключенном импорте. Частичный checkpoint, созданный другой версией парсера
(в том числе при другом значении флага), не возобновляйте:
API вернёт `parser_version_mismatch`, после чего нужен штатный полный
regenerate. Checkpoint без версии считается legacy и остаётся совместимым.

### Checkpoint исходного файла и bundle source manifest

Migration `fd0b1c2d3e4f` добавляет nullable
`document_staging.source_file_hash`. При создании checkpoint сервис записывает
SHA-256 исходного файла; если байты файла изменились до частичного resume,
возвращается `partial_regeneration_unavailable` и требуется полный regenerate.
Checkpoint без этого поля остаётся legacy-совместимым.

Производный OKF bundle содержит `sources.json` (schema version 1) с деревом
источников. В нём допустимы только относительные `saved_path`; абсолютные и
выходящие за корень пути сериализуются как `null`. Этот manifest предназначен
для диагностики и восстановления метаданных, а скачивание оригиналов всё равно
разрешается только через зарегистрированный source endpoint.

### Модель и авторство

В проверенном локальном контуре `LLM_MODEL` и `LLM_CHAT_MODEL` установлены в
`openrouter/openai/gpt-4.1` по разрешению пользователя. GPT-4.1 прошла небольшой
синтетический набор извлечения фактов и противодействия инструкциям из источника;
это не гарантия безошибочности на произвольных документах. Nemo воспроизводимо
исполняла инструкции из EML и DOCX. Production env examples остаются примерами:
перед включением imports проверяйте фактически выбранную модель и её ответы,
а не переносите результат приёмки GPT-4.1 на другую модель.

При явном вопросе об авторстве чат повторно читает исходные SQL-чанки, а модель
выбирает только проверяемые дословные цитаты. Отправитель и office creator не
доказывают авторство вложения. Явная строка «Автор таблицы: …» показывается как
указание источника; подписанные реплики — как обозначения реплик, без переноса
подписи на весь документ. Нераспознанные подписи или недостаточная выдача дают
неустановленное авторство. Проверка лексическая и не охватывает все парафразы.
Предварительная оценка риска всех чанков и решение администратора остаются
отдельным будущим планом, не частью уже включённого контроля.
