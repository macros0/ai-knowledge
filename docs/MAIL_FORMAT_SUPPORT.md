# Поддержка сохранённых Outlook-писем

Сервис принимает выбранные пользователем `.eml` и `.msg` как один документ. Outlook,
COM, PST/OST и сетевые API не используются.

Корневой `.eml` допускается только как структурированное RFC 5322-сообщение: в нём
должны быть разделитель заголовков и хотя бы один структурный mail-header (`From`,
`To`, `Date`, `Message-ID`, `MIME-Version` или `Content-Type`). Один `Subject` не
считается сообщением. Некорректный файл отклоняется на preview с `422` и кодом
`mail_parse_failed` до записи документа, задания или постоянных вложений.
Проверка корневых EML/MSG выполняется и при `dedup_enabled=false`; поиск
похожих документов от этого не включается. Root RTF-only, защищённое письмо
и неподдерживаемый Outlook object отклоняются с отдельными кодами
`mail_rtf_unsupported`, `mail_protected`, `mail_object_unsupported`.
Отказ дочернего источника не запрещает загрузку читаемого родителя.
Начиная с `mail-sources-v22`, MSG распознаёт IRM также по named MAPI
`PidNameContentClass` (`Content-Class`, `PS_INTERNET_HEADERS`), даже без
transport-заголовка. Встроенные MSG наследуют карту имён корневого контейнера,
но читают значения из собственного storage. Повреждённая карта отклоняется;
расшифровка и проверка криптографической подписи не выполняются.
Таймаут и лимит памяти supervisor имеют коды `parser_timeout` и
`parser_resource_limit`; занятые slots — прежний `429` с `Retry-After`.
Отказ установки OS-защиты — `503 parser_isolation_unavailable`, без admission
документа и без попытки повторить разбор в незащищённом процессе.

Перед выпуском импорт выключен по умолчанию (`MAIL_IMPORT_ENABLED=false`).
После приёмки его включает оператор через `MAIL_IMPORT_ENABLED=true`. При выключенном
флаге новые `.eml`/`.msg` отклоняются, а письма внутри DOCX/XLSX/PDF сохраняются
как оригинальные вложения со статусом «Письмо сохранено, импорт отключён» без
извлечения тела и без индексации. Текст и другие вложения родительского документа
обрабатываются. Выключение не удаляет и не скрывает уже обработанные письма и их
дерево источников. Переключение флага меняет версию парсера в checkpoint;
частичный resume между режимами требует полного regenerate.

Разбор недоверенных файлов выполняется в отдельном worker с лимитом 120 секунд,
1024 MiB и максимум двумя одновременными worker на один backend-процесс. При
занятых слотах preview возвращает `429` с `Retry-After`; увеличение этого
предела требует отдельного нагрузочного прогона.

Граница worker использует JSON с ограничением 16 MiB, а не pickle IPC. Перед
самим разбором worker оставляет только системный allowlist окружения и не
получает `DATABASE_URL`, ключи LLM или другие настройки backend.
Ошибки parser-библиотек через эту границу передаются только как стабильный тип
ошибки, без `str(exc)` и потенциальных фрагментов письма.

## HTML-письма

С `mail-sources-v17` общий обработчик EML/MSG сохраняет ссылки HTML на
`http`, `https` и `mailto` в абзацах и таблицах. Адреса не запрашиваются при
извлечении. Относительные, protocol-relative, `file`, `data`, `javascript`
и некорректные адреса остаются обычным текстом подписи ссылки. Скобки и другие
разделители Markdown в адресе кодируются; амперсанд экранируется на Markdown-слое,
чтобы повторное декодирование entities не меняло query-параметры.

Текстовые узлы HTML экранируются как буквальный текст: `![pixel](...)`,
`&copy;`, entity-decoded `<img>` и префиксы списков не становятся картинкой,
другим символом, raw HTML или структурой Markdown. Вложенные/незакрытые anchors
не поглощают соседние абзацы. Это не разрешает HTML-рендеринг писем.
С `mail-sources-v18` CID-картинки PNG/JPEG/GIF/WebP связываются с локальным
вложением того же письма, в том числе без имени файла. Формат проверяется по
bytes после допуска по лимитам, оригинал сохраняется без перекодирования.
Одинаковые CID у родителя и вложенных писем не смешиваются; повтор CID внутри
одного письма неоднозначен и не отображается. SVG, повреждённые и отсутствующие
картинки остаются подписью с предупреждением `cid_image_unavailable`; сохранённый
оригинал доступен для скачивания. Удалённые картинки не загружаются парсером.
Письмо только с картинкой не отправляется в LLM и получает `no_text_layer`;
OCR не выполняется. Даже короткий текст рядом с картинкой обрабатывается.

С `mail-sources-v19` тема письма сохраняется в каноническом тексте и метаданных,
но сама по себе не запускает генерацию и не считается текстовым слоем. Пустое
письмо и письмо только со сканом получают `no_text_layer`; текст XLSX-вложения
обрабатывается отдельно от пустого тела письма. При возобновлении после сбоя
публикации это решение вычисляется заново, готовые чанки не генерируются повторно.
Извлечённые изображения PDF не подменяют оригинальный PDF в дереве источников.

В смешанной цепочке MSG → EML → MSG → XLSX уровень 3 останавливается до чтения
MAPI-свойств и bytes XLSX. Доступен предыдущий контейнер MSG, узел пропущенного
XLSX имеет `skipped_depth` и предупреждение `attachment_depth_exceeded`.

## MSG backend

### Неподдерживаемые текстовые контейнеры

С `mail-sources-v16` неразобранные CFB (включая legacy DOC/XLS), ZIP,
PST/OST и TNEF получают `unsupported_attachment_format` и статус
`unsupported`, даже если файл переименован в `.bin`. Поддерживаемые DOCX/XLSX,
PDF/EML/MSG сначала проходят обычное распознавание и извлечение. Сохранённые
bytes неподдерживаемого контейнера доступны для скачивания; его внутренний
текст не индексируется, доступное тело письма и соседние вложения сохраняются.
Документ получает `attachment_partial_result`; дерево источников объясняет
ограничение на русском и английском. Лимиты размера/глубины/числа узлов имеют
приоритет перед диагностикой формата.

Это сигнатурное обнаружение потенциально текстовых контейнеров, а не проверка
их исправности: ZIP/CFB fixtures имеют реальную контейнерную структуру,
PST/OST/TNEF probes проверяют заголовки. Сигнатуры сверены с
[MS-PST HEADER](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/c9876f5a-664b-46a3-9887-ba63f113abf5)
и [MS-OXTNEF ABNF](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxtnef/b03b5704-ef54-4390-b981-dc78f8e79a05).
Произвольные исторические варианты и архивы с префиксом этой проверкой не
покрываются. Обычные непрозрачные бинарники и картинки остаются `saved` без
предупреждения о потере текста.

С версии `mail-sources-v8` используется собственный reader выбранных MAPI-свойств
поверх `olefile`; справочник имён свойств берётся из `msg_parser` 1.2.x
(BSD-2-Clause). `MsOxMessage` больше не вызывается: он заранее читает вложения
и распаковывает RTF. Установленная зависимость `compressed-rtf` 1.0.x (MIT)
используется генератором тестовых fixture, но RTF не распаковывается при импорте.
Проверены на Python 3.12 локально
с `tests/fixtures/mail/outlook-sample.msg`: SHA-256
`028d84ffe67e1865009669d13d4c12682943b32eccf7f84a8da1899db63b0131`.
Образец происходит из MIT-набора тестов Microsoft MarkItDown; он проверяет реальный
OLE/MAPI контейнер, тему и plain-text body без Outlook.

`tests/fixtures/mail/rtf-simple-sent.msg` (Apache-2.0, SHA-256
`8adf5c3c77b46d9fa5910c3bb6ba54930160c4a9292348669f11c4d17cac8421`)
содержит ANSI plain body (`1000001E`) вместе с RTF (`10090102`): извлечение
plain body подтверждено. Прежнее название теста «RTF-only» было неточным;
этот файл не доказывает извлечение RTF без plain/HTML альтернативы.

`synthetic-rtf-only-compressed.msg` и `synthetic-rtf-only-uncompressed.msg`
(MIT, SHA-256 в manifest) содержат настоящий поток `10090102`, без `1000`/`1013`.
Корневое и вложенное RTF-only письмо получают `unsupported_rtf_body`, source
показывает «Не поддерживается». RTF-поток не открывается; доступные обычные
вложения обрабатываются отдельно. Problem-код объясняет, что нужно скачать
оригинал и сохранить письмо с plain/HTML-телом. Это явное ограничение формата,
а не утверждение о поддержке преобразования RTF.

Для ANSI читается MAPI codepage; `28591` явно сопоставлен с `iso-8859-1`
по [таблице Microsoft](https://learn.microsoft.com/en-us/windows/win32/intl/code-page-identifiers).
Наличие Python codec проверяется через `codecs.lookup`, а не декодированием
пустой строки, которое не гарантирует такой проверки.

Бинарные вложения читаются непосредственно из CFB-потока `37010102`: путь
`msg_parser.PtypObject` удаляет нулевые байты и потому непригоден для сохранения
оригиналов. Затем bytes проходят общий рекурсивный путь DOCX/XLSX/PDF/EML.
Вложенный MSG может быть OLE
substorage, а не отдельным байтовым потоком: его topic/body и последующие
вложения читаются относительно полного пути substorage и получают дочерний
узел источника. Это также обходит ошибку зависимости, которая разрешала
вложенные свойства от корня CFB и подставляла тело внешнего письма.
`tests/fixtures/mail/nested-rtf.msg` (Apache-2.0, SHA-256
`ee87b46667a0f262b3f119967a5854610bd197508067c51b53fb7ff0abfb8962`) проверяет
этот путь без Outlook.

Синтетический `synthetic-unicode-attachment.msg` (MIT,
SHA-256 `2fa5cdebfe6526c943c788e2613c02e24fc855fae072a4fcfd50ed8dbc044229`)
добавляет кириллическую тему и настоящее XLSX-вложение. Проверены DOCX → MSG →
XLSX, включая MSG в ячейке DOCX, принадлежность значения 3509/12 дочернему
источнику и побайтовое равенство сохранённых MSG/XLSX. Это синтетический
CFB/MAPI fixture, а не результат экспорта из установленного Outlook.

Для каждого сохранённого вложения имя на диске строится только из `source_id` и
индекса (`source-root-0.xlsx` и т. п.); исходное имя остаётся только метаданным
источника. Каталог вложений и каждый создаваемый файл проверяются до записи:
symlink/reparse point или коллизия, которую нельзя безопасно выделить, дают
`skipped_storage`, не отменяя разбор соседних источников.

Тип вложения определяется структурой bytes, а не только суффиксом имени:
RFC 5322-сообщение в `xl/embeddings/` и EML-вложение PDF получают тот же
рекурсивный mail path, что и standalone-файл. Канонический текст одного
корневого документа ограничен 2 000 000 Unicode-символов. При достижении
лимита сохраняются source/download metadata, документ получает предупреждение
`text_limit_exceeded` и problem `text_partial_result`; хвост не попадает в
поиск.

С `mail-sources-v15` XLSX обходит все файлы `xl/embeddings/`, включая `.eml`,
`.msg`, `.xlsx` и имена без расширения. Directory entries пропускаются;
node/byte admission выполняется до чтения payload. MSG/EML извлекаются также
из CFB `Package` и `\1Ole10Native` (raw NativeData или Packager file record).
DWORD-размер NativeData проверяется по
[MS-OLEDS 2.3.6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-oleds/cc825ec3-f0ed-4023-97f6-13c323ac1172),
поля Packager сверены с
[Apache POI Ole10Native](https://github.com/apache/poi/blob/trunk/poi/src/main/java/org/apache/poi/poifs/filesystem/Ole10Native.java).
Пути и команды внутри record никогда не выполняются и не используются для I/O.
Извлечённый файл сохраняется без пересериализации; исходная оболочка остаётся
в корневом документе. Неизвестные/усечённые layouts остаются opaque вложением.
Это поддержка проверенных layouts, а не всех разновидностей OLE.

S/MIME encrypted EML (`application/pkcs7-mime`) не расшифровывается и не
индексируется. Новая корневая загрузка отклоняется до admission. Для вложенного
письма или уже сохранённого документа исходные bytes остаются доступны,
а разбор даёт предупреждение и problem `encrypted_mail`. Для `multipart/signed`
сервис извлекает доступное тело, но не заявляет о проверке подписи.

У MSG классы `IPM.Note.SMIME` и header `Content-Class: rpmsg.message` дают
`protected_mail`: fallback body не индексируется. Новый root отклоняется до
admission; оригинал вложенного или ранее сохранённого источника остаётся доступен.
Класс SMIME может обозначать и непрозрачную подпись, поэтому этот статус
не объявляет каждый объект зашифрованным. Для `IPM.Note.SMIME.MultipartSigned`
доступное тело извлекается с `signature_verified=false`. Calendar/contact/task
и прочие классы вне mail/post/report дают `unsupported_mail_class`.
Различия классов основаны на [MS-OXOSMIME](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxosmime/6d0deda8-4e31-4949-bdd6-8c2e54d04736)
и [MS-OXPROPS](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxprops/183b7080-abbe-4b25-bb5c-160397282de8).
Проверены диагностические маркеры на синтетических MSG; реальная криптографическая
совместимость IRM/S/MIME этим не подтверждается, подписи не проверяются.

Текст любых source blocks, включая письма и их вложения, считается
недоверенными справочными данными. Системный prompt запрещает выполнять или
повышать приоритет инструкций из документа; они могут быть описаны только как
факт, если этого прямо просит пользователь.

Точное место концепта (`exact`) сохраняется только для проверенного дословного
диапазона исходного чанка. Если цитаты нет, поиск абзаца по терминам текста
концепта может дать отдельный статус `inferred` («Предполагаемый абзац»);
совпадение только темы письма, общее слово или противоположное утверждение с
отрицанием недостаточны. Когда надёжного кандидата нет, интерфейс открывает
чанк без подсветки конкретного абзаца. Старые почтовые диапазоны на целый
абзац проверяются при чтении и не считаются точными только из-за сохранённых
координат.

Из почтовых headers сохраняются только subject, From, To, Cc, Date,
Message-ID, In-Reply-To и References; у MSG также сохраняются класс сообщения
и Content-Class для диагностики защищённого содержимого.
`date_raw` хранит исходную дату, `sent_at` — нормализованное UTC-время или null.
Невалидная дата и строковая дата без известного часового пояса остаются неизвестными.
MAPI FILETIME reader преобразует непосредственно в UTC по
[контракту FILETIME](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-filetime),
предпочитая ClientSubmitTime времени доставки. Bcc и transport headers (например, Received) не входят в metadata
или canonical text и потому не передаются в индекс или LLM.
У вложенных MSG без DisplayTo/DisplayCc fallback использует только записи
получателей с явно указанной ролью To/Cc; Bcc, ReplyTo и неизвестная роль
не превращаются в To. Этот фильтр введён в `mail-sources-v5`; сохранение дат и
связей переписки — в `mail-sources-v6`; точные bytes вложений, контекст дочернего
MSG и диагностика классов — в `mail-sources-v7`; корневой native reader,
отказ от RTF и проверка глубины перед OLE в общем пути — в `mail-sources-v8`;
отложенное чтение MSG и проверки MIME перед transfer decode — в `mail-sources-v9`;
исходные RFC822 bytes и ограничения MIME-структуры — в `mail-sources-v10`:
старые незавершённые checkpoints требуют штатной проверки версии, а уже
опубликованные документы автоматически не перегенерируются.

## Ограничения

- Нет PST/OST, Graph, автоматического обхода ящика и внешних загрузок.
- Уровни вложений 1–2 разбираются; третий отмечается как пропущенный.
- Одно вложение ограничено 50 MiB, суммарно 200 MiB и 1000 узлов.
- В HTML-письмах не выполняются скрипты и не загружаются удалённые ресурсы.
- Не подтверждены IRM/шифрованные/подписанные MSG и нестандартные RTF codepage
  варианты сверх pinned ANSI fixture.
- RTF-only без plain/HTML явно не поддерживается на корне и во вложениях;
  RTF-поток не читается и не распаковывается.
- Общий путь вложений отклоняет слишком большой исходный payload и запрещённую
  глубину до открытия OLE/ZIP; допустимые исходные bytes на границе глубины
  сохраняются для скачивания в пределах общего бюджета.
- В MSG дескрипторы вложений читаются отложенно: исчерпанный счётчик проверяется
  до свойств attachment, глубина substorage — до его тела, declared stream size
  и общий byte budget — до `olefile.openstream` (он сам буферизует поток).
  Property/metadata streams тоже расходуют общий бюджет. Фактическая длина
  сверяется после чтения. Ошибка дочернего stream не отменяет соседние источники.
  CFB directory обрабатывается библиотекой при открытии контейнера под защитой worker.
- В MIME количество и глубина проверяются до разбора дочерних заголовков и
  извлечения attachment payload. Счётчик включает body/container части;
  для неразобранного остатка после лимита создаётся один marker.
  Заголовки ограничены 64 KiB на часть, multipart — 32 уровнями,
  тело письма — 50 MiB до декодирования. Повреждённый root multipart
  отклоняется; ошибка дочернего multipart сохраняет читаемых соседей.
  Размер обычного base64 leaf вычисляется без декодирования; для прочих byte
  leaves используется верхняя граница wire bytes. Отклонённая MIME-часть
  остаётся доступной через оригинальный контейнер и не создаёт фиктивный файл.
- Вложенное `message/rfc822` не сериализуется заново: сохраняются исходные
  bytes после transfer decode. Проверены LF/CRLF, folded/long headers,
  quoted-printable Windows-1251 внутри ребёнка, 8bit/base64 контейнер и
  наличие/отсутствие завершающей строки. `multipart/digest` также проверен.
- Windows supervisor назначает worker в Job Object до допуска к разбору:
  1024 MiB committed memory на job/process, без breakaway, kill-on-close.
  Проверены отказ выделения памяти без RSS polling, cleanup потомков после
  success/timeout/crash, аварийная смерть supervisor, ошибки создания/назначения
  job без запуска parser и без утечки concurrency slot. Уведомления memory limit
  учитываются даже при отказе во время загрузки интерпретатора.
- На POSIX RLIMIT_AS устанавливается до parser; ошибка установки не игнорируется.
  Worker получает свою process group; при обычном завершении вызова, timeout
  или crash группа уничтожается. Проверены реальный отказ allocation и cleanup
  потомков. Аварийная смерть Linux-supervisor отдельно не квалифицирована;
  process group не заменяет контейнерную границу жизненного цикла.
- Полный gate лимитов ещё открыт: расширенная malformed/bomb матрица требует
  отдельной квалификации. Q01 на v12 прошёл (100 входов, 82.579 MiB;
  все 9 checks, подробности в отчёте приёмки).
  Последующий v11 меняет обход DOCX OLE: nested table/textbox без повторного
  извлечения, header/footer через relationships собственной части, linked OLE
  с явной диагностикой без сетевого запроса. Windows/Linux parser suites и
  браузерный DOCX smoke прошли. Последующий v13 ограничивает DOCX OLE до
  разрешения relationships, оставляя один маркер пропущенного остатка;
  Windows/Linux parser suites прошли, Q01 v12 не является замером v13.
  Корневой файл по-прежнему целиком читается после upload size admission;
  это не потоковый парсер. Общие worker guards не заменяют ранние лимиты.

Семантика OS-лимитов различается: Windows Job Object ограничивает committed
memory ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)),
POSIX RLIMIT_AS — адресное пространство процесса
([Python](https://docs.python.org/3/library/resource.html#resource.RLIMIT_AS)).
Это не обещание единого межплатформенного порога RSS. Windows оставляет RSS
polling дополнительной проверкой; основная защита не зависит от его результата.
