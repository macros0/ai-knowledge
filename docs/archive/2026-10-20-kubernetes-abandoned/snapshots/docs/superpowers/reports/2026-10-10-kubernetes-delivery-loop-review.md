   соответствующего caller; исторические next/OPEN не исполняются повторно.
   Доказательства остаются в acceptance, очередь — только в общем плане.

## Уточнение при повторном запросе о зацикливании

Windows311/Linux319 и audit protocol Windows329/Linux344, а прежние рекомендации
по-прежнему начинались с повторного исправления completion/retry. Карточка 2б

Исправлены эти три противоречия и определён один ближайший законченный caller.
Основания: раздел «Изменение после разбора» этого отчёта; разделы «Карточка 2б»
и «Дополнение проверки — 09.10.2026» общего плана. Это проверка текущих документов,
не новый разбор всей сессии. Прежние компонентные результаты не перезапускались.

Правила против повторов уже существовали в плане, но документ сам продолжал
содержать устаревшие поручения. Их удаление проверено; улучшение фактического
исполнения сможет подтвердить только закрытый штатный сценарий, а не эта правка.

Оставались три устаревших формулировки: строка состава кандидата всё ещё называла

## Рекомендации и изменения плана

Исполнять [конечный остаток 2б](../plans/2026-10-03-kubernetes-rollout.md#конечный-остаток-2б-и-ближайшая-проверка):

1. Реализация полного backup API caller проверена Windows449/Linux480.
   Закрыть оставшийся настоящий Pod-путь карточки 2б.3.2: producer success
   на существующем стенде сразу после этого caller, до остальных restore/migrate.
   Integrity/totals/snapshot уже имеют common caller/API поддержку.
   PG export уже принят компонентно, включая настоящий архив и отдельный restore.
   Audit hold/export не являются следующими поручениями; настоящий backup
   проверяется уже в 2б.3.2, затем используется в общем 2б.4. Неизменные proofs
   не повторяются. После clean отказа ближайшие действия уточнены в верхнем разделе.
2. Закрыть остальные штатные migration/backup/restore callers и captured
   application retirement в `Manager.stop` на том же кандидате.
3. Проверить единую связанную реализацию Windows/Linux и настоящим native
   Job/caller сценарием, затем handoff/activation и домашний непустой lifecycle.
4. Выпустить проверяемый комплект; TLS и реплики выполнить следующими этапами.

Known-completion retry/deadline и Linux publisher/waiter уже проверены; прежние
рекомендации выполнить их заново удалены. В общем плане добавлена короткая
карточка первого caller с критериями окончания и пределом расширения предпосылок.
Два цикла только с новыми helper/proof/status требуют локализации блокера перед
третьим; новый полный аудит либо очередная матрица не заменяют закрытие caller.

Не повторять неизменные 806/A/Scale/terminal291 ради нового статуса. Узкий
RED/GREEN не требует автоматически полной матрицы; изменение общего guard
проверяется по его области, итоговые required checks сохраняются. Новый blocker
нуждается в воспроизводимом отказе штатного caller или уже согласованном
требовании. Гипотеза сама по себе не добавляет release gate.

Не создавать новый controller/store/executor/стенд для каждой части. Не принимать
private582 в runtime до связанной приёмки. Opt-in TLS-specific T3–T6 и реплики
следуют после compact; общие guards, durable outbox и выбранная явная DR-ротация
ключа сохраняются. Реквизиты внешней среды относятся к отдельной deploy-копии.
R5 quarantine и R1 retirement не получают нового разрешения на очистку/повтор.

## Точечная повторная проверка: почему конечный результат всё ещё открыт

Проверка относится к sealed metadata source
`d0c7323d7ff18553ee8f349f83081f08f372e5e966c671e707353341f2330a53`.
579 исходных hashes и 27 записей scope сверены с файлами; runtime не изменён.
Тестовые счётчики ниже прочитаны из результатов прежнего исполнения, не являются
новыми прогонами этой проверки. Новая полная диагностика сессии не выполнялась.

1. **Ожидаемый отказ caller ещё не является backup.** Owning test
   `compact-delivery/effect-tests.py.before-backup-complete:2614–2624`
   явно ожидает `OperationError`, отсутствие manifest и ноль completion/delete.
   `compact-delivery/backup-metadata-component.json:25–40` также отделяет prefix/API
   от actual producer/full backup/native. Поэтому текущие 368/399 подтверждают
   продвижение префикса, но не готовый комплект. Новая карточка требует отдельный
   положительный полный caller и настоящий успех producer.
2. **Не определён конец согласованного backup.**
   `compact-delivery/lifecycle.py.before-backup-complete:15052–15099`
   содержит только before totals и записывает complete manifest перед
   `verify_backup`; `:2967–3002` проверяет hashes/trust, без проверки tar contents.
   Это прочитанный путь, не воспроизведённая здесь авария. В карточку добавлены
   after totals, семантическая проверка файлов до публикации и отказные проверки
   finalization/ENOSPC/invalid identity без consumer-visible complete manifest.
3. **Завершение producer и toolbox нельзя механически соединить.**
   `compact-delivery/lifecycle.py.before-backup-complete:978–991`
   показывает, что producer complete сверяет before/after и пишет `/work/complete`;
   `:9308–9326` запускает отдельный completion и retirement. План теперь требует
   одного согласованного завершения. Возможная гонка при их соединении остаётся
   риском предстоящей реализации, а не заявленным результатом live теста.
4. **Документ продолжал поручать завершённый участок.** В окончании карточки
   2б.3.1 оставался переход к `check_integrity.py`, хотя текущий prefix включает
   integrity/totals/snapshot. Поручение удалено; единственный следующий результат
   — полный backup. Настоящая проверка этого результата перенесена ближе, чтобы
   ошибки среды/producer обнаруживались до следующих restore/migration helpers.

Исправлены общий план, краткая TLS-очередь и этот отчёт; acceptance прошлых
snapshot не переписана. Код, runtime, source seal, кластеры и safety deadlines
этой правкой не меняются. После review продолжать owning backup-критерий;
не запускать ещё один полный разбор зацикливания ради обновлённого статуса.
