# Добавление языка: стоп-слова, перевод интерфейса и справочников

Инструкция администратора (роль `KB_Admin`). Панель управления — **/admin/languages**
(«Поддержка языков»).

## 1. Что значит «язык» в системе

Язык = запись в таблице `locales` (статус `draft` / `active` / `disabled`) + три
необязательных слоя:

| Слой | Что даёт | Где настраивается |
|---|---|---|
| Стоп-слова | язык-aware поиск (запросы на этом языке не шумят служебными словами) | «Стоп-слова» |
| Runtime UI-словарь (override) | переводы интерфейса без релиза фронтенда | «Перевод интерфейса» |
| Переводы справочников | локализованные теги / названия разработок / модули | «Перевод справочников» |

Статус `active` (двухуровневая модель, 08.09.2026) делает язык доступным: в поиске
(стоп-слова объединяются по всем активным языкам) и в `request_locale` (отображение
справочников по cookie). **В переключателе языка (топбар) активный язык появляется
только если он есть в статическом манифесте фронтенда** (`ru/en/de`) — «активный» ≠
«UI-язык». `ru` — fallback, его отключение запрещено.

**Важно про поиск:** стоп-слова действуют ТОЛЬКО на сторону запроса. Индексная
формула заморожена (индекс строился с фиксированным ru-набором) — реиндекс при
правке стоп-слов не нужен и не поможет.

## 2. Два сценария добавления

**(а) Корпусный язык (стоп-слова/поиск), без UI** — всё через Admin UI, релиз не
нужен: добавить → импортировать стоп-слова → активировать (§3). В топбар такой
язык не попадёт (нет в манифесте), runtime-словарь автосидируется en-копией.

**(б) UI-язык (появляется в переключателе)** — дополнительно минимальный релиз
фронтенда:
1. запись в `frontend/src/i18n/locales/index.js`: `de: { label: "Deutsch", short: "DE",
   messages: en }` — для «заглушки» (английские строки + немецкие форматы дат/чисел)
   указывается ССЫЛКА на en-словарь, отдельный файл не нужен; реальный перевод — позже
   через runtime override (§8);
2. синхронно `frontend/src/i18n/boot.js` (no-JS список `["ru","en","de"]`);
3. тест консистентности `frontend/test/i18n.test.mjs` прогоняется автоматически.

После релиза язык донастраивается через Admin UI, как в сценарии (а).

## 3. Пошаговая процедура

1. **Добавить язык** (форма код+название) — появится строка со статусом «Черновик».
2. **Импортировать стоп-слова** (кнопка «Стоп-слова»): категория BM25,
   «Предпросмотр» → «Применить» (merge — дополнить сид, replace — заменить набор).
3. **Активировать язык.** Guard: есть хотя бы одно BM25-слово (гейта «presence в
   манифесте фронтенда» НЕТ с 08.09.2026). При активации языка без runtime-словаря
   автосидируется полная en-копия (v1, note «auto: en copy on activation») — она
   станет стартовой точкой перевода в «Перевод интерфейса». Переключатель языка
   (для языков манифеста) появится сразу без перезагрузки; после отключения — сразу
   исчезнет.
4. *(Опционально)* **Перевод интерфейса** — см. §8.
5. *(Опционально)* **Перевод справочников** — см. §9.
6. Проверить поиск на новом языке (кнопка «Проверить на тестовых запросах»
   в редакторе стоп-слов).

## 4. Стоп-слова: где взять и как подготовить

Проверенные источники списков (бери заготовку, не истину):

| Источник | Что это |
|---|---|
| **stopwords-iso** — https://github.com/stopwords-iso/stopwords-iso | списки для ~50 языков, производные Snowball и других канонических наборов; файлы `<язык>.txt`, одно слово на строку — формат готов для вставки в textarea |
| **Snowball** — https://snowballstem.org/algorithms/ | исходные канонические списки стеммеров (страницы по языкам) |
| **NLTK** — `nltk.corpus.stopwords` (Python) | стандартные списки по языкам |

Обязательно **кураторская чистка под домен**: выкинуть слова, которые в вашем
домене несут смысл. Для HR/SAP-домена это, например, «работа/работы», «документ/
документы», «поля» — по таким словам реально ищут.

**Формат импорта:**
- одно слово на строку (textarea принимает многострочную вставку);
- нижний регистр; только буквы/цифры, без пробелов, апострофов и дефисов;
- алфавит: **латиница с европейскими диакритиками + кириллица + цифры**
  (`a-zа-яё0-9ßà-öø-ÿā-žșț`, с 08.09.2026) — валидатор и токенайзер работают с
  ними. Набор покрывает европейские языки (de/fr/es/pt/it/скандинавские/pl/cz/
  hu/ro/tr) — акценты вроде `après`, `élève`, `español` импортируются и
  токенизируются целиком;
- длина ≤ 64 символов, практически осмысленно ≥ 2 (однобуквенные токены
  отбрасываются поиском);
- лимит 10 000 слов на набор;
- режимы: **merge** (дополнить текущий набор) / **replace** (полная замена).
  Пустой replace — деструктивная очистка набора: кнопка меняется на
  «Удалить все N стоп-слов» и требует явного подтверждения (сервер проверяет его
  отдельно — API без UI тоже не очистит набор молча).

**Немецкий язык и ß.** Токенайзер НЕ нормализует ß→ss (`Maße` ≠ `Masse` — это
разные слова), поэтому в стоп-лист добавляйте **обе орфографии**: `dass` и
`daß` (подсказка показывается в редакторе стоп-слов для локали de). Если в
списке встречаются слова только с умлаутами/ß — они валидны и импортируются
(даже если как токены немецкого запроса почти не встречаются, лишними не будут).

**Французский и слитные формы (апостроф/дефис).** Токенайзер режет ПО АПОСТРОФУ И
ДЕФИСУ (это разделители, не буквы): `aujourd'hui` → токены `[aujourd, hui]`,
`celle-ci` → `[celle, ci]`. Полная слитная форма НИКОГДА не станет токеном — как
стоп-слово она бесполезна, импорт отклоняет её с понятной ошибкой. При чистке
французского списка **удаляйте слитные формы** (или, если фрагмент осмыслен,
добавляйте его: `celle-ci` → `celle`). Списки из корпусов со слитными/дефисными
формами (часть NLTK-производных) требуют такой чистки по §4.

**Языки вне европейского набора букв:** слова с буквами, которых нет в алфавите
выше (кириллица покрыта; греческий/арабский/CJK и т.п.), токенайзером не
распознаются. Добавление нового языка с другими буквами = расширение
`sparse.TOKEN_EXTRA_LETTERS` (смена индексной формулы) + полная пересборка
sparse-векторов:
```powershell
python scripts/rebuild_sparse.py   # из backend/, требует Qdrant и БД
```

## 5. BM25-слова и маркеры: в чём разница

У стоп-слов два вида (`kind`), конвейер обработки запроса:

```
запрос → tokenize(query, стоп-слова kind=bm25)   ← вычитаются ДО лексического
                                                    поиска и ДО маркеров
       → токен не в kind=marker                    ← фильтр ТОЛЬКО маркеров
                                                        Matched terms / Title match
```

| | **BM25** (`kind=bm25`) | **Маркеры** (`kind=marker`) |
|---|---|---|
| Где действует | текст запроса: BM25-ветка поиска + термины Matched terms | доп. фильтр ПОСЛЕ bm25, только для маркеров Matched terms / Title match |
| Что это | «структурные» слова: предлоги, союзы, артикли, местоимения (и, в, на, the, of, for) | вопросительные/вспомогательные слова, пережившие bm25-фильтр (какие, есть, можно) |
| На что влияет | какие токены вообще участвуют в лексическом поиске | какие блоки LLM считает «относящимися к вопросу» (анти-шум `Matched terms`, `Title match`); на сам BM25-вектор запроса НЕ влияет |

Оба вида — только сторона запроса, оба меняют поведение сразу, без реиндекса.
Удаление дефолтного ru-слова возвращает его в запросы, но НЕ в индекс (в индексе
его нет — индекс строился с замороженным ru-набором).

## 6. Почему у ru есть маркеры, а у en — нет

Это дизайн, а не пропуск. В панели у en отображается «90 / 0» (bm25/marker) —
**норма**.

- **ru**: сид BM25 содержит структурные слова (и, в, на, не, для…), но НЕ
  вопросительные — они живут отдельным сидом `kind=marker`: «какие, какой, какая,
  каких, каким, кто, где, когда, почему, зачем, сколько, есть, нет, да, можно,
  нужно, должен, должна, может, могут, будет, быть, также, только».
- **en**: сид BM25 **уже включает** вопросительные и вспомогательные слова:
  what, which, who, whom, when, where, why, how, is, are, do, does, did, has,
  have, had, will, would, should, could, may, might…
- Маркерный фильтр выполняется ПОСЛЕ bm25-фильтра → для en-запросов эти слова
  уже вычищены, отдельный слой избыточен.

**Для нового языка:** проверьте, покрывает ли ваш bm25-список вопросительные
слова языка. Если нет — внесите недостающие как `kind=marker` (не в bm25, если
хотите, чтобы они продолжали участвовать в лексическом поиске, но не считались
маркерами блока).

## 7. Осторожно: любое изменение — только после исследования поиска

Стоп-слова меняют поведение поиска **мгновенно**. Слишком агрессивный список
молча выкидывает значимые термины из запросов — пользователь этого не заметит,
просто «поиск стал хуже находить».

### Методика (обязательная)

1. **Зафиксировать критерий ДО прогона** (иначе «после» легко принять желаемое
   за действительное):
   - **Регрессия** = источник baseline пропал из выдачи ЦЕЛИКОМ, при этом он
     матчился содержательными терминами (не только стоп-словами);
   - **Не регрессия** = смещение позиции / выход из топ-5 при живом контентном
     матче (законное переранжирование);
   - **Новое ложное срабатывание** = появился источник, сматченный только
     возвращённым в запрос словом, с нерелевантным теме заголовком (актуально
     при replace, удаляющем слова из набора).
2. Снять эталон ДО изменения:
   ```powershell
   .\scripts\start-all.ps1        # нужен живой стек (Qdrant, Ollama, PG)
   cd backend
   python scripts/probe_sources.py --baseline
   ```
3. Применить изменение стоп-слов через UI («Предпросмотр» → «Применить»).
4. Повторить прогон и сравнить:
   ```powershell
   python scripts/probe_sources.py
   ```
   Вывод: `ok` — все baseline-источники на месте; `!!` — источник пропал,
   разбирайте по критерию. Для каждого источника показаны matched terms (`mt=…`) —
   по ним видно, чем источник матчился.
5. При сомнении — откат: «История импортов» → «Откатить».

Лёгкая альтернатива для быстрой проверки — кнопка «Проверить на тестовых
запросах» в редакторе стоп-слов (top-N источников по вашим запросам, без фиксации
эталона; для приёмочных прогонов используйте probe_sources).

### Реальный пример исследования (подключение EN-стоп-слов, 06.09.2026)

Проблема: EN-вопрос с the/of/for против RU-корпуса с латинскими SAP-идентификаторами
давал ложные BM25-срабатывания. Критерий зафиксирован заранее (см. выше).
Прогон по 5 RU-контрольным запросам + 2 EN-диагностическим:

| Запрос | До (en выключен) | После (en/bm25 подключён) |
|---|---|---|
| `the certificate of disability` | 10 источников; шум, сматченный ТОЛЬКО стоп-словами: «Правила ведения User-Exit разработок для BEx-переменных» (`mt=the,of`), «Форма GET_BW_ENH» (`mt=of`) | **4 источника**, все по содержательным терминам `certificate, disability` (блоки `IS_CERTIFICATE_OF_DISABILITY`) |
| `for all entries in table` | 7 источников, шум по `for/all/in` | **1 источник** — точное попадание «SELECT … FOR ALL ENTRIES OF TABLE» |
| 5 RU-контрольных | — | все `ok`, без регрессий |

Разбор: шумовые блоки исчезли, потому что перестали матчиться by `the/of/for`;
поле-уровневые блоки (`CERTIFICATE_DATE` и т.п.) сместились за топ-10 — по
критерию это переранжирование, не регрессия. Изменение принято.

## 8. Перевод интерфейса (кратко)

- **Экспорт** (кнопки в разделе): «Скачать текущий язык» — эффективный словарь
  (override → встроенный словарь → ru-fallback), образец для переводчика;
  «Скачать английский источник» (с 08.09.2026 — английский международный
  язык-источник для перевода; ru-словарь доступен через «Скачать текущий язык»
  при выбранном ru в редакторе); «Скачать только активный override» (бэкап).
- **Загрузка = ПОЛНАЯ замена override-слоя.** Для точечных правок удалите из
  файла непереопределяемые ключи — остальные продолжат браться из встроенного
  словаря и ru. Не заливайте эффективный образец целиком.
- Валидация при загрузке: ключи ⊆ ru-словаря, `{param}`-плейсхолдеры совпадают,
  plural-формы соответствуют локали (en — `one, other`; ru — `one, few, many`).
- **Полный перевод языка** ведите через словарь релиза (`en.js` + релиз
  фронтенда); runtime override — для оперативных точечных правок без релиза.

## 9. Переводы справочников: как устроено и как улучшать

### Особенности архитектуры

- **Канонический текст — неизменен**: теги, названия разработок и метки модулей
  в поиске, Qdrant и `okf_concepts` остаются в каноническом (ru) виде — реиндекс
  не нужен и не делается.
- **Перевод — слой отображения**: `tag_translations` / `development_translations`
  / `attribute_value_translations`; пользователь видит `display` по своему языку
  (cookie `okf.locale`). Фильтр по тегу понимает и перевод (резолв: перевод →
  канонический текст).
- **Машинные черновики** помечены `is_machine_translated` и «требуют проверки»,
  пока человек их не подтвердит. Бэкфилл **идемпотентен**: подтверждённые
  человеком переводы НИКОГДА не перезаписываются; машинные без подтверждения —
  обновляются при повторе.
- **Провайдер**: `translation_provider=llm` — внешний LLM-маршрут (в dev —
  OpenRouter; модель видна в разделе «Перевод справочников» и печатается CLI
  перед запуском); `off` — только ручной ввод (для прод без интернета).
- Счётчик «без ручного перевода» в UI считается тем же запросом, что и цели
  бэкфилла — показанное число совпадает с фактическим прогоном.

### Действия для улучшения переводов

| Кто | Действие | Как |
|---|---|---|
| Admin | Запустить автоперевод | «Перевод справочников»: чекбоксы сущностей (теги/разработки/модули), предупреждение о машинных черновиках, «Перевести». Или CLI: `python scripts/backfill_translations.py --locale en --entities tags,developments,attributes` (из `backend/`; печатает провайдера и модель ДО запуска) |
| Admin / Editor | Просмотреть черновики тегов | «Справочник тегов» → фильтр «Требует проверки перевода» → раскрыть «Переводы» → «Подтвердить» (подтверждает все машинные переводы тега) или «Подтвердить все (N)» массово |
| Admin / Editor | Исправить перевод тега | в «Переводах» тега — поле правки для текущего языка интерфейса → «Сохранить». Правка становится РУЧНОЙ (подтверждённой) и защищена от будущих бэкфиллов |
| Admin | Догнать новое | после массового добавления тегов/разработок — повторный бэкфилл: дообработает только отсутствующее/непроверенное, ручные не тронет |
| Admin | Приоритизировать ревью | начинать с тегов с большим счётчиком использования (виден в «Справочнике тегов») — они чаще встречаются пользователям |
| Admin (прод без интернета) | Ручной ввод | `translation_provider=off` + ввод переводов вручную |
| Любой пользователь | Сообщать о неудачном переводе | если display-имя тега/разработки не находится фильтром или вводит в заблуждение — сообщить администратору (фильтр принимает и канонический текст, так что поиск не ломается) |

**Ограничение:** ревью-интерфейс есть только для тегов. Названия разработок и
метки модулей переводятся машинным бэкфиллом и отображаются локализованно, но
ручная правка их переводов через UI пока не предусмотрена (задел на будущее).
