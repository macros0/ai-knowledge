# Диагностика ошибок без доступа разработчика к production

Администратор открывает **Администрирование → Диагностика ошибок**. Базовый
ограниченный журнал кодов ошибок хранится до семи суток. Для воспроизведения
редкой проблемы администратор выбирает область и включает подробный сбор на
5, 15, 30 или 60 минут. Сеанс останавливается вручную или автоматически;
закрытая вкладка не продлевает срок. Для ошибок браузера пользователь отдельно
подключает свой браузер; администратор может выдать одноразовый код. Сбор
браузера требует явного согласия в интерфейсе и прекращается при выходе.

После воспроизведения запишите показанный пользователю **код обращения**,
остановите сбор и запросите пакет. Откройте «Состав» до скачивания: `partial`,
`gaps`, покрытие времени каждого компонента и число событий показывают, какие
данные отсутствуют. `recorder_loss` означает потери в очереди backend за время
текущего процесса: такой пакет консервативно помечается неполным даже при узком
фильтре. После аварийного завершения процесса счётчики в памяти недоступны;
отсутствие этого маркера в offline-пакете не доказывает отсутствие потерь.
`frontend_loss` означает пропуски или деградацию в Node spool, а
`frontend_status_unavailable`/`frontend_status_stale` — отсутствие свежего
подтверждения его состояния; оба случая делают пакет неполным.
`invalid_input` означает, что один или несколько файлов событий не удалось
прочитать полностью либо их записи не прошли проверку схемы. Доступные
события остаются в пакете, но полнота выбранного периода не подтверждена;
проверьте права на диагностический каталог и повторите сбор после исправления.
`recorder_sampled_success` — число намеренно не записанных успешных HTTP
запросов **с запуска backend**, а не только в выбранном пакете: при нагрузке
сохраняются первые 20 в секунду на шаблон маршрута. Scope счётчиков recorder
и frontend также указан в `manifest.json` (`counter_scopes`).
Ошибки HTTP, предупреждения и события операций этим ограничением не режутся.
Скачанный ZIP администратор вручную размещает в SharePoint в месте, доступном
только согласованным участникам, и передаёт разработчику ссылку. Приложение
не отправляет пакет наружу само. Пакет в системе хранится до
24 часов и затем удаляется; удаление из интерфейса прекращает новые скачивания.

В пакете только фиксированные файлы: `summary.txt`, `manifest.json`,
`events/{backend,frontend,browser}.jsonl`, `snapshots/{runtime,operations}.json`.
События проходят строгий allowlist: коды, время, UUID обращения/операции,
разрешённые имена модулей и функций, числовые счётчики. Сообщения исключений,
тела запросов и ответов, SQL, промпты, текст документов/чата, ключи,
произвольные пути, стеки с динамическими именами и `docker logs` не входят.
Статус зависимостей берётся из кэша без нового запроса к ним. ZIP имеет
проверяемые CRC и SHA-256; `manifest.json` содержит версию схемы, ревизии
сборок, интервалы и пропуски. Пустой компонент или `unknown` означает отсутствие
подтверждённых данных, а не подтверждение его исправности.

## Развёртывание и лимиты

Для production задайте `OKF_DIAGNOSTICS_DIR=/srv/okf-knowledge/diagnostics`
**вне** `OKF_DATA_DIR` (`/srv/okf-knowledge/data`) и
`DIAGNOSTICS_MIN_FREE_MB=2048`. Один
и тот же production env-файл передавайте как `OKF_RUNTIME_ENV_FILE` и в
`docker compose --env-file`. Перед запуском стека создайте каталоги на хосте:

```bash
python3 backend/scripts/prepare_diagnostics_dirs.py \
  --root /srv/okf-knowledge/diagnostics --data-dir /srv/okf-knowledge/data \
  --app-uid 1000 --app-gid 1000 --frontend-uid 1000
```

Если UID frontend отличается от UID backend, на хосте требуется `setfacl`:
bootstrap даст только frontend UID чтение каталога `backend/control` и новых
файлов в нём. Frontend монтирует этот каталог только для чтения; весь backend
spool и ZIP ему не доступны. Backend монтирует frontend spool для чтения.
Оба сервиса после начальной подготовки запускаются непривилегированно.
На Windows выберите отдельную папку с унаследованным ACL только для
запускающего пользователя и проверьте реальную запись/чтение; Linux bootstrap
на Windows не выполняется и не раскрывает папку всем пользователям.

Квота: 500 MiB суммарно (backend 480, frontend 20), в backend baseline 50,
сеанс 100, один ZIP 200 MiB. Перед записью сохраняется минимум 2 GiB
свободного места. Сегменты ограничены 5 MiB; старый baseline ротируется,
подробный сеанс по достижении лимита останавливается. Очередь пакетов:
одна сборка, два ожидающих, не более трёх запросов в час на администратора.
У одного администратора одновременно может быть только один незавершённый
пакет. Очистка старых файлов и метаданных выполняется при запуске backend и
затем регулярно.
Docker `json-file` для пяти сервисов ограничен `10m × 3` **на контейнер**;
его 150 MiB в худшем случае не входят в диагностическую квоту. Следите за
местом для обеих категорий.

Если после аварии Node показывает `storage_degraded` и в frontend-каталоге
остался `writer.json`, сначала убедитесь, что прежний frontend-процесс точно
завершён и его каталог принадлежит этому Compose project. Только после этого
эксплуатационный администратор может убрать старый marker и перезапустить
frontend; автоматического захвата чужого marker нет. Не удаляйте другие файлы
spool для «исправления» ошибки.

При штатном `docker compose restart frontend` PID 1 сначала посылает Next
запрос на сброс безопасного журнала и освобождение marker, затем завершает
процесс. После SIGKILL/OOM marker намеренно остаётся до ручной проверки.

Флаги `DIAGNOSTICS_BASELINE_ENABLED`, `DIAGNOSTICS_CAPTURE_ENABLED`,
`DIAGNOSTICS_BUNDLE_ENABLED`, `DIAGNOSTICS_DOWNLOAD_ENABLED` управляют
возможностями раздельно. Выключение подробного сбора не удаляет baseline.
Изменение env требует перезапуска соответствующих контейнеров. Не меняйте
частоты и квоты без замера свободного места и нагрузки.
На синтетическом поиске в Linux Docker Desktop временный capture увеличил
p95 на 18,2%, а одновременная сборка ZIP — на 37,7%; на отдельном CT 102
получено +17,8% и +67,4%. Оптимизация вынесена в отдельную задачу; сбор
включайте только для ограниченного воспроизведения и следите за задержкой
бизнес-запросов. Эти цифры не являются оценкой нагрузки реального корпуса.

## Когда backend недоступен

Не останавливайте работающий backend ради сбора: его каталог занят writer lock,
а UI/API сохраняет аудит. После аварийной остановки можно выполнить offline
экспорт той же версией образа, без подключения к PostgreSQL:

```bash
./scripts/production/collect-diagnostics.sh \
  --env-file deploy/production/bundled.env --project okf-prod \
  --diagnostics-dir /srv/okf-knowledge/diagnostics \
  --since 2026-09-28T08:00:00Z --until 2026-09-28T09:00:00Z \
  --output /srv/okf-support/support-20260928.zip
```

Если работающий Compose project использует дополнительный файл конфигурации
(например, для LXC), передайте тот же файл через
`--compose-override /путь/к/override.yml`. Иначе offline-контейнер может
получить другой образ или параметры запуска. Архив bundled backup хранится
в закрытом каталоге владельца; разовые контейнеры backup/restore читают и
пишут его от root, а постоянный backend продолжает работать под UID
приложения.

Для внешней БД используйте соответствующий env-файл. Выходной каталог должен
существовать и быть доступен UID приложения; файл не должен существовать.
Скрипт не останавливает сервис и откажет при активном backend. `--dry-run`
проверяет аргументы и состояние без запуска контейнера. CLI создаёт архив
эксклюзивно, проверяет свободное место, пишет безопасное событие
`offline_export_requested` в локальный журнал и указывает
`audit_reconciliation=pending_sql`: SQL-аудит при отсутствии БД не обещается.
Он не сохраняет полный Docker inspect, конфиг или журналы. Код возврата 0 —
успех, 2 — неверный ввод, 3 — writer занят/нет доступа, 4 — квота/сборка.
Wrapper передаёт CLI только статус, код выхода, `OOMKilled`, времена старта и
остановки и SHA-256 ID образа контейнеров выбранного Compose project, включая
одноразовую службу `migrate`. Эти поля
попадают в `snapshots/runtime.json`; если состояние контейнеров недоступно,
манифест содержит `container_state_unavailable`.

Если оба контейнера остановились до записи события, процесс завершён OOM-kill
или браузер был офлайн/не присоединён, соответствующих событий может не быть.
`gaps` и `coverage` в манифесте следует читать перед выводом о полноте.
Старые raw LLM dump-файлы, если они существовали до этой функции, в пакет не
попадают; обращайтесь с ними отдельно как с данными приложения.

## Откат

Сначала выключите `DIAGNOSTICS_CAPTURE_ENABLED`, затем
`DIAGNOSTICS_BUNDLE_ENABLED` и `DIAGNOSTICS_DOWNLOAD_ENABLED`; остановите
активный сеанс и перезапустите сервисы с выбранным runtime env. Baseline и
очистку по сроку оставьте включёнными, если не требуется полный аварийный
отказ. Новые таблицы SQL и уже собранные ZIP не удаляйте ради отката кода.
Образ, возвращающий запись raw LLM ответов в production, использовать нельзя:
сохраните соответствующее исправление или выпустите hotfix. Понижение схемы
проверяйте на копии и только после решения владельца данных. `data.tar`
обычного bundled backup содержит только `OKF_DATA_DIR`; отдельные диагностические
файлы туда не входят. После восстановления одних SQL-записей без ZIP пакет
должен считаться недоступным, а прежний активный сеанс — остановленным.
При восстановлении bundled backup в новый Compose project заранее подготовьте
**отдельный** диагностический каталог и передайте его
`restore-bundled.sh --target-diagnostics-dir`; новый backend не должен делить
writer lock и файлы со старым проектом.
